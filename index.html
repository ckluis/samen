The hard 80% of a SaaS, solved once — and adversarially proven.

Samen is a substrate for one builder, or a small studio, to launch many products without re-solving the parts that are genuinely hard: PII vaulting and masking, crypto-shred erasure, and a two-plane architecture where support works against masked data by default. One command emits a running product that passes its own 19-step gate with zero hand-edits.

The claim, stated honestly

Most vendors tell you support can't see customer data. That is almost never true.

Samen makes a narrower promise and then proves it:

PII is masked by default. Reveal is grant-gated, second-party-approved, logged in a hash-chained log the tenant can read, and time-boxed. Cross-tenant views are aggregate-only and token-blind.
What we deliberately do not claim. An earlier version of this page said “run support without ever seeing PII.” It sounded better and it was false by construction, so it was retired. Support can see PII — through a grant a second person approved, that expires on its own, and that the tenant can audit without asking permission.

That retraction is the shortest honest summary of how this repo is built. Every claim below is attached to a test, a verifier tier, or a committed sabotage that proves the test can fail.

The problem

Every product rebuilds the same 80% — and rebuilds the leak with it.

Ship a B2B SaaS and you will build the same ten surfaces you built last time: authentication, billing, a CRM of some shape, a support desk, notifications, file handling, CSV export, search, settings, and an admin view your own staff uses to unstick customers.

auth billing CRM support desk notifications files CSV export search settings admin / operator view

That is the famous 80%, and the usual conclusion is that it is a code-reuse problem: write it once, carry it forward, save the months. That conclusion is the cheap half of the story.

Every one of those surfaces is also a place customer data comes out. The support desk renders it. The CSV export writes it into a file somebody then emails. The logs catch it in passing. The admin impersonation view sees everything, by design — that is what it is for. Add a surface and you have not added one feature; you have added another door onto the same data, each with its own idea of who may open it and whether anyone finds out.

So the real cost of the 80% is not the months. It is that each rebuild reproduces the disclosure surface, and the rule that was supposed to govern it now has to be remembered in one more place, by one more person, under deadline.

Six data surfaces × three products = eighteen places a rule has to be remembered. Consolidating them does not help unless the consolidated version changes what a field returns when nobody asked a question.

The turn

Samen solves the 80% once, at the substrate — and makes masking the default state of a field, not a feature someone remembers to add.

A field declared as PII does not hold plaintext anywhere at rest. The row carries a vt_… token; the value lives in a per-subject-keyed vault; and what every reader gets back — the desk, the JSON API, the CSV writer, the log line — is •••• unless a grant a second person approved says otherwise, and even then only until it expires.

This is a disclosure-surface problem, not a code-reuse problem. Sharing a support-desk library across three products gives you one implementation of the desk. It does not give you one place where the decision to show a customer’s phone number is made. Reuse alone just means you copied the leak forward with tidier code. What has to be shared is the field’s default, the single decrypt path, and the audit record — not the CRUD.
The architectural spine

Six idioms, applied to every object, in every scope.

The interesting word is not six. It is every. A masking rule that the support desk honours and the CSV writer forgets is not a masking rule — it is a convention, and conventions fail at the exact moment someone is shipping under pressure. So these six hold at the substrate, for every resource, on both planes, in code nobody has to remember to call. A guarantee that holds in most places is not a guarantee.

Idiom 01

Self-qualifying storage

You write attribute :name. A compile-time transformer projects it to com_name — the same qualified name in the database, in CDC, in logs, and in the catalog. Abbrevs are permanent, like a ticker: once com_ means company, it means company everywhere, forever.

Idiom 02

A machine catalog

Every table and every field lands in tam_table and fld_field, written inside the migration transaction rather than by a nightly scan. A committed schema.dict.json is what grounds LLMs and tooling. A reference to an uncatalogued column does not compile, so the catalog cannot quietly fall behind the schema.

Idiom 03

The PII vault

Declaring a pii_attribute routes the value into a per-subject-keyed vault; the row keeps only a vt_… token, and plaintext is nowhere at rest. Masking is the field’s normal value: %Masked{} renders as •••• in UI, JSON, CSV and logs alike — CSV masks by omission. There is exactly one decrypt chokepoint.

Idiom 04

Postgres as the engine

Events ride LISTEN/NOTIFY. Queues drain with SKIP LOCKED. Background work is Oban, in the same database as the rows it touches. That buys one transaction boundary instead of three systems agreeing later: a reveal approval and the job that auto-revokes it commit together, or neither happens.

Idiom 05

A malleability ladder

Customer-specific shape has four rungs, in order of blast radius: Tier-0 config rows, Tier-1 jsonb custom fields validated at write, Tier-2 tenant-defined objects, Tier-3 builder code-composition. Types are declared, not stringly — Money, Percent, Score, Duration, Priority, URL, Email, Phone, Address — and the vault write path re-runs each type’s cast_input, so a value is validated and normalized before it is tokenized.

Idiom 06

Two planes, one core

The tenant plane and the operator plane are two front doors onto one kernel, not two codebases that drift apart. Your staff read the same %Masked{} values your customers’ users do. Seeing plaintext takes a grant that a distinct party approved — enforced in policy and by a database CHECK — that expires on its own and lands in a hash-chained log the tenant can read without asking.

None of the six is novel on its own. What is unusual is refusing to apply any of them selectively: the generators emit them, the verifier tiers check them, and a committed sabotage patch exists to prove each check can actually fail.

Why “self-qualifying” storage matters more than it sounds

Prefixed column names look like a style preference. They are load-bearing, because they are what makes the catalog impossible to drift from the schema.

  • The projection is compile-time, not convention. You write attribute :name on a company resource; a transformer rewrites it to com_name for storage, for the CDC stream, for log fields, and for the catalog entry — one derivation, four consumers, no second place to keep in sync.
  • Abbrevs are permanent, like a ticker symbol. An abbrev is allocated once and never reassigned. That is what lets a column name be a durable identifier across renames, extracts, and downstream systems that saw it years ago.
  • A reference to an uncatalogued column does not compile. The catalog is not a document that describes the schema; it is a dependency of the schema. You cannot add a field and forget to register it, and you cannot register a field that does not exist.
  • This is what makes the rest mechanical. Once every field is qualified and catalogued, “which fields hold PII” stops being tribal knowledge and becomes a query — which is exactly what the vault, the masking renderers, and mix samen.verify.no_plaintext_pii run against.
Idiom 03 · the PII vault

Masking is not a rendering step. It is the field's normal value.

You write pii_attribute :email, :string. A compile-time path routes that field — every write, every read, every export — through one vault chokepoint to a per-subject key. The domain row stores a token, vt_9f2c…. The ciphertext lives in the vault. Plaintext is nowhere at rest.

The consequence, and it is the whole point. Because •••• is what the field already returns, forgetting to mask is not a mistake available to you. There is no un-masked default waiting to leak through a new template, a new serializer, a hurried inspect/1, or a log line someone added at 2am. To get plaintext you have to ask — and asking is the thing that writes the audit record.
UI •••• JSON:API •••• CSV column absent logs · CDC ••••

CSV is the interesting one. It masks by omission — the column is not in the file at all. A masked export cannot be un-masked by staring at it, because there is nothing in the bytes to stare at. Downstream tooling receives a schema without the field, not a field it might one day try to un-redact.

What this costs you. The guarantee is exactly as strong as key custody. Destroying a subject's key material destroys their data everywhere — that is precisely how erasure works here — which means a lost key is an accidental erasure, not a recoverable incident. Samen makes that trade on purpose and does not pretend it is free.
One declaration. One chokepoint. One decrypt path. Four surfaces that all default to ••••, and a CSV that masks by leaving the column out.

Why there is exactly one chokepoint — and what runs on the write path before tokenization

One decrypt path is not an aesthetic preference. It is what makes the guarantee checkable. If plaintext can be produced at forty call sites, then “no plaintext leaks” is forty separate claims, each decaying independently as the codebase grows. Route every read through one function and the claim collapses to a single question a machine can answer: who called it, under what grant, and was it recorded?

  • The verifier can point at it. mix samen.verify.no_plaintext_pii runs as a separate OS process — it does not share the application's memory or its assumptions — and attests that no tier holds plaintext: domain rows, the vault, audit events, rollups, Oban args, the KMS store.
  • The write path validates before it tokenizes, not after. Samen ships rich declared types — Money, Percent, Score, Duration, Priority, URL, Email, Phone, Address. The vault write path re-runs each declared type's cast_input, so the value is validated and normalized before it becomes ciphertext. Get that order wrong and you have stored a malformed value you can no longer inspect, and normalization becomes a migration you cannot run.
  • The token is a join key, not a hint. The row carries vt_9f2c…. It is stable enough to join, group and audit on, and it says nothing about the value behind it. Analytics can use it; analytics cannot resolve it.
  • Masking is a value, not a formatter. %Masked{} is what the field returns. Every surface that renders it — HEEx, JSON:API serializers, CSV writers, the logger, CDC — is rendering an ordinary value, which is why none of them had to be taught about PII.
The reveal path

Support sometimes needs the real value. So make the exception expensive, visible, and self-expiring.

A dispatcher is on the phone with a customer whose address bounced. She needs the address — the actual string, not ••••. Pretending otherwise only pushes the real work into a shared spreadsheet nobody audits. Samen keeps the exception inside the system and charges for it.

Before the grant, the field reads •••• — on every surface, for everyone. For the life of the grant, and only for this subject, and only for the fields named in it, it reads 14 Wharf Rd, Bristol. When expires_at passes it reads •••• again, and nobody had to remember to make that happen.

Four properties, each with teeth. A property enforced only in application code is a property that holds until the next refactor. Three of these four are enforced by the database, where a wrong deploy cannot reach them.
Said plainly: your operators can see PII. Samen does not claim otherwise. It claims that each time it happens, a second person agreed to it, the tenant can read the record without asking anyone's permission, and the access ended on its own. That is a narrower promise than the industry's, and it is one that can actually be kept.
The refused path is not a form validation. It is a table constraint: a row where granted_by = requestor_id cannot exist.
Property 01 — second-party

The requester cannot approve

Two people, always. The policy layer checks it, and so does the table: CHECK (granted_by <> requestor_id). Application code is the part most likely to be wrong, and the part a hurried change touches. The constraint holds anyway — from a console session, a migration, a background job, or a refactor nobody reviewed carefully.

Property 02 — time-boxed

It ends whether or not anyone remembers

Every grant carries expires_at and cannot be renewed in place. The Oban auto-revoke job is enqueued in the same transaction as the approval — so the revocation is already durable before the grant is usable. There is no window in which a live grant exists with no scheduled end.

Property 03 — logged, tenant-side

Written where the tenant can read it

The record lands in a hash-chained, append-only, tenant-readable log. A database trigger refuses UPDATE and DELETE on the chain. The operator cannot edit the record of their own access, and the tenant does not have to file a request to see it.

Property 04 — scoped

Specific fields, specific subject

A grant reveals these fields for this subject. It is not a role that gets unmasked, not a session that gets elevated, and not a support tier that sees more. Two customers means two grants, two approvals, two audit entries.

Each entry carries the hash of the one before it, so removing or editing an entry breaks every entry after it — and the trigger refuses the edit in the first place.
Why the database CHECK matters more than the policy check — and why a grant can never be renewed in place

The policy check and the constraint are not redundant. They fail differently. A policy check lives in code — the layer that gets refactored, mocked in tests, bypassed by a seed script, and reached through paths nobody enumerated. A CHECK (granted_by <> requestor_id) lives in the table definition. It does not care which code path, console session, migration or future rewrite produced the insert: the row cannot exist. For a self-approval to land, both enforcements have to fail, and they have no failure mode in common.

  • “Cannot be renewed in place” prevents the standing grant. A grant with a renew button becomes permanent the first afternoon someone puts it on a schedule. Extending access here means a new request and a new second-party approval — so every extension is a separate, separately-approved entry in the chain. The log shows how many times access was granted, not one row with a date that keeps moving.
  • The auto-revoke is enqueued in the approval's transaction. Not after it, not in a callback, not on a cron sweep. If the job cannot be enqueued, the approval does not commit. The end of the access is durable before the access begins.
  • Cross-tenant analytics is a different actor entirely. Aggregate work runs as a token-blind actor over resources that carry no pii_* columns at all — there is no masked field to unmask, because there is no field. The reveal path refuses that actor structurally, before any grant lookup or vault check is consulted. The two paths are therefore mutually exclusive by construction: an actor that can reveal cannot run cross-tenant, and an actor that runs cross-tenant has nothing to reveal. Neither is a runtime flag someone can flip.
  • The chain is tenant-readable on purpose. An audit log only the operator can read is a log the operator grades themselves. Hash-chaining plus a trigger that refuses UPDATE/DELETE means the tenant is reading a record the operator could not have quietly tidied.
Idiom 06 · Two planes, one core

Your admin tool is the biggest leak in the company. Unless it is the same app.

Every product built on samen runs two planes over the same resources: a tenant product plane and an operator control plane. The operator plane is not a second application with its own queries — it is the same objects rendered through a different actor. Support sees the real UI, the real layout, the real workflow, the real bug. The PII inside it renders ••••.

Same route, same left nav, same breadcrumb, same tabs, same six rows in the same order, same non-PII values — LD-40277, the hours-of-service clock, the dispatch status. This is not a redacted screenshot of a different screen. It is the screen, rendered for an actor whose PII fields resolve to %Masked{}. The operator can reproduce the bug without reproducing the disclosure — and still has enough left on the row to work the ticket.

One resource definition, three actors

The third actor cannot be granted anything, because there is nothing there.

Cross-tenant work — MRR, queues, cohorts, backlog health — runs as a token-blind actor over resources that carry no pii_* attributes at all. Not filtered at query time. Not masked at render time. Structurally absent from the schema. The reveal path refuses that actor before it ever reaches a grant check or the vault.

Masking is a property of the actor, not of a screen. The third lane has no plaintext path to refuse — the columns are not in its schema.
Actor 01 · Tenant

Reads its own data in the clear

The dispatcher who entered the driver sees the driver. Scoping is enforced at the resource, not bolted on per-query, so there is no "forgot the WHERE clause" class of bug to audit for.

Actor 02 · Operator

Masked by default, grant-capable

Support and engineering render the real product through masked impersonation. Plaintext requires a grant a different person approved, time-boxed by expires_at, with an auto-revoke job enqueued in the same transaction as the approval.

Actor 03 · Aggregate

Token-blind, and empty of PII

Cross-tenant analytics run over resources with no pii_* attributes. The reveal path structurally refuses this actor before any grant lookup or vault call — there is no vt_… in reach to exchange.

samen_web · planes + identity spine masked impersonation second-party approval CHECK (granted_by <> requestor_id) hash-chained, tenant-readable log
Why the operator plane is built from the same objects — and why a separate admin app is the leak

The usual shape is a second application: an internal console, its own controllers, its own queries, its own serializers, written faster and reviewed less than the product. It is the same database with none of the same discipline.

  • Every query path is a road to plaintext. Masking that lives in the product's render layer is simply not present in the admin app. A hand-written SELECT in a console returns the column, and nothing in the system objects.
  • Divergence is silent. The product adds a field; the admin app does not learn it is sensitive. The leak is introduced by a change that looked local.
  • Audit coverage does not transfer. The reveal grant, the hash chain, the expiry — those are properties of the product's reveal path. A separate app that reads the row directly produces no audit record at all, so the tenant cannot see that it happened.

Building the operator plane from the same resources inverts that. There is one decrypt chokepoint, so there is one place to gate, one place to log, and one place a reviewer has to read. The operator UI cannot drift from the product UI because it is the product UI with a different actor — which is also why impersonation is useful for support: the reproduction is real.

The cost is honest and worth naming: the operator plane is constrained by what the resource layer exposes. There is no escape hatch to "just run a query" — by design, because that escape hatch is the thing being removed.

Why the analytics pane loses columns instead of masking them

Masking is a render-time answer about a field that exists. The operator pane still reads Fleet.Driver; pii_full_name is right there in the resource definition, the row is right there in Postgres, the ciphertext is right there in the vault. What the operator’s session lacks is a grant, so the type resolves to %Masked{} and the template prints bullets. Change the grant and the same field prints a name. That is a policy outcome, and policy outcomes can be wrong.

The analytics pane is not making that call. Analytics.ShipperCohort is a different resource with a different attribute list, and that list has no pii_* entry on it. There is no field to mask, no ciphertext to decrypt, and no key loaded into the process doing the read. A bug in the masking logic cannot leak a driver’s name here, because the query that produced these rows never selected one.

That is why the reveal button on this pane is refused rather than merely denied: the refusal is decided on the actor, at the top of the function, before a grant table is queried. An aggregate actor and a reveal are mutually exclusive by construction, so there is no ordering of grants, approvals or expiries that can put them together.

Two claims, two strengths. The operator pane says we did not give it to you. The analytics pane says we never had it to give. Only the second one survives a mistake in the code above it — which is the whole reason reporting runs on its own resources instead of on a filtered view of the real ones.

1. The PubSub envelope carries an id, never a body.

Broadcasting a message publishes its id and nothing else. Every subscriber then re-reads that message through its own scope before rendering a single character. A masked operator session cannot receive plaintext by subscribing to the topic, because the topic never carried plaintext to begin with — the read that produced the text on your screen was your read, under your actor.

2. The unfurl resolver composes two kernel gates that did not change.

A pasted ref is resolved by running the host’s own resource through OrgScope and then PiiResolution — the same two gates every other page uses. No code path in the chat feature reads a column directly, unwraps a %Masked{}, or calls Vault.reveal. And this is a framework capability rather than a chat trick: a catalog-driven default card renders any catalogued resource, so a new vertical’s new object unfurls the day it is catalogued, with zero card code written.

Why the same message can render two different truths without a second code path

The naive way to build this is two renderers: the tenant view, and an operator view that redacts. That is two code paths, and the redacting one is the newer, less-reviewed one. It drifts the first time somebody adds a field.

  • There is one renderer. Samen.Web.ObjectRef is a standalone module: it takes a ref and an actor and returns a card. Chat is its first consumer, not its owner — a CRM detail page can unfurl a related object, an audit entry can unfurl its subject, a notification can unfurl its target. The two columns above call the identical function with two different actors.
  • The difference lives in the actor, not the template. Masking is the field’s normal value, so the operator column is not a redacted copy of the tenant column — it is what the resource layer returns when the reader is an operator. There is no branch in the card that says if operator.
  • Cross-plane visibility is the impersonation bridge, reused. The thread is owned by the tenant org; the SaaS participant reaches it carrying the target org_id from a grant, so OrgScope is satisfied for both parties with no new policy and no upward escalation. An operator whose session targets a different org sees the thread as zero rows — cross-plane access is a grant that expires, not a standing door.
  • Identity is masked by default. A tenant participant can opt in per conversation, and a tenant admin can set a disclosure override for the whole org. The default is the safe one, and turning it off is a recorded act.

The property worth stating plainly: adding a field to the driver resource does not require a decision about the chat card. Declare it as PII and it masks in the card on the next render, in every plane, because the card was never the thing deciding.

Erasure

“Delete my data” is usually a DELETE. That is not erasure.

The row goes away and the value does not. It survives in the audit log that recorded the change, the rollup table that summed it last night, the Oban job argument still sitting in the queue, the CDC stream that already shipped it downstream, and the backup taken an hour before the request. Scrubbing a column is a promise about every copy you can currently think of. Samen makes a different promise.

Erasure is key destruction. The subject's PII lives as ciphertext behind per-subject key material. Destroy the key and the ciphertext everywhere becomes permanently unreadable at once — including in the tiers you forgot you had.
Before  ·  one key, six tiers
Plaintext is nowhere at rest. Every tier holds ciphertext that is meaningful only while the subject's key exists.
After  ·  the key is destroyed
Nothing was walked, scrubbed, or rewritten. One destruction, and every tier — including tiers no migration ever touched — is unreadable at the same instant.
The destruction oracle

The attestation runs as a separate OS process.

mix samen.verify.no_plaintext_pii is one of the 24 verifier tiers. It walks every tier — domain rows, vault, audit events, rollups, Oban args, the KMS store — and attests that the subject is unrecoverable.

The separate-process detail is the whole point. An in-process check can be satisfied by the same memory that produced the data: a cached struct, a warm decrypt, a connection that still holds a key. A fresh OS process sees only committed state, so what it attests is what actually persists.

driftwood — the deepest vertical — regenerates the subject and re-runs the whole shred game-day on every CI run. The proof is not a one-time report filed in a compliance folder; it is a build step that can go red.

Scope, stated plainly. The verifier tier ships for any generated app, but the full regenerate-and-shred game-day is currently exercised end-to-end in driftwood, the deepest vertical. Erasure also cannot reach a system samen never wrote to — a copy exported to a spreadsheet, or a downstream consumer that decrypted and stored plaintext of its own, is outside the boundary and this page will not pretend otherwise.
Why key destruction is checkable and row-scrubbing is not

The difference is not strength of encryption. It is what kind of statement each approach asks you to prove.

  • Row-scrubbing asks you to prove a negative over an unbounded set. “No copy of this value survives anywhere” ranges over every table, every derived rollup, every queued job, every log line, every replica, every backup, and every downstream consumer — including the ones added last week by someone who did not know the value was sensitive. There is no finite list to check, so there is no test that can be written for it. What ships instead is a migration and a hope.
  • Key destruction asks you to prove a positive over a finite set. The claim is: this key material does not exist, and every tier that could hold ciphertext for this subject holds only ciphertext. Both halves are enumerable. The tiers are named — domain rows, vault, audit events, rollups, Oban args, the KMS store — so a verifier can walk them and a sabotage patch can make the walk fail.
  • It fails loudly instead of quietly. If a new tier appears that stores plaintext, the oracle finds plaintext where it expected ciphertext and CI goes red. A scrub-based approach has no equivalent signal: the new tier simply is not in the migration, and nothing notices.
  • Reversal is impossible rather than merely difficult. A scrubbed column can be restored from a backup taken minutes earlier, which is exactly the situation the request was meant to end. Restoring a shredded subject would require the key, and the key is the thing that was destroyed.

The honest limit: this bounds recovery to systems inside samen's write boundary. It says nothing about a plaintext copy that left through a legitimate reveal grant — which is why grants are second-party approved, time-boxed, and logged where the tenant can read them.

The generator

One command, and a whole new vertical is already running.

The proof that a substrate is real is generative. mix samen.gen.app does not hand you a folder of TODOs to fill in. It emits a product — web UI, JSON:API, seeds, observability, tests, and its own verifier gate — and that app passes its 19-step gate on the first run with zero hand-edits. Not a scaffold you then fix. A thing you can boot.

Generate it, then make it prove itself

You give it three things: a module name, a table prefix, and a permanent abbreviation. The abbrev is permanent the way a stock ticker is permanent — every table and column the app ever creates is projected through it, so storage stays self-qualifying from the first migration.

Then you do the only interesting thing: you run the generated app’s own gate. Nothing is edited in between. If the substrate had drifted from what it generates, this is where it would show.

Idiom 05 · the malleability ladder

Customers customize. The guarantees should not bend.

Every B2B product eventually gets asked for a field, an object, a workflow that was not in the plan. Samen answers that on a ladder with four rungs, and it is explicit that the higher you climb, the less the platform can promise on your behalf.

Tier-0 and Tier-1 keep the full guarantee: custom jsonb fields are validated at write against rich declared types — Money, Percent, Score, Duration, Priority, URL, Email, Phone, Address. The vault write path re-runs each type’s cast_input, so a value is validated and normalized before it is tokenized. Tier-2 hands tenants their own objects. Tier-3 is code, composed by a builder — and code is reviewed, not guaranteed.

The rungs are labelled with what the platform still owes you at that height. Nothing on the ladder can route a PII value around the vault chokepoint.

What the 19 steps check, and why a generated app running its own gate is a harder claim

A template that compiles proves one thing: the template compiles. The generated app’s gate is a different kind of evidence, because it is the same class of verification the substrate runs on itself. The steps fall into five groups:

  • It builds clean. Compile with warnings as errors, formatter check, static analysis, dependency and license audit — a generated app is held to the same lint bar as the kernel.
  • It is internally consistent. Every table and column the app created must appear in the machine catalog (tam_table / fld_field), written inside the migration transaction. A reference to an uncatalogued column does not compile.
  • Its storage self-qualifies. The abbrev projection is verified end to end — DB, CDC, logs and catalog must agree on the same physical names.
  • Its PII posture holds. mix samen.verify.no_plaintext_pii runs as a separate OS process and attests that no plaintext PII sits at rest anywhere it should not — domain rows, vault, audit events, rollups, Oban args, the KMS store.
  • It actually runs. Migrations apply, seeds load, the server boots, and the routes answer over HTTP. Then the sabotage harness is pointed at the generated gate to confirm the generated tests can fail.

That last step is the one that matters. A gate nobody has tried to break is a decoration. The whole repo carries 301 committed sabotage patches on the principle that a test which cannot fail is treated as a bug — and the generated app inherits that treatment rather than an exemption from it.

The vendor seam

Every SaaS bills and mails. Most frameworks marry a vendor to do it.

Payments and email are the two things a B2B product cannot avoid, and they are exactly where a framework quietly hard-codes a provider — a webhook signature here, a customer id there — until leaving costs a quarter. In Samen the kernel names zero Stripe strings. Adapters live in sibling packages: samen_stripe, samen_postmark, samen_ses, samen_resend.

Delete all four adapter packages. The kernel still passes.

That sentence is the section. It is not a design principle written on a wiki, it is a thing that is run: remove samen_stripe, samen_postmark, samen_ses and samen_resend from the tree, and samen_core plus samen_web still go green.

A vendor boundary you can only argue about is not a boundary. A vendor boundary you can falsify in one command is. If a Stripe string ever leaks into the kernel, that check is what turns red.

zero vendor strings in kernel 4 detachable adapter packages 1 ESP behaviour

All four are detachable; one is drawn lifted to make the point. The behaviour stays, the kernel stays green, the vendor is the only thing that leaves.

Email · one behaviour, three vendors

Three genuinely different auth models, behind one seam.

A seam is only proven by vendors that disagree with each other. These three disagree at the most awkward layer there is — how they authenticate an inbound webhook — and each satisfies the same shared, non-vacuous conformance harness.

ESP 01

samen_postmark

Basic-Auth. The simplest of the three, and the one that would let a lazy interface hide its assumptions.

ESP 02

ESP 03

One place a message can leave

There is a single send chokepoint. Nothing dispatches around it, which is what makes the next line enforceable rather than aspirational.

Rendering

PII-safe by construction

Template rendering resolves through the vault plane, and the no-leak gate is fail-closed and non-skippable — a template that would put plaintext PII on the wire does not get to send.

Billing · the vendor you most want to be able to leave

A subscription lifecycle you can reason about — and no PAN column that can compile.

Card data is not stored, and not merely by policy: payment methods are hosted-only, so there is no column for a primary account number to land in. The rest is the unglamorous, correctness-shaped part of billing.

hosted checkout subscription lifecycle sync fetch-on-event idempotent out-of-order safe invoice mirroring tax mirroring hosted-only payment methods dunning metered usage signature fail-closed webhook ingress DLQ

Webhooks are treated as untrusted hints rather than facts: a signature that does not verify is rejected closed, a verified event triggers a fetch of current state from the provider, applying that state is idempotent, and events arriving out of order do not corrupt the subscription. Anything that still cannot be applied lands in a dead-letter queue where a human can see it, instead of disappearing.

Honest scope: this all runs on the keyless lane. Dispatch is proven against hermetic fakes and injected-transport cassettes. No host wires a live provider. Every generated app boots with billing and ESP unconfigured and says so plainly, with a :not_configured empty state rather than a silent failure or a fake success. The live lanes — real Stripe keys, real Postmark or SES or Resend credentials — are documented, but they are not in CI, and nothing on this page should be read as a claim that they are.
What makes a conformance harness “non-vacuous”, and how we know ours is

A conformance harness is a single shared test suite that any vendor adapter must satisfy to be considered an implementation of the behaviour. It is what turns “we have an interface” into “we have a seam”: a new ESP is not integrated by editing the kernel, it is integrated by passing the suite.

The failure mode is a harness that every adapter passes because it asserts almost nothing — an interface-shaped test that would go green against an empty module. That harness proves nothing, and it proves nothing quietly, which is worse.

  • It exercises the awkward parts. Signature verification, rejection of a bad signature, replay handling, delivery and bounce events, and the mapping back onto the kernel’s own vocabulary — not just “send returned :ok”.
  • Three disagreeing vendors keep it honest. Basic-Auth, SNS-RSA and Svix-HMAC cannot share an accidental assumption. If the harness had quietly encoded one vendor’s shape, the other two would not pass it.
  • A committed sabotage proves the harness can fail. This is the part that closes the loop. Among the 301 sabotage patches in the repo are ones aimed at the ESP path: apply the patch, and the named conformance tests must fail — not “something broke” — then revert and verify a byte-exact restore. A test that cannot fail is treated as a bug.

So the seam claim has two halves, and both are executable: delete the adapters and the kernel still passes; break the adapters and the harness still notices.

Erasure

The transcript is inside the envelope

An agent conversation about a subject is subject data. It lives inside the erasure envelope, so when that subject's key material is destroyed the transcript goes with them — the same crypto-shred, not a separate cleanup job someone has to remember.

Why "runs as the approver, not the requester" is the load-bearing clause

Approval workflows usually get this backwards. The agent asks, a human clicks yes, and the write then executes under the agent's identity — because that is the process already holding a connection. That design launders the agent's permissions through a human click: the human approved one write, but the credential that performed it can perform every other write too, and the audit trail records a service account.

  • Authority is bound at approval, not before it. There is no standing agent credential to escalate, steal, or forget to rotate.
  • The blast radius is the approver's own permissions. An agent cannot propose its way past what the human approving it could have done by hand.
  • The write is attributable to a person. The audit record names the approver, and kind: "ai_agent_write" keeps the origin distinguishable rather than flattening it into ordinary traffic.

The sabotage loop

For each of the 301 committed patches, the harness runs the same five steps. The step that matters is the third: the named tests must fail. Not “something broke” — the specific test, identified by name, that is supposed to be guarding that behaviour.

That specificity is the whole difference between this and mutation testing that counts breakage. A patch that removes the decrypt chokepoint must break the chokepoint test. If it breaks something else instead, the harness fails the run: the guarantee is not where the repo claims it is.

Five stages, run once per patch. Stage 03 is the one that makes the other 300 results mean anything: the harness names the test it expects to break, and a run in which some other test breaks instead is a failed run.

Why a byte-exact restore is part of the loop, not a courtesy

A sabotage harness edits the working tree on purpose. If a revert leaves residue — a stray line, a reordered file, a changed timestamp baked into a fixture — every result after that patch is run against a tree nobody described. Failures start looking like flakes, and the harness quietly becomes a random number generator that reports green.

  • The hash is taken before the patch, not after. Stage 01 records a SHA-256 of each touched file, so the restore is checked against the pre-patch truth rather than against whatever the revert produced.
  • Restore is verified, not assumed. git checkout succeeding is not evidence; a matching digest is. A mismatch fails the run rather than continuing on.
  • It keeps the 301 independent. Because each patch starts from a tree proven identical to the last one, the results compose. Without it they would only be a sequence.

Scope 02

Support can see PII.

The claim was never “never.” It is: reveal is grant-gated, approved by a second and distinct party, time-boxed with an auto-revoke job, and readable by the tenant in a hash-chained log they do not need permission to open. The stronger-sounding version — support that never sees plaintext at all — was retired because it was false by construction, and the retraction is in the repo rather than in a footnote.

Scope 03

pawchart’s mount leverage is a mount number, not a total.

Its four scope-mount files are roughly 188 authored lines that mount framework surfaces as-is. That number says something real about the substrate and nothing at all about the app: pawchart as a whole is a hand-built veterinary product of roughly 3,900 authored lines. An earlier version of this material quoted the mount total as if it were the app’s size. That was an overclaim, and it was corrected rather than reworded.

Scope 04

The AI plane is designed and gated, not shipped.

ADR-047’s agent loop — the agent proposes, a human approves, the write executes carrying the approver’s authority — and ADR-048’s compaction contract are both ratified decisions. The implementing batches are filed as work items, not merged as code. Read them as a design you can argue with, not a feature you can call.

Scope 05

Verticals are proof, not product.

driftwood (freight), pawchart (veterinary) and demo (an API-only dogfood host) exist so the substrate has to survive three unrelated domains instead of one friendly one. They are not being sold, are not seeking users, and have no roadmap of their own. If a vertical is doing something clever, that is a bug in the kernel.

Scope 06

Suite counts are directional.

samen_core 2606, samen_web 1711, demo 465, driftwood 123, pawchart 49 — accurate when written and stale by the next phase, because they grow every phase. Rather than ask you to trust a printed number, the page hands you the command: mix test per package, and ls scripts/sabotages/*.patch | wc -l for the sabotage count. Run them against the tree and the tree wins.

How this list stays true

An overclaim gets retracted in the repo, not softened on the page.

This section is maintained the same way the code is. When a reviewer finds a claim that outruns its evidence, the fix is a commit — the claim comes out of the docs, the correction goes into the tree, and the retraction stays visible. Two of the six items above exist only because that happened. A boundary you can read is worth more than a promise you cannot check.

What the keyless lane can prove, and the exact thing it cannot

The distinction worth holding onto is between protocol conformance and vendor reality.

  • Proven on the keyless lane. One ESP behaviour with three vendor implementations — Postmark Basic-Auth, SES SNS-RSA, Resend Svix-HMAC — driven against a shared conformance harness that is non-vacuous: signature verification, replay handling and failure mapping all have to actually happen, and a sabotage patch exists to prove each assertion can fail. Transports are injected, so the code under test is the code that would ship.
  • Not proven, and not claimed. That a live Stripe account, a live Postmark domain or a live SES identity behaves the way the cassette says on the day you wire it. Vendor behaviour drifts; a recorded interaction does not.
  • Why it is built this way. The kernel names zero Stripe strings — you can delete all four adapter packages and samen_core plus samen_web still pass. Keeping live keys out of CI is what keeps that property honest instead of aspirational.

So the correct summary is narrow and checkable: the seams are proven, the wires are yours.

Two ways in

Run it in ten minutes, or read it for an afternoon.

There are two honest reasons to open this repository. One is to generate a working product and watch it pass its own gate. The other is to take the ideas and use them somewhere else entirely. Both are supported on purpose.

Path A · Use it

Generate an app and make it prove itself.

You need Elixir 1.20 on OTP 29, and a local PostgreSQL that trusts $USER on localhost. Nothing else — no Docker, no API keys, no accounts.

# prerequisites: Elixir 1.20 / OTP 29
# local PostgreSQL trusting $USER on localhost

$ cd samen_core
$ mix samen.gen.app --module Harbor \
      --prefix hb --abbrev hrb

$ cd ../harbor
$ MIX_ENV=test bash ci.sh
...
19/19 verifier steps passed # zero hand-edits

The point of that last line is the word first: the generated app is expected to clear all 19 steps of its own gate on the first run, with zero hand-edits. If it needs a fix from you to go green, the generator is broken — not your setup.

On authorship

Every commit in this repository was written by Claude under human direction and marked Co-Authored-By: Claude. A human operator set the direction, reviewed the work, and gated it adversarially — the sabotage harness, the verifier tiers and the ADR record exist largely because an AI-authored codebase has to be checkable by someone who did not type it.
