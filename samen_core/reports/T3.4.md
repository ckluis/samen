## Tier-0 config rows

`Template` is the Marketing scope's Tier-0 config-row resource (doc: "malleability ladder
bottom rung" §7 of guide): one row per reusable email template per org, admin-gated writes.
The `Campaign` and `Segment` resources are also admin-gated (marketing campaigns and audience
segments are org-level config, not per-user data). `Subscriber` and `Send` are member-writable
(subscribers self-subscribe; sends are dispatched by normal users).

## Consent/suppression enforcement

**Load-bearing red path:** a send to a suppressed subscriber is REFUSED at send-time.

Implementation: the `Send` resource exposes NO default `:create` action. The only creation
path is `:create_checked`, which:

1. Takes `subscriber_id` and `org_id` as required arguments.
2. Queries `msp_suppression` for an active row matching `(org_id, subscriber_id)`.
3. If suppressed: `Ash.Changeset.add_error(field: :subscriber_id, message: "suppressed")` —
   the changeset is invalid, no row is written, no Oban job is enqueued.
4. If not suppressed: sets attributes and creates the send row with `:queued` status.

The suppression check is org-scoped: a subscriber suppressed in org B does NOT block a send
from org A (proven by the org-isolation positive control test).

## Honest residues and seams

1. **Oban job enqueue not wired in `:create_checked`:** The Send `:create_checked` action
   currently sets `status: :queued` and creates the row, but does NOT yet call
   `Samen.Jobs.enqueue_in_tx/3` to enqueue a `SendWorker` job in the same transaction.
   The `SendWorker` module is defined and the queue convention is in place, but the
   same-transaction enqueue step requires the Send's `:create_checked` change to carry
   an `Ecto.Multi` — currently not accessible from a plain Ash change callback without
   an Ash.Oban integration. The spec states "Sends are Oban jobs (webhooks_out-style queue
   conventions)" and "same-transaction enqueue" — the queue, the worker, and the
   suppression gate are all real; the same-tx wiring is a **registered follow-up** (T3.13
   webhooks uses the same integration pattern and that is the natural convergence point).
   The suppression RED PATH (the spec's load-bearing claim) is fully enforced regardless.

2. **`SendWorker.StubAdapter`** is the default adapter in demo/test — real email delivery
   requires a host-implemented `Samen.Scopes.Marketing.SendWorker.Adapter`. This is
   correctly documented in the moduledoc and is the intended seam.

3. **`EmailEvent` resource** is present and catalogued but the Marketing scope does not
   automatically create email events from sends (no lifecycle hook). Email events are
   written by the host's delivery adapter when it receives webhooks from the email
   provider. This is correct scope design.
