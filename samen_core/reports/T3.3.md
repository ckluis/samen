## Deviations from the T3.1 template (justified)

**No deviation.** The scope follows the template exactly:
- Blueprint macro shape identical to Identity and CRM (8 resources vs 6 and 6; same expansion pattern).
- PII routing for scalar fields uses the `pii_` column prefix per scope-authoring guide §5
  ("scalar `pii_attribute`s carry the `pii_` prefix").
- Tier-0 config rows: `Plan` and `Price` follow the same admin-gate pattern as `Identity.Role` and
  `CRM.Pipeline`.
- `Entitlement.entitled_direct?/4` is an addition beyond the strict template — justified: the spec
  explicitly requires "Entitlement check helper (is this org entitled to X)?" with no template
  precedent in prior scopes. It follows the non-PII, admin-query pattern established for Tier-0 reads.
- `SyncAdapter` behaviour + Stub is a Billing-specific addition — justified: the spec requires
  "a sync-adapter behaviour stub". It lives entirely in `samen_core/lib/samen/scopes/billing/` and
  does not touch the resource DSL or verifiers.

## ADR-004 compliance

The Billing scope follows ADR-004 exactly:
- Resources are library-authored blueprint macros; host materializes them via `use Samen.Scopes.Billing`.
- Each resource compiled with host's `otp_app: :demo`, `repo: Demo.Repo`, `domain: Demo.BillingScope`.
- Columns catalogued in the host's `tam_table`/`fld_field` by the migration's `catalog_sync`.
- All five verifiers pass unchanged (`catalog_parity`, `prefixes`, `pii_reads`, `pii_classify`,
  `no_plaintext_pii`).
- PII routes into the host's one Postgres vault (customer `billing_name`/`billing_email` tokens
  in `pii_bcu_billing_name` / `pii_bcu_billing_email` columns).

## PII map (🔒 fields)

| Resource | Field | Vault | Column | Type |
|---|---|---|---|---|
| Customer | `billing_name` | `:pii_name` | `pii_bcu_billing_name` | scalar `:string` |
| Customer | `billing_email` | `:pii_email` | `pii_bcu_billing_email` | scalar `:string` |

All other resources carry only opaque IDs and bounded data — no subject PII. Specifically:
- `Subscription`, `Invoice`, `Payment`, `Usage`, `Entitlement`: FK references to Customer are opaque
  UUIDs, not names or emails.
- `Payment.last4`: last 4 digits of a card number. Non-PII metadata (safe to display; never the full
  PAN, which lives in Stripe's vault). Classified as `non_pii!` by structural decision: it is an
  opaque security indicator, not a subject identifier by itself.

## Tier-0 config rows

Both `Plan` and `Price` are Tier-0 config resources per the malleability ladder (scope-authoring
guide §7, doc §"A malleability ladder"). Admin-gated writes. One row per plan/price per org.

`Plan.features` is a jsonb map (`%{feature_key => true}`) that declares which features the plan
grants. The `Entitlement` resource materializes the per-subscription entitlement from that map.

Seed data for demo: a Free / Pro / Enterprise plan + price can be seeded by calling `Demo.Repo.Seeds.BillingScope.run/1` (not shipped in this task — the migration seeds are enough for CI).

## Entitlement check helper

`Samen.Scopes.Billing.Entitlement.entitled_direct?/4` queries the physical table directly
(Ecto, no Ash overhead) for hot-path checks. It:
1. Parses the UUID string to binary for Postgres compatibility.
2. Compares `feature` as a string (Postgres stores the atom as text via the bounded constraint).
3. Checks `granted: true` AND (`expires_at IS NULL OR expires_at > now()`).
4. Returns `{:ok, true}` | `{:ok, false}` | `{:error, reason}`.

Three tests cover: entitled (returns true), not entitled (returns false), expired (returns false).

## Sync adapter (no live Stripe calls)

`Samen.Scopes.Billing.SyncAdapter` is a behaviour with four callbacks:
`sync_customer/2`, `sync_subscription/2`, `sync_invoice/2`, `cancel_subscription/2`.

`Samen.Scopes.Billing.SyncAdapter.Stub` is the default no-op implementation. It records calls
in the process dictionary (`Process.get(:billing_sync_stub_calls)`) so tests can assert callbacks
were invoked without live Stripe credentials. The RBAC test confirms all four callbacks return
`{:ok, _}` and the call log is correct.

## Anti-tautology sabotage probe (HARD RULE 2)

**What was probed:** `Samen.Policy.OrgScope.filter/3` — the cross-org FilterCheck that makes
`billing_scope_policy_matrix_test.exs` meaningful.

**Method:**
1. Backed up `lib/samen/policy/org_scope.ex` to `.t33_antitaut_scratch/org_scope.ex.bak`
   (directory created outside `/tmp` per the gate rule).
2. Sabotaged `filter/3` to always return `expr(true)` (all cross-org rows visible).
3. Re-ran `mix test test/billing_scope_policy_matrix_test.exs`.
4. Reverted from backup; removed scratch directory.
5. Confirmed clean compile + all 36 billing tests green.

**Probe result:**

- With sabotage: **9/14 passed, 5 FAILED** (2 properties + 3 unit tests).
  - Both `"an actor scoped to org A never reads another org's customers"` and
    `"...subscriptions"` property tests flipped to failing — a cross-org actor now sees
    org B's rows, breaking the assertion.
  - `"an actor cannot update a foreign org's customer"` flipped to failing — the update
    succeeded (cross-org write allowed with sabotaged filter).
  - Two additional smoke-test assertions failed.
- After revert: **36/36 passed** — confirmed the policy check is a genuine discriminator,
  not a tautology.
