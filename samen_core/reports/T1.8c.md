## What shipped

### `Samen.PiiClassify` — heuristic scanner

The scanner implements the two-axis heuristic from the vision doc §llm backstop paragraph:

**Axis 1: Identifier-shape name** — the logical attribute name contains any of the PII identifier tokens (`ssn`, `dob`, `mrn`, `cdl`, `tax_id`, `email`, `phone`, `mobile`, `passport`, `birthdate`, `license_no`, `address`, `account_no`, `credit_card`, and a wider list). Match is substring-based (`:user_email` and `:email_address` both hit the `email` pattern).

**Axis 2: PII-shaped seed/sample values** — the attribute's `:default` or `:constraints` carry a value matching email-shaped (`/^[a-zA-Z0-9...]+@.../`), SSN-shaped (`/^\d{3}-?\d{2}-?\d{4}$/`), or phone-shaped patterns.

**Flag-on-hit, NOT assume-all-strings-are-PII.** Only `:string` / `:date` attributes are scanned. A `:notes` or `:description` column never flags.

**"New" semantics** — a column is new if it is NOT present in the committed `schema.dict.json` baseline (loaded via `load_baseline/1`). Columns already in the baseline were reviewed when the baseline was committed; they do not re-flag.

### `mix samen.verify.pii_classify` — mix task

- Discovers resources from `:ash_domains` config (or `--domain` CLI args)
- Loads the `schema.dict.json` baseline (or `--baseline` path)
- Loads `Samen.NonPii` registry entries for accepted overrides
- Calls `Samen.PiiClassify.scan_resources/3`
- Exits 0 on pass, 1 (via `:erlang.halt/1`) on any violation
- Exposes `check/3` separated from `run/1` for in-process test assertions

### Override flow

A flagged column is cleared in exactly two ways:

1. **Declare it in `pii do … end`** as `pii_attribute` → vault-routed, off-scanner.
2. **Review-gated `non_pii!` override** via `Samen.NonPii.register/1` with DISTINCT second reviewer (`cleared_by != reviewed_by`). A self-review override is rejected by `Samen.NonPii` (`{:error, :self_review}`) and ignored by the scanner even if artificially injected. Every accepted override is **registered in the catalog** via `Samen.NonPii.catalog_flags/1` (plan D8).

## Acceptance criteria — each clause

### (a) Heuristic name+value scanner

**Name scanner:** `Samen.PiiClassify.pii_name?/1` — substring match against 40+ PII identifier tokens. Tests confirm: `:ssn`, `:dob`, `:mrn`, `:cdl`, `:tax_id`, `:email`, `:phone`, `:user_email`, `:email_address`, `:contact_phone` all hit; `:notes`, `:description`, `:label`, `:status`, `:count` do not.

**Value scanner:** `Samen.PiiClassify.pii_shaped_value?/1` — regex against email/SSN/phone shapes. Tests confirm: `"user@example.com"` → `:email`; `"123-45-6789"` → `:ssn`; `"+1-800-555-1234"` → `:phone`; `"active"` → `{false, nil}`.

### (b) Flag-on-hit closes the opt-in gap

**RED PATH: `attribute :ssn, :string` fails.** `PersonRecord` has plain `:ssn, :string` with no `pii do` block → scanner returns violations naming the column. Test: "RED PATH: attribute :ssn, :string on plain resource fails build" asserts `violations != []` and `violations =~ "ssn"` and `violations =~ "identifier-shape"`.

**RED PATH: `attribute :dob, :date` fails.** Same resource, `:dob, :date` column → flagged. Test: "RED PATH: attribute :dob, :date on plain resource fails build".

**RED PATH: email-shaped value fails.** Tested via `pii_shaped_value?("user@example.com")` → `{true, :email}`.

### (c) Vault-routed columns do NOT flag

`pat_patient` has `:dob` and `:mrn` in a `pii do` block. Tests confirm neither flags under `scan_resource/3`.

### (d) Pre-existing columns in baseline do NOT re-flag

Test: "a column in the baseline is not flagged" — builds a `MapSet` containing `{table, pcl_ssn}` and confirms the column is excluded from violations. Test: "column in baseline is skipped even if name-shape matches" — full baseline of all `PersonRecord` columns → zero violations.

### (e) `non_pii!` without distinct second reviewer fails

**RED PATH: self-review rejected.** `NonPii.register(%{cleared_by: "alice", reviewed_by: "alice", ...})` → `{:error, :self_review}`. Test: "RED PATH: non_pii! with cleared_by == reviewed_by is rejected".

**RED PATH: self-review entry does NOT clear the column.** An artificially injected `%Samen.NonPii.Entry{}` with same `cleared_by`/`reviewed_by` does not prevent the column from flagging (the scanner's `non_pii_cleared_set` filters out same-reviewer entries). Test: "RED PATH: a column cleared by self-review still appears in violations".

### (f) Properly reviewed override passes AND lands a catalog row

**GREEN PATH.** `NonPii.register(%{cleared_by: "alice", reviewed_by: "bob", ...})` → `{:ok, entry}`. After registration, `scan_resource` with the real `entries(repo: TestRepo)` produces no violation for the cleared column. Test: "GREEN PATH: properly reviewed non_pii! override clears column from violations".

**Catalog registration (plan D8).** `NonPii.catalog_flags/1` returns a map containing `{table, column} => %{cleared_by, reviewed_by, reason}`. Test: "GREEN PATH: non_pii! override is registered in the catalog (plan D8)".

### (g) Exit codes

**Exit 0:** `mix samen.verify.pii_classify --domain SamenCore.Support.PropDomain` → exit 0, output contains "OK". Test: subprocess.

**Exit 1:** `mix samen.verify.pii_classify --domain SamenCore.Support.PiiClassifyDomain` → exit 1, output contains "likely-PII" and "ssn". Test: subprocess.
