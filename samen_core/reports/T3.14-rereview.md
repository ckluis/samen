## Residues / bounded findings (honest, NOT mandatory — all documented or lower-risk)

1. **CMS Block cross-org FK residue (live-confirmed).** F3.2 did not name CMS, so
   `SameOrgFk` is NOT wired on CMS `Block` (belongs_to :page, nullable) or `SeoMeta`
   (belongs_to :page). My live probe: an org-A actor CAN create a Block referencing an
   org-B page (allowed). Blast radius is a dangling cross-tenant FK only — no PII read
   (OrgScope read-filter still hides the foreign page) and no suppression-style bypass
   (unlike Marketing). Lower severity than the fixed Marketing case, but it is the same
   *class* F3.2 named, and the guide checklist now says "every resource with a belongs_to
   FK" — so CMS Block/SeoMeta are an inconsistency with the stated template. Recommend
   wiring `SameOrgFk` on CMS Block/SeoMeta in a follow-up (mechanical, per the template).

2. **Support/Billing SameOrgFk lack a dedicated red-path test.** The wiring exists and
   works at runtime (my probes proved it), but only CRM + Marketing have explicit
   cross-org-FK red-path tests. Matches what the fix report claimed (it only claimed
   red paths for Marketing + CRM), so this is a coverage gap, not a false claim — but a
   regression on the Support/Billing wiring would go uncaught by the suite. Recommend a
   one-test-each addition mirroring the CRM red path.

3. **`SameOrgFk` `:target_has_no_org_id` doc/behavior mismatch (latent, not exploitable).**
   The moduledoc (lines 141–143) says an org-less target is "treated as a pass," but the
   code returns `{:error, :target_has_no_org_id}`, which flows to the `{:error, reason}`
   branch and REFUSES the write. Not reachable in the current wiring (no wired FK targets
   an org-less anchor), so it cannot misfire today — but if the omit-`relationships`
   default (validate every belongs_to) is ever used on a resource with an org-less FK
   target, legitimate writes would be refused. Recommend making the code match the doc
   (treat `:target_has_no_org_id` as a pass) or the doc match the code.
