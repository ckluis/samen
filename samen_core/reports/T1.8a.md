## What was built

### `mix samen.verify.catalog_parity`

Three directions checked:

1. **Storage → catalog** (no uncatalogued column): every physical column on a
   Samen-managed table has a matching `fld_field` row. Violations are annotated
   with the owning resource module (Gate-0 fix F4 diagnostic quality).

2. **Catalog → storage** (no orphan catalog row): every `fld_field` row has a
   physical column in the DB.

3. **Resource → tam_table** (Gate-0 fix #5 — ghost table detection): every
   `Ash.Resource.Info`-visible resource with an AshPostgres data layer must appear
   in `tam_table`. A whole uncatalogued table passes the first two checks silently;
   this third direction catches it by name.

Additional features:
- Allow-list for intentional shadow columns (Gate-0 fix F2): configure via
  `config :my_app, :catalog_parity_allow_list, [{"table", "col"}]`.
- Repo discovery from `:ecto_repos` with `--repo MyApp.Repo` override.
- Exits via `:erlang.halt(1)` (fail-closed; no cleanup hook can swallow the exit code).

### `mix samen.verify.prefixes`

Two layers checked:

1. **fld_field row prefix**: every row in `fld_field` for a Samen-managed table
   starts with the resource's registered abbrev + `_` (or `pii_<abbrev>_` for
   scalar PII attributes — the doc's "PII routing note").

2. **Physical column prefix**: every column in `information_schema` for a
   Samen-managed table carries the same valid prefix. This catches columns added by
   raw DDL that bypassed `catalog_sync` — the S0.2 caveat F1 / Gate-0 fix task #2
   backstop.

The abbrev is looked up from `tam_table.tam_resource` → `Samen.Info.abbrev/1` so
the check keys on the **registered** abbrev, not a pattern guess.

PII scalar columns (`pii_<abbrev>_*`) are accepted alongside normal `<abbrev>_*`
columns — this matches the `Samen.Transformers.MaterializePii` convention where
scalar `pii_attribute` fields get the `pii_<abbrev>_` prefix set explicitly as
their `:source`.

## Red-path tests

Four red-path scenarios, each proven via both unit (check/1) and exit-code
(System.cmd) layers:

| Scenario | Fixture | Verifier | Exit code |
|---|---|---|---|
| Uncatalogued column | `ALTER TABLE ... ADD COLUMN` (no catalog_sync) | catalog_parity | 1 |
| Orphan fld_field row | `INSERT INTO fld_field` for non-existent column | catalog_parity | 1 |
| Ghost table (Gate-0 fix #5) | `DELETE FROM tam_table WHERE ...` (removes resource's catalog entry) | catalog_parity | 1 |
| Unprefixed column | Raw column + bad fld_field row, both without abbrev prefix | prefixes | 1 |

Fixtures inject violations via direct Postgrex connections (not the SQL sandbox)
so the injected state is immediately visible to child mix processes spawned for
exit-code assertions.

## Design decisions

### PII scalar column prefix exception

The `prefixes` verifier accepts both `<abbrev>_` and `pii_<abbrev>_` as valid
prefixes. This matches the `MaterializePii` transformer's `source_for/2` logic:
scalar `pii_attribute` fields (`:date`, `:string` etc.) get `pii_<abbrev>_` in
their physical column name; composite PII fields (FullName/Emails/Phones) get
the plain `<abbrev>_` prefix like all other attributes. Both are equally
vault-routed; the column name convention is the doc's "PII routing note."

### Allow-list for shadow columns

The `pat_care_note` and `pat_subject_id` columns (added by the T1.7 erasure
migration) are raw DDL columns on `pat_patient` that are not Ash attributes. They
therefore don't appear in `Samen.Catalog.fields(Patient)` and `catalog_sync` never
emitted `fld_field` rows for them. They are added to the test `catalog_parity_allow_list`
to keep the verifier green in the kernel's own test suite; a production app that adds
similar operational columns should do the same.

### Ghost table detection (Gate-0 fix #5)

The ghost table check discovers resources from `:ash_domains` config (same source
as `mix ash.codegen`). A resource whose migration ran but whose `catalog_sync` was
never called will appear in `Ash.Domain.Info.resources` but not in `tam_table` —
the verifier catches it by name and reports both the table name and the resource
module. The check also detects resources whose physical table doesn't exist at all
(missed migration + missed catalog sync).
