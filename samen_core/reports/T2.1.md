## Scope delivered

### (a) Same-transaction enqueue helper

`Samen.Jobs.enqueue_in_tx/3` generalises the T1.6 pattern (reveal-grant auto-revoke) into a canonical helper. It delegates to `Oban.insert/3` (which uses an `Ecto.Multi` step), ensuring the job row is inserted inside the caller's transaction. A rollback anywhere in the multi removes the job row.

**Crash test (red-path):** `test/jobs_enqueue_in_tx_test.exs`:
- Happy path: commit leaves exactly one job row.
- Crash path: a multi step fails AFTER `enqueue_in_tx` — no `oban_jobs` row survives.
- Alternative call form: accepts a pre-built `Ecto.Changeset`.

**Anti-tautology probe (probe 1, crash test):**
- Sabotaged `enqueue_in_tx` to insert the job OUTSIDE the multi (a separate `repo.insert!` call) in a scratch copy at `/Users/clank/Desktop/projects/samen/_probes/t2_1_anti_tautology/` (cleaned up after).
- Result: crash test **FAILED** as expected (`job_count_for(...)` was `before_count + 1` instead of `before_count` — the out-of-band insert survived the rollback).
- Reverted. The crash test is discriminating, not vacuously true.

### (c) Cron wiring + DLQ/retry policy convention

`Samen.Jobs.default_crontab/0` returns `[{"*/10 * * * *", Samen.Jobs.RollupRefreshWorker}]` — the rollup heartbeat scaffold (T2.3 will replace with real AshOban triggers).

`Samen.Jobs.RollupRefreshWorker` (`lib/samen/jobs/rollup_refresh_worker.ex`) is a scaffold Oban.Worker on the `:rollups` queue (`max_attempts: 5`) that logs a heartbeat and returns `:ok`.

The `demo/config/config.exs` Oban config is updated to wire `Oban.Plugins.Cron` and `Oban.Plugins.Pruner` (7-day max_age) in non-test envs. `demo/config/test.exs` overrides with `testing: :manual, plugins: false` so tests see job rows but no auto-execution or plugin timers.

DLQ / retry convention is documented in `Samen.Jobs` `@moduledoc`: `max_attempts: 20` (≈ 4–6 hours of capped exponential backoff), `:discarded` state is the DLQ, `{:discard, reason}` for permanent failures.

### (d) Starvation isolation test

`test/jobs_starvation_isolation_test.exs`:

**Setup:** a real Oban instance (not `:manual`) with two queues: `slow_queue: 1` and `fast_queue: 2`. Uses a dedicated named Oban supervisor (`StarvationTestOban`) so it does not interfere with the test-mode global Oban.

**Starvation proof:** enqueues 3 slow jobs on `slow_queue` (fills the limit=1 + 2 queued), waits for them to start, then enqueues one fast job on `fast_queue`. Fast job must complete within 3 s. The slow jobs are still running. PASSED: `fast_queue`'s jobs are unaffected by `slow_queue` saturation.

**Concurrency limit red-path:** enqueues 4 slow jobs; samples `concurrent` count from an ETS counter while the jobs run; asserts `concurrent <= 1`. PASSED.

**Anti-tautology probe (probe 2, concurrency limit):**

- Result: concurrency limit test **FAILED** as expected — counter showed 4 concurrent executions when the assertion requires ≤ 1.
- Reverted. The concurrency assertion is discriminating.

## Simulation seam (documented per plan)

The starvation isolation test is **single-node** (one BEAM, two queues on one Oban supervisor). A multi-node Fly/Kubernetes cluster with `n` nodes has effective concurrency `n × limit` per queue (open-source Oban limits are per-node). This means:

- **`:erasure` queue (limit 1) is not truly single-concurrent on multi-node clusters.** An advisory lock or Oban Pro global limits is needed for the hard single-concurrency guarantee across nodes.

**Operator TODO:** Before deploying on multi-node Fly (Phase 4+), either adopt Oban Pro's global concurrency limits for the `:erasure` and `:maintenance` queues, or add a Postgres advisory lock inside `Samen.Erasure.shred/2` to serialise concurrent shred attempts. This is not a Phase-2 scope item; the single-node proof is sufficient for `samen_core` as a library.
