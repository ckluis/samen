## Scope delivered (plan T3.9; vision doc §core "custom OBJECTS in `tnt_record` +
`tnt_object`/`tnt_field`", malleability ladder rung 3; Twenty metadata model = SPEC only)

### `tnt_object` — the tenant-tier object catalog
`Samen.CustomObjects.ObjectRow` — a plain Ecto DDL table (same bootstrap reasoning
as `tam_table`/`tnt_field`), org-scoped, UNIQUE `(org, object_key)`.
`Samen.CustomObjects.define_object/2` upserts one; `list_objects/2` IS the
tenant-tier object catalog (the `tnt`-namespaced parallel to the system
`tam_table`).

### `tnt_field` — SHARED with T3.8
A custom object's fields ARE Tier-1 `tnt_field` rows, keyed on the object's
synthetic table name `Samen.CustomObjects.object_table/1` = `"tnt$obj$<key>"`
(a sentinel prefix disjoint from every physical `<abbrev>_<name>` table, so the
Tier-1 and Tier-2 catalog checks never collide). `define_object_field/2` is a thin
wrapper over `Samen.CustomFields.define_field/2` — the type + constraint + PII-shape
machinery is reused verbatim, not re-implemented.

### `tnt_record` — org-scoped rows, validated jsonb
`Samen.CustomObjects.Record` — the one Tier-2 piece that is a real **Ash resource**
(`use Samen.Resource`, abbrev `tnr`), so it inherits org-scope policy
(`Samen.Policy.OrgScope`) and abbrev storage (`tnr_*`) for free. Columns:
`tnr_object_key`, `tnr_attributes` (validated jsonb bag), `tnr_refs` (opaque
OUT-references). ONE physical `tnt_record` table keyed by object — NOT a table per
custom object (the vision doc rejects Twenty's runtime-DDL model; the system schema
stays compile-time provable, no DDL at runtime).

### CRUD + org-scope
`create_record/4` / `list_records/3` go through the ordinary Ash API with a
`%Samen.Scope{}` actor, so org-scope policy applies. Validated-at-write via
`Samen.CustomObjects.RecordChange` (`before_action`, inside the action tx,
consistent with `CustomFields.Change`/`Vault.Change`): object gate (enabled
`tnt_object` required) → attribute bag validated by `CustomFields.validate_bag/4`
(reused Tier-1 engine) → refs validated as opaque IDs.

### Catalogued as tenant-tier objects
`mix samen.verify.tnt_catalog` extended with Check 3 (T3.9): every custom-object
field (`tnt_field` on `tnt$obj$<key>`) and every `tnt_record` must reference a
defined `tnt_object`. Wired as step 11/12 of `demo/ci.sh`.

### THE ONE-WAY BOUNDARY — documented AND enforced (3 layers)
Data may reference OUT of the tenant regime into the system regime (a
`tnt_record.refs` opaque ID pointing at a system row), never the reverse:
1. **compile-time** — `Samen.Verifiers.TntBoundary` (wired into `Samen.Extension`'s
   verifier list): a `use Samen.Resource` **system** resource declaring a
   relationship (`belongs_to`/`has_*`/`many_to_many`) → `Samen.CustomObjects.Record`
   FAILS compile with a `Spark.Error.DslError`. (Red path — probe 3 below.)
2. **whole-app sweep** — `mix samen.verify.tnt_boundary` scans every configured
   domain's resources for a relationship into `tnt_record`, AND asserts no FK
   constraint targets a tenant-regime table (`tnt_record`/`tnt_object`). Wired as
   step 12/12 of `demo/ci.sh`.
3. **value-shape** — `RecordChange` rejects a PII-shaped or free-text `refs` value,
   so an OUT-ref can only be an opaque uuid / bounded token (a ref can't launder
   PII across the boundary).

Structurally there is no FK on `tnt_object`/`tnt_record` and no FK from any system
table into them (asserted by the sweep + a DB FK scan).

**Out of scope (per plan, P6+):** NO workflow builder, NO UI designer.

## Simulation seams / honest notes (R11 minimal-viable)
- **Cross-app repo seam (documented, not faked):** `Samen.CustomObjects.Record`'s
  backing repo is compile-bound in samen_core (`compile_env :tnt_record_repo`), so
  in the demo build the resource resolves to `SamenCore.TestRepo`, not `Demo.Repo`.
  Record-row CRUD through the Ash resource is proven end-to-end in the KERNEL suite
  against Postgres; the DEMO dogfoods the object/field-definition + validation +
  catalog + boundary machinery (all repo-parametric at runtime) against `Demo.Repo`.
  A production multi-tenant deploy would parametrize the record repo per host — an
  explicit R11 minimal-viable seam, named in `tnt_object_scope_test.exs` moduledoc,
  not hidden. This is the honest boundary of "minimal viable".
- **Validation reuses Tier-1** — the PII-shape containment is the same value-shape
  heuristic `Samen.PiiValueShape` documents (a heuristic, not a taint proof). The
  load-bearing seals are structural (no FK either direction, the compile-time
  boundary verifier, fail-closed rejection) + the durable CI catalog backstop.
- **No AWS/Neon needed** — all local Postgres; the vault is untouched (Tier-2
  attributes are contained in the sealed jsonb bag, never vault-routed — same design
  as Tier-1).
