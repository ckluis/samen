### C3 Root-Cause Note

`mix samen.verify.pii_reads` defaulted to `Application.get_env(:samen_core, :ash_domains)` but
the demo configured domains under `:demo`. Fixed by adding
`config :samen_core, :ash_domains, [Demo.Crm]` to `demo/config/config.exs`. Without this, the
verifier built an empty registry and returned exit 0 even with a planted leak. The fix ensures
the registry discovers demo's PII fields.

### C4 Probe Note

`Samen.PiiClassify.pii_name?/1` is a pure function (no DB needed). Directly verified:
`pii_name?(:ssn) == true`, `pii_name?(:display_name) == false`. Full fail-closed evidence is
in the samen_core test suite red-path tests. The demo's clean check (`violations = []`) confirms
no false positives on the demo's registered/reviewed columns.

## Known Caveats

1. **C4 anti-tautology not done at mix-task level.** The `pii_classify` task requires a real Ash
   resource with a PII-named attribute. Creating one requires adding the abbrev to the registry
   (hardcoded to samen_core's priv). A temp resource would need registry manipulation. The
   unit-level proof (`pii_name?(:ssn) == true`) is the pragmatic substitute; the samen_core
   test suite has the authoritative red-path for C4.

2. **Coverage total 68%, not 90%.** The 90% target is not met at the aggregate level. Most core
   functional modules are at 80-94%. The gap is auto-derived `Inspect` protocol stubs and Mix
   task entry points.

3. **C3 verifier requires `:samen_core, :ash_domains` config in consumer apps.** Without it, the
   registry is empty and the verifier is effectively disabled. This is a documentation/convention
   gap — consumer apps MUST set `config :samen_core, :ash_domains, [...]` for C3 to be effective.
   The demo sets this and the gate passes. A future T should enforce this automatically.
