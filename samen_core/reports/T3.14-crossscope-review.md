## Finding F3.1 — MANDATORY-IN-PHASE (MED): de-vaulting a free-text 🔒 field escapes the verifier gate

The scope-authoring guide §5 claims: "The `no_plaintext_pii`, `pii_reads`,
`pii_classify`, and `vault_declared` verifiers all enforce this automatically … A 🔒
field you forget to vault fails them (the red path)." **This is false for 🔒 fields
whose logical name is not in the C4 heuristic token-list** (Support `message.body`,
Primitives `notification.rendered_body`, `webhook.signing_secret`). Proven by sabotage
(probes 1+2 above): removing the `pii do` block for `body`/`signing_secret` leaves the
entire verifier gate green. The Support blueprint moduledoc itself admits "`body` is
NOT in the default heuristic PII-name-token list" yet the same doc claims the field is
"fully enforced by `pii_reads`, `no_plaintext_pii`, and `pii_classify`." The gate does
NOT enforce the *presence* of the declaration — it only enforces the *consequences* of
a declaration that exists. The actual safety net for these fields is the per-scope
vault-routing TEST, not the gate.

Why it is a caveat, not a breach: (a) the fields ARE vaulted today (green), (b) the
vault-routing test does catch removal, (c) this is the same class as Gate-2 F2.2
(report/guide prose oversells a guard). But an auditor or a future scope author who
trusts the guide's "verifiers catch a forgotten 🔒" claim is over-trusting.

**Fix (pick one, both cheap):**
- (a) Add a `vault_declared_parity` check: for every resource whose column name matches
  `^pii_[a-z]{3}_` in the migration/catalog (a vault-routed storage name) OR whose doc
  scope-table entry is 🔒, assert the resource has a matching `pii_attribute`. This makes
  "the DB has a `pii_*` column but the resource no longer routes it" a fail-closed
  violation. (The de-vault probe left `pii_smg_body` in the DB while the resource dropped
  the route — exactly the mismatch this catch would flag.)
- (b) At minimum, downgrade scope-authoring guide §5 and the Support/Primitives blueprint
  moduledocs to state precisely: "the verifier gate enforces vault *consequences*; the
  authoritative red path for a forgotten free-text 🔒 field is the scope's
  `*_vault_routing_test.exs`." Recommend (a)+(b).

## Finding F3.2 — MANDATORY-IN-PHASE (MED): cross-org FK values are writable (foreign-org reach on WRITE)

`Samen.Policy.OrgScope` protects *reads* (foreign-org rows invisible, verified: a
foreign person loads as `nil` through a relationship) and *writes to a foreign row*
(row.org_id ≠ actor.org_id → Forbidden). But **nothing validates that a `belongs_to`
FK points at a same-org row.** Probed live (demo):

- **Marketing `Send.create_checked`**: actor in org A passes `org_id: org_a` (its own
  org, so the write is authorized) with `subscriber_id` = a subscriber owned by org B.
  The suppression check queries `msp_suppression` for `(org_a, subscriber_b)` — finds
  nothing (org A has no suppression for a foreign subscriber) — so **a send row is
  created in org A referencing org B's subscriber** (`status: :queued`), and the
  SendWorker would enqueue delivery to org B's (vaulted) email. Org A never sees the
  plaintext, but org A can trigger a send to another tenant's subscriber and bypass
  org B's suppression list. This is the Marketing scope's load-bearing suppression
  guarantee being circumventable across the tenant boundary.
- **CRM `Activity`**: actor in org A creates an activity in org A with
  `person_id`/`company_id`/`opportunity_id` referencing org B's rows — **succeeds**.
  (Read of the foreign parent is still filtered to `nil`, so no PII leaks; but the
  dangling cross-tenant FK is stored.)
- **Support `Message`**: actor in org A creates a message in org A with
  `conversation_id` referencing org B's conversation/ticket — **succeeds**.

Why it is a caveat, not a breach: no foreign PII is *readable* by the writer (OrgScope
read-filter holds). The blast radius is cross-tenant referential pollution + the
Marketing suppression-bypass send. The doc's isolation model ("foreign-org rows are
invisible") is about reads; cross-org FK writes are unaddressed by the guide and
unguarded by every scope.

**Fix:** add a same-org FK validation (a reusable `Samen.Policy`/change or an Ash
`relate_actor`-style constraint) on `belongs_to` FKs in tenant-plane creates/updates —
at minimum on the Marketing `Send.create_checked` (validate the subscriber's org_id ==
the send's org_id before the suppression query) so the suppression guarantee cannot be
crossed. Broadly, document the cross-org-FK-write residue in the scope-authoring guide
and add a same-org-FK check to the template. A red-path test: org-A send referencing
org-B subscriber must be refused.

  actual is `pii_bcu_...`).
- **Marketing** moduledoc: `msu_pii_email` (WRONG — actual `pii_msu_email`).
- **Support** moduledoc line 69 + inline comments: `smg_pii_body` (WRONG — actual
  `pii_smg_body`); yet the same file's PII-map table (line 12) says `pii_smg_body`
  (RIGHT). Self-contradictory within one file.
- CRM/Primitives/Identity: correct (`pii_` first) or composite (no prefix), consistent.

Storage-name discipline is an idiom the guide calls out explicitly; the doc drift
should be corrected to `pii_<abbrev>_<name>` uniformly.

## Finding F3.4 — IDIOM DRIFT (LOW): CMS diverges from the split-read/split-write policy idiom

- **CMS Block** carries a redundant/overlapping policy: `policy action_type([:read,
  :create, :update, :destroy]) → authorize_if OrgScope` immediately followed by
  `policy action_type([:create, :update, :destroy]) → forbid_unless OrgScope +
  RoleAtLeast :admin`. Because Ash ANDs all matching policies, writes still require
  admin+org (not a hole), but the write action_types in the first policy are redundant
  and every other scope uses a clean read-only-first / write-second split. Align to the
  template.
- **CMS Page/Post** gate the default `:update` (content edit) at `OrgScope` only (any
  member may edit content), while `:publish`/`:archive` require admin. This is a
  reasonable CMS design but is an unstated divergence from the "writes require a role
  floor" pattern the other scopes follow; it should be documented as an intentional
  choice in the guide (Tier-0 vs content-edit distinction) rather than silent drift.
- (Consistent across all six, for the record: mount macro shape, `pii do` reveal via
  `Samen.Reveal.grant_checker().granted?/1`, `OrgScope` FilterCheck, `RoleAtLeast`
  gates, Tier-0 admin-gate, the four standard test files, abbrev registration.)
