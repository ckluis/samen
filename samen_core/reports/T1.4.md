## Scope coverage

### (a) pii_* vault tables + FK tokens in domain rows, wired to T1.3 DSL

The `pii_vault` table uses a single-table design keyed by `(subject_id, vault_name, field_name)` with a `vault_name` discriminator. `Samen.Vault.store_field/5` writes a vault row and returns a `"vt_*"` token. The caller sets the token on the domain row's token column. `Samen.Vault.materialize/2` uses `Samen.Pii.Info.fields/1` (T1.3) to resolve token columns to `%Masked{}` values at read time. The T1.3 DSL declarations are the routing table — the vault runtime consumes them, not column-name heuristics.

### (b) Samen.Kms behaviour + adapters + AwsKmsDynamo skeleton

The `Samen.Kms` behaviour has 6 callbacks: `generate_subject_key/1`, `unwrap/1`, `shred/1`, `attest/1`, `backups_disabled?/0`, `pseudonym/2`. All three adapters are tested against the shared conformance suite (`test/kms_conformance_test.exs`). The `AwsKmsDynamo` skeleton:
- Compiles cleanly
- Passes every conformance test in disabled mode (delegates to `InMemory`)
- Guards network calls with `Application.get_env(:samen_core, :aws_kms_dynamo_enabled, false)`
- Documents the production wiring plan in the module docstring
- Raises a clear diagnostic if called with the flag set to `true` (not implemented yet)

### (c) No plaintext-key cache (ADR-001 §6 seam)

T1.4 ships with NO in-memory unwrapped-DEK cache. Every `unwrap/1` is a live store call. The documented seam is in `Samen.Kms` (the module docstring) with:
- The exact cache requirements if one is added (process-memory only, evicted on shred, denied on outage)
- The mandated red-path test: `assert {:error, :shredded} = adapter.unwrap(subject)` after shred, even within TTL

### (d) attest/1 returning positive tombstones (ADR-001 §5)

Both `InMemory` and `FileBacked` implement the distinction:
- `:active` — subject has a live key
- `:shredded` — positive tombstone with `destroyed_at` + `attestation_id`
- `:absent` — never seen, no tombstone

RED PATH 3 verifies that `:absent` and `:shredded` are distinct states (a silently-dropped row cannot masquerade as a destroyed key), and that `attest/1` after `shred/1` returns `:shredded`, not `:absent`.

## Gate-0 fix task #1 — Phoenix.HTML.Safe

The Gate-0 report (S0.5 audit) identified `Phoenix.HTML.Safe` as the one unmet acceptance clause from the spike. This module is now implemented in `Samen.Masked`:

```elixir
if Code.ensure_loaded?(Phoenix.HTML.Safe) do
  defimpl Phoenix.HTML.Safe, for: Samen.Masked do
    def to_iodata(%Samen.Masked{}), do: Samen.Masked.mask()
  end
end
```

The implementation uses a compile-time optional guard so `samen_core` has no Phoenix dependency; the protocol is implemented when `phoenix_html` is present. This ensures `<%= @person.email %>` in HEEx renders `"••••"` rather than raising `Protocol.UndefinedError`.

## ADR-001 red paths (all 6 mandated, all verified)

### RED PATH 1 — PITR cannot resurrect the key

**Test:** `test/vault_pitr_test.exs` — physical `pg_dump` / `psql` round-trip.  
**Mechanism:** `Samen.Kms.FileBacked` stores wrapped DEKs in a directory outside Postgres. `pg_dump` captures ciphertext in the vault table but never the key directory. After `shred/1`, decrypt raises `:shredded`/`:unavailable` even in the restored DB.  
**Strongest form:** pointing the key store at a brand-new empty directory (modeling a DB-only restore with no key store) causes `unwrap/1` to return `:absent`/`:unavailable` — the restored ciphertext is permanently undecryptable.

### RED PATH 2 — Post-shred decrypt raises :shredded

**Test:** `test/vault_test.exs` — "RED PATH 2 — post-shred decrypt denies" (both adapters).  
`{:error, :shredded}` is the only valid response from `reveal/3` after `shred/1`. `{:ok, plaintext}` would fail the assertion.

### RED PATH 3 — Attestation is positive tombstone, not mere absence

**Test:** `test/vault_test.exs` — "RED PATH 3 — attest returns positive tombstone, not :absent".  
Also in `test/kms_conformance_test.exs`: "attest after shred stays :shredded (positive tombstone, not absence) — RED PATH 3".  
The oracle requires a POSITIVE tombstone; `:absent` is FAIL for a post-shred assertion (ADR-001 §5).

### RED PATH 4 — Pseudonym unlinks on shred (RQ5)

**Test:** `test/vault_test.exs` — "RED PATH 4 — pseudonym unlinks on shred (RQ5)".  
Also in `test/kms_conformance_test.exs`: "pseudonym is stable pre-shred and denied post-shred — RED PATH 4 (RQ5)".  
`pseudonym/1` returns `{:error, :shredded}` after `shred/1`. One KMS shred unlinks both vault ciphertext and trace-sink pseudonym.

### RED PATH 5 — Store outage fails closed (RQ4)

**Test:** `test/vault_test.exs` — "RED PATH 5 — store outage fails closed (RQ4)".  
`Samen.Kms.FileBacked.simulate_outage(true)` makes `unwrap/1` return `:unavailable`. No plaintext cache exists by construction. Outage is deny-recoverable: healing the store (outage false) restores decryptability without any key destruction.

### RED PATH 6 — backups_disabled?/0 oracle check-2 gate

**Test:** `test/vault_test.exs` — "RED PATH 6 — backups_disabled?/0 oracle check-2".  
Both dev adapters return `true` (no PITR by construction). The anti-tautology probe asserts that `false` from an adapter would cause the oracle check-2 to exit non-zero.

## Anti-tautology probe

**Target:** RED PATH 2 (post-shred decrypt) — the most critical guarantee.

**Method:** Replaced `shred/1` in `Samen.Kms.InMemory` (scratch copy) with a no-op that returns a fake `:shredded` attestation without destroying the DEK. Then ran `mix test test/vault_test.exs`.

**Result:** 3 tests FAILED:
1. "InMemory: reveal denies with :shredded after shred" — `match (=) failed` (got `{:ok, plaintext}`)
2. "InMemory: attest after shred returns :shredded with destroyed_at" — attestation showed `:active`, not `:shredded`
3. "InMemory: pseudonym unlinks on shred" — pseudonym succeeded after the no-op shred

This confirms the red-path tests are non-vacuous: they fail when the guard is removed.

**Revert:** The original `in_memory.ex` was restored. Final suite: 154 tests passed, exit code 0.

## Known residues and carry-forwards

1. **AwsKmsDynamo is a skeleton.** Network calls are behind `aws_kms_dynamo_enabled: false`. The `backups_disabled?/0` check (oracle check-2 with `DescribeContinuousBackups`) is stubbed as a `raise`. This is explicitly scoped to T1.4; the oracle (T2.9) will wire the real check.

2. **T1.4 seam for TTL cache.** Documented in `Samen.Kms` module docstring. No cache ships. If added, it must be evicted on shred (PubSub broadcast), deny on outage, never persisted, and carry its own red-path test.

3. **Domain resource token columns.** Currently added to `pat_patient`/`stf_staff` fixtures via migration. T1.5 will wire the Ash change that replaces plaintext materialization with transparent token routing, and define the protocol for how resources declare their token column layout.

4. **`Samen.Vault.materialize/2`** depends on the T1.3 `Samen.Pii.Info.fields/1` API and the `<field_name>_token` convention. Token column discovery currently uses the convention `:"#{field_name}_token"`. T1.5 may formalize this as part of the DSL.

5. **`scan_no_plaintext/2`** is an oracle-style scan over all vault rows for a subject. The full destruction oracle (T2.9) will expand this to cover all tiers (replica, rollups, audit, CDC, trace-sink).
