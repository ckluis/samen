## (a) Partitioned table, monthly RANGE, BRIN, catalog rows

### DDL design

`aud_event` is a `PARTITION BY RANGE (aud_occurred_at)` table. The migration:

1. Creates the parent table with columns `aud_id, aud_event_type, aud_subject_id, aud_actor_id, aud_correlation_id, aud_detail, aud_occurred_at`. Primary key is `(aud_id, aud_occurred_at)` — the partition key must be included in any primary key on a partitioned table (Postgres requirement).

2. Creates the first child partition `aud_event_y2026m07` covering July 2026 (the current phase month).

3. Creates a `BRIN` index `aud_event_brin_occurred_at` on the partition key. BRIN is the doc-mandated index type for time columns on huge append-only tables — a few-KB index regardless of table size (normal B-tree indexes grow proportionally to row count).

### Partitioned-table catalog handling

**Key design decision:** only the PARENT partitioned table (`aud_event`) gets catalog rows in `tam_table`/`fld_field`. Child partitions (`aud_event_y2026m07`, etc.) are NOT registered — they are transparent storage shards that inherit the parent's schema. Registering each partition would:
- Duplicate catalog rows (they'd all have the same column set)  
- Require catalog maintenance every time the PartitionManager creates a new partition

`information_schema.columns` with `table_name = 'aud_event'` returns the parent table's column set, not the children's (they inherit it). The `catalog_parity` verifier and `no_plaintext_pii` tiers both query this way and see the correct, single column set.

The catalog rows are written as raw `execute/2` SQL in the migration transaction (not via `catalog_sync` macro) because `Samen.AuditEvent` is a plain `Ecto.Schema`, not an Ash/Spark resource — `catalog_sync` requires `AshPostgres.DataLayer.Info.table/1` and `Ash.Resource.Info.attributes/1`. The raw SQL INSERT shares the same migration `BEGIN...COMMIT` and provides the same atomicity guarantee.

**`schema.dict.json`:** `aud_event` does NOT appear in `schema.dict.json` because that artifact is generated from Ash resource domains (via `mix samen.catalog.dump`). It IS present in the physical `tam_table`/`fld_field` rows that `catalog_parity` checks. This is intentional: `schema.dict.json` is for LLM grounding on domain resources; the physical catalog (`tam_table`) is the enforcement surface.

## (b) Append-only enforcement — belt and braces

### Layer 1: REVOKE (braces — role layer)

```sql
REVOKE UPDATE, DELETE ON aud_event FROM clank
```

The app role (`clank` in dev/CI; configurable via `:aud_event_app_role`) cannot issue UPDATE or DELETE at all. Any attempt fails at the Postgres permission layer before the trigger fires.

### Layer 2: trigger (belt — DDL layer)

```sql
CREATE TRIGGER aud_event_append_only_tg
BEFORE UPDATE OR DELETE ON aud_event
FOR EACH ROW EXECUTE FUNCTION aud_event_enforce_append_only()
```

The trigger function raises:
```
aud_event is append-only: UPDATE and DELETE are not permitted. Event id: ?, type: ?
```

Even if an operator re-grants UPDATE/DELETE to the app role (or runs ad-hoc SQL as a Postgres superuser), the trigger stops the mutation. This is the "belt" that catches what the role revocation misses.

### Red-path tests

Both layers are tested in `test/aud_event_test.exs`:

- `UPDATE via repo.query raises (trigger layer)` — asserts `Postgrex.Error` matching `~r/append-only/i`
- `UPDATE via Ecto schema raises (trigger layer)` — same via `Ecto.Changeset` + `repo.update!`
- `DELETE via repo.query raises (trigger layer)` — asserts `Postgrex.Error` matching `~r/append-only/i`
- `DELETE via Ecto repo.delete raises (trigger layer)` — same via `Ecto.Changeset` + `repo.delete!`

## (c) Partition manager

### `Samen.AuditEvent.PartitionManager` (Oban worker)

- **Queue:** `:maintenance` (concurrency 1, per T2.1 taxonomy)
- **Cron:** `{"0 1 * * *", Samen.AuditEvent.PartitionManager}` (daily at 01:00; configure in host app)
- **Idempotent:** `ensure_partition` uses `CREATE TABLE IF NOT EXISTS ... PARTITION OF`
- **`ensure_upcoming_partitions/3`:** creates N months ahead of the given anchor date

### Erasure-window gate

`detach_partition/3` refuses to detach a partition whose time window is still erasure-relevant, via the `Samen.AuditEvent.ErasureWindowPolicy` behaviour:

```elixir
@callback still_relevant?(partition_info()) :: {:relevant, String.t()} | :not_relevant
```

**Configuration:**
```elixir
config :samen_core, :erasure_window_policy, MyApp.CustomErasureWindowPolicy
config :samen_core, :default_erasure_window_days, 90  # default
```

**`DefaultErasureWindowPolicy`:** keeps any partition whose `to_ts` (upper bound) falls within the last `default_erasure_window_days` days (default: 90). This is a conservative time-based floor. T2.3 replaces this with a real rollup-linkage check once rollups exist (the policy seam is wired for that).

**Red-path test:** `PartitionManager.detach_partition(Repo, july_2026)` returns `{:error, :erasure_window_active, detail}` (July 2026 is within the 90-day window). Tested and confirmed.

**`:force` bypass:** an operator can call `detach_partition(Repo, date, force: true)` to bypass the gate with a logged warning. This is the explicit operator-override path.

**Simulation seam:** no physical Neon/AWS replica exists in this environment. The partition manager targets the primary repo only. T2.5 PITR game-day task is the operator TODO for replica wiring.

## (d) T1.6/T1.7 audit row migration onto aud_event

### Grant lifecycle → aud_event

`Samen.Reveal.Grants.write_audit/2` now emits BOTH:
1. The existing `rvl_reveal_audit` row (unchanged — backward compatible)
2. A new `aud_event` row with `event_type = "grant_lifecycle"`

Fields on the `aud_event` row:
- `event_type` = `"grant_lifecycle"` (bounded enum)
- `subject_id` = the subject's opaque UUID (NOT plaintext PII)
- `actor_id` = the operator actor id (NOT plaintext name)
- `correlation_id` = the grant_id or request_id (opaque UUID)
- `detail` = `"event=granted expires_at=..."` (operator metadata, no subject PII)

### Erasure → aud_event

`Samen.Erasure.seal_db_tiers/5` has a new `Ecto.Multi` step `:aud_event` that writes:
- `event_type = "erasure"` (bounded enum)
- `subject_id` = the subject's UUID
- `actor_id` = the erasure actor id
- `detail` = `"outcome=shredded vault_sealed=N non_pii_redacted=M attestation_id=..."` (system tokens, no PII)

Both conform to the token-only-downstream invariant: `subject_id` is the subject's opaque ID, `actor_id` is the operator's opaque ID — neither carries the subject's plaintext name, email, DOB, or any other PII.

## no_plaintext_pii AudEvent tier

`Samen.NoPlaintextPii.Tiers.AudEvent` is a new CI-mode tier that:
1. Queries `information_schema.columns` for `aud_event` (the parent table)
2. Applies the name gate (PII-named plaintext columns fail) + allow-list gate (unknown plaintext columns fail)
3. Allow-lists: `aud_id`, `aud_event_type`, `aud_subject_id`, `aud_actor_id`, `aud_correlation_id`, `aud_detail`, `aud_occurred_at`

Registered in `Samen.NoPlaintextPii.default_tiers/0` alongside the existing tiers.

## Verifier robustness fix

`mix samen.verify.prefixes` (`abbrev_for_resource/1`) was calling `Samen.Info.abbrev/1` on `Samen.AuditEvent` which raised `ArgumentError` because it's not a Spark DSL module. Fixed by adding `rescue ArgumentError -> nil` to the function — plain Ecto schemas that are catalogued but not Ash resources return `nil` (no abbrev), and are filtered from the abbrev-check table by `Enum.filter(fn {_t, {_r, abbrev}} -> is_binary(abbrev) end)`.

This is the correct policy: `aud_event` columns carry the `aud_` prefix by convention (enforced by the allow-list in the `AudEvent` no_plaintext_pii tier), but the prefix is not a Spark DSL-declared abbrev — it's structural. The `prefixes` verifier does not flag `aud_event` because `abbrev_for_resource` returns `nil`, causing the table to be excluded from abbrev-based prefix checking.

## Resource test updates

Two existing tests in `test/resource_test.exs` were tightened:

1. **`NO INHERITS` test:** now skips migration files that contain `PARTITION OF` (which is aud_event's partitioning DDL, not table inheritance). The check was `content =~ ~r/inherits/i` which would falsely match the `PARTITION OF` migration because the docstring says "INHERITS" in prose (comparing the two concepts). Updated to match only `\bINHERITS\b` and skip files with `PARTITION OF`.

2. **`pg_inherits is empty` test:** partitioned tables create `pg_inherits` rows (parent-child partition relationships, and also index inheritance rows with `relkind = 'I'`). The test now asserts that all `pg_inherits` rows come from partitioned parents (`relkind = 'p'`) or index parents (`relkind = 'I'`), and that NO rows come from regular table parents (`relkind = 'r'` — which would be classic table inheritance). The four fragment-composition resource tables (`pat_patient`, `stf_staff`, `com_contact`, `cpy_company`) are still verified to be plain `relkind = 'r'` with `relhassubclass = false`.
