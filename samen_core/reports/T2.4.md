## (a) Expand/contract conventions + additive helpers

A migration declares itself with `use Samen.Migration, phase: :expand | :contract`. The phase is discoverable at the file-source level (regex) so the CI check never has to compile migration files (which would collide with Ecto's own compilation — see the down/0 note below).

**Additive helper** `add_nullable_column/3,4` emits a reversible `ALTER TABLE ... ADD COLUMN` / `DROP COLUMN` pair. `null: false` is **rejected** (`ArgumentError`) — a NOT NULL add is a contract-phase op, not additive. This keeps expand backward-compatible so the old binary keeps running against the new schema (doc §runs 2), which is what makes rollback-by-redeploy safe.

**down/0 CI check** (`Samen.Migration.DownCheck` + `mix samen.verify.migrations`): against a **throwaway scratch DB** (created + dropped by the task — never prod/dev), it migrates all up, then for each `:expand` migration steps `down` (running its `down/0`) and back `up`, failing closed if any down is missing, raises, or is not a clean round trip. `:contract` migrations are NOT down-tested — the doc covers them by PITR, not `down/0` (§runs 2b). Wired into `demo/ci.sh` as step 7/7 (green: "exercised down/0 for 1 expand migration(s)").

## (b) DDL timeout posture

`expand_setup/0,1` and `contract_setup/1,2` emit, as the first statements of the migration transaction:

```
SET LOCAL lock_timeout = '5s';
SET LOCAL statement_timeout = '15s';
```

`SET LOCAL` scopes to the current tx (reverts on COMMIT — never leaks into the pool). `lock_timeout` bounds lock-acquisition (the blocking-lock stall); `statement_timeout` bounds execution. Values live in one source of truth (`__timeout_sql__/0`) so the live test asserts against the shipped constant, not a hardcoded literal.

## (c) Carve-outs + T1.2 composition (the paired-migration pattern)

`concurrent_index/3` (`CREATE INDEX CONCURRENTLY`) and `chunked_backfill/4` (each chunk its own short committed tx) run **outside** the DDL transaction and both **REQUIRE `@disable_ddl_transaction true`** — they raise otherwise. They deliberately do **not** set `statement_timeout`, so the 15s ceiling can't abort a large index build or backfill (doc §runs 2b).

**Composition with T1.2 `catalog_sync` (documented + tested):** `catalog_sync` REFUSES to run under `@disable_ddl_transaction true` (Gate-0 fix #4 — outside a tx a crash between DDL and the catalog INSERT is fail-open); `concurrent_index` REQUIRES it. So the two are **mutually exclusive within one migration by construction**. The resolution is the paired-migration pattern: a CONCURRENTLY migration carries no catalog rows (an index is not a catalogued object; the catalog row for the underlying column was written by the transactional expand that added it). If index metadata ever needs recording, it goes in a *separate transactional* migration. `concurrent_index`'s guard message documents this explicitly. The test `catalog_sync REFUSES under @disable_ddl_transaction true` re-asserts the other half of the pattern.

Live-verified: `test/fixtures/carveouts/` runs a real `CREATE INDEX CONCURRENTLY` build (survives; index exists in `pg_indexes`) + a chunked backfill (chunk_size 10 over 25 rows → all 25 filled). `migration_lock: false` on the scratch migrator run avoids advisory-lock/CONCURRENTLY connection contention on the small scratch pool (documented in the test).

## (d) `contract_ready?` bake-window gate

`contract_setup(change_key)` refuses (raises) unless `contract_ready?/3` returns `{:ready, _}`. The bake clock is a `samen_migration_meta` row written by the paired expand's `expand_setup(change_key: ...)` at `now()` (run/deploy time — not the migration file's author-time timestamp). `contract_ready?` returns:

- `{:not_ready, {:no_expand_row, key}}` — the expand never ran → **fail closed** (no bake clock at all).
- `{:not_ready, {:baking, elapsed, window}}` — expand ran but window not elapsed.
- `{:ready, elapsed}` — baked.

Window configurable via `config :samen_core, :contract_bake_window, {amount, unit}` (default `{7, :day}`).

## Simulation seams / operator TODOs

1. **No physical replica / Neon** in this environment. The down/0 CI check and carve-out tests use a **local** throwaway scratch DB (created + dropped per run) as the "scratch DB" the spec calls for. PITR of the irreversible contract phase (the doc's coverage for non-reversible contracts) is the T2.5 game-day task — registered there, not faked here.
2. **`samen.verify.migrations` scratch-DB naming** derives from the base repo's `database` config plus a random suffix, and drops the DB after. In CI it needs a role that can `CREATE DATABASE` (the local `clank` role has it). Production CI should run it against a dedicated CI Postgres, not prod.
3. **`migration_lock: false`** is used only inside the carve-out *test* (single-process migrator) to avoid advisory-lock/CONCURRENTLY pool contention. Real deploys keep the default migration lock; the CONCURRENTLY carve-out there runs against a full production pool.
4. **`samen_migration_meta` is not catalogued** (like `schema_migrations` / `oban_jobs`) — it holds only change keys, phases, timestamps, and migration module names (no subject data), so the PII oracle and catalog-parity correctly ignore it.
