## Red paths (HARD RULE 2)

1. **`pii_attribute` → undeclared vault fails compile.** A `pii_attribute` routing
   to a vault the `pii do` block never declared raises `Spark.Error.DslError` at
   compile time (closed-world routing). Enforced primarily by the `MaterializePii`
   **transformer** (`{:error, DslError}` reliably aborts compile in this Ash/Spark
   version; the `VaultDeclared` **verifier** is defense-in-depth + introspection).
   Control: the same resource with the vault declared compiles and routes.

2. **A likely-PII composite type declared OUTSIDE a `pii do` block is not silently
   plain.** `attribute :full_name, Samen.Type.FullName` (a composite PII type) as a
   plain attribute compiles (it is a valid Ash attribute), but the classification
   oracle flags it: `Classification.classify(type) == :pii` while
   `Info.vault_routed?/2 == false`. That mismatch is exactly the C4 `pii_classify`
   (T1.8c) violation — the composite is NOT treated as plain-by-omission. Control:
   a genuinely non-PII `:boolean` attribute classifies `:non_pii` and is cleared,
   proving the oracle discriminates rather than calling everything PII.

3. **Unclassified type is masked-by-default** — covered as a green+property proof in
   `pii_classification_test.exs` (an unknown type and a raw `:string` both classify
   `:pii`), and load-bearing-ness proven by the anti-tautology probe below.

## Anti-tautology probes (HARD RULE 2) — both confirmed, reverted

- **Probe A (undeclared-vault guard).** Sabotaged BOTH guard layers in scratch:
  `MaterializePii.verify_vaults_declared/2 → :ok` AND `VaultDeclared.verify/1 → :ok`.
  Result: the bad-vault resource compiled with no raise; red-path test 1 FAILED
  ("Expected exception Spark.Error.DslError but nothing was raised"). Reverted both
  files; red path passes again (3 passed). → guard is load-bearing.
- **Probe B (mask-unknown-by-default).** Sabotaged `Classification.classify/1` clause
  (3) to fall through to `:non_pii` instead of `:pii`. Result: 3 tests + 1 property
  FAILED — the keystone tests (unknown type → `:pii`; `:string` → `:pii`) and the
  red-path-2 "composite outside `pii do` not silently plain" assertion. Reverted;
  13 passed again. → the mask-unknown-by-default default is load-bearing, not a
  tautology.

`red_paths_failing_closed: true` — every red-path assertion flips to failure when
its guard is neutered.

## Storage naming (vision doc PII routing note) — verified

- Composite fields (FullName/Emails/Phones) route BY VAULT NAME: carry the resource
  abbrev, NO `pii_` column prefix — `full_name → pat_full_name`. (`source: nil` →
  `AbbrevStorage` prefixes normally.)
- Scalar `pii_attribute` fields carry the `pii_` prefix — `dob → pii_pat_dob`,
  `mrn → pii_pat_mrn`. (`MaterializePii` sets an explicit `source: :pii_<abbrev>_<name>`
  that `AbbrevStorage` honors verbatim, no double-prefix.)
- Both are equally vault-routed; downstream verifiers key on the DECLARATION via
  `Samen.Pii.Info`, never on the prefix. `vault_routed_columns/1` returns the union
  including the un-prefixed composites (`pat_full_name`) — proving verifiers must not
  rely on a `pii_` prefix to find vault-routed data.

## Introspection API for T1.4/T1.5 (delivered)

`Samen.Pii.Info` exposes, per resource: `pii_attributes/1`, `vaults/1`, `fields/1`
(→ `%Field{name, type, vault, storage_name, composite?}`), `routing/1`
(`vault => [storage_name]`), `vault_routed?/2`, `vault_routed_columns/1`. This is the
list-of-vault-routed-attributes / their-vaults / their-storage-names contract the
task states T1.4/T1.5 and the verifiers need.
