## Scope coverage (T1.7 (a)–(d))

**(a) `Samen.Erasure.shred(subject_id)`** destroys the subject key via `Samen.Kms.adapter().shred/1` FIRST and outside the DB transaction (the key store is external per ADR-001; its destruction is the load-bearing act and cannot participate in a Postgres tx). Then, in ONE Ecto.Multi transaction, it: stamps the SHREDDED sentinel (`state="shredded"`, `erased_at`) on every `pii_vault` row of the subject (the token FK the domain row carries now points at a dangling/sentinel row — doc D7 "down to a dangling token"; ciphertext is left in place as useless bytes so the oracle can still witness it is undecryptable); redacts registered `non_pii!` columns; writes an `"erased"` audit row on the reveal lifecycle log (`rvl_reveal_audit`); and writes + returns the erasure report. Returns `{:ok, %{attestation: att, report: report}}`. The attestation is always positive (`:shredded` with `destroyed_at`) after a successful shred. Fails closed (`{:error, {:kms_shred_failed, reason}}`, no sentinel/report/fabricated attestation) when the key store is unreachable.

**(b) `non_pii!` registry** (`Samen.NonPii`): `register/1` records a review-gated override with who/why metadata (`cleared_by`, `reviewed_by`, `reason`) in the `npi_non_pii` catalog table, flagged per `(table, column)`. It enforces the distinct-party invariant at the registry layer (`{:error, :self_review}` when `cleared_by == reviewed_by`) — a single actor cannot wave a plaintext column through. `catalog_flags/1` is the read side the catalog/oracle consume. Per the task, only the registry + its erasure arm live here; the build-time enforcement UX (fail the build until a flagged plain column has a distinct-2nd-reviewer entry) is T1.8c.

**(c) Row-level redaction on erasure** (`NonPii.redact_for_subject/3`): because key-shred does not reach plaintext columns (the doc names `non_pii!` as an explicit key-shred carve-out), erasure overwrites each registered column's plaintext with a non-reversible redaction sentinel where the row's `subject_column` matches, via a parameterized `UPDATE` (identifiers hard-gated to `/^[a-z_][a-z0-9_]*$/`, values bound). It returns the cell count + a per-column tally recorded in the report. Idempotent (0 additional cells on a second pass via the `IS DISTINCT FROM` guard).

**(d) Erasure report artifact** (`era_erasure_report`, one row per call): attestation id, outcome (`shredded` | `already_shredded` | `absent`), a `tiers` JSON map the T2.9 oracle consumes (KMS state + `positive_tombstone` flag; vault `rows_total`/`rows_sealed`/`rows_still_active`; `registered_non_pii` redaction columns), and the sealed/redacted tallies. `Samen.Erasure.latest_report/2` reads it back; `erased?/2` is the oracle predicate (KMS attests `:shredded` AND no vault row still `"active"`).

## Design notes / decisions

- **Key-shred first, outside the tx.** The DEK destruction is the guarantee; the DB-tier sealing/redaction/report is bookkeeping the oracle reads. If the DB tx fails after the key is gone, the data is already unrecoverable (fail-safe) and a re-run is idempotent and completes the sentinel/redaction/report.
- **Sentinel, not deletion, of vault rows.** The ciphertext stays physically present but stamped `state="shredded"`, so the oracle's DB-tier scan can assert "0 rows still active" AND "every remaining row is undecryptable" rather than inferring erasure from row absence. This matches the doc's "dangling token / undecryptable bytes" framing.
- **Distinct-party at the registry layer** mirrors the reveal grant's `granted_by <> requestor_id` discipline — the same anti-single-actor safety.
- **Audit on the existing reveal lifecycle log** (`rvl_reveal_audit`, new event `"erased"`) rather than a new table, so erasure rides the same tamper-evident chain the Phase-4 G4 hash chain will cover.

## Residues / carry-forwards

1. **Oracle consumption is T2.9.** This task produces the report artifact and the `erased?/2` predicate; T2.9 wires the full multi-tier oracle (`:absent`/`:active` KMS state = FAIL, PITR-history scan, CDC/rollup tiers). The `tiers` map already carries the `positive_tombstone` and `rows_still_active` signals it needs.
2. **`non_pii!` enforcement UX is T1.8c.** Here only the registry + erasure arm exist. The `pii_classify` verifier that fails the build until a flagged column is registered (with a distinct 2nd reviewer) is T1.8c; `catalog_flags/1` is the surface it reads.
3. **Redaction recipe is per-registered-column.** A `non_pii!` column's subject-matching column is declared at registration time (`subject_column`). Resources whose subject linkage is indirect (a join, not a direct column) are out of scope for T1.7's row-level arm; the demo (`pat_patient.pat_subject_id`) uses a direct column.
4. **`pii_vault` is one physical table** (the T1.4 decision), so the sentinel scan is one tier. When per-vault physical tables land, the sentinel columns replicate per table.
