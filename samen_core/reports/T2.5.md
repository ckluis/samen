## (a) The runbook

`docs/runbooks/pitr-gameday.md` is the full quarterly drill script for the **bad-contract**
scenario. Structure: operator-TODO header → honest-RPO framing → §A preflight → §B inject
fault → §C detect/decide → §D arm (i) forward-fix/expand-reversal (RTO ≤ 30 min target) →
§E arm (ii) full PITR branch-validate-promote (RTO ≤ 2 h drilled) → §F local-simulation
description → §G measured evidence appendix.

The doc's honest framing is stated as its own section: a bad-contract PITR restore's
**effective RPO = detection latency** (restore to a point before the contract throws away
every business write since the contract COMMITted), which is *why* forward-fix/expand-
reversal is the preferred control and restore is the last resort. The steady-state
RPO ≤ 1 min (hardware/infra failure) is told apart from the bad-contract RPO.

## (b) The local simulation

**Seam (documented, operator-TODO'd):** Neon's copy-on-write WAL branch is simulated by a
`pg_dump` logical snapshot taken at the pre-contract instant; "restore/promote" is a
`psql`-restore into a fresh local DB. The RESTORE-ARM mechanics (fresh DB, app validation,
key-store exclusion) are identical to production; only the snapshot substrate differs. Real
Neon registered as operator TODO.

**Orchestrator (`pitr-gameday-sim.sh`)** drives, in order:
1. `migrate` — demo-shaped DB (`samen_pitr_drill_base`) migrated to the pre-contract
   baseline (all demo migrations before the expand/contract pair, incl. the
   `samen_migration_meta` bootstrap); seed a real PII subject into the vault (ciphertext in
   Postgres; wrapped DEK in the external file-backed key dir).
2. `pg_dump` base (branch @ pre-contract); assert **key material absent from the dump**
   (`grep` for `master.key`/`.dek`).
3. `expand` (reversible additive `cnt_tier` add) then `bad_contract` (drop the load-bearing
   `cnt_display_name`).
4. `detect` — app validation harness fails on the missing column (measured).
5. **Arm (i)** `reverse` — reverse the expand via its tested `down/0` (`Ecto.Migrator.run
   :down`) + forward-fix re-add; re-validate (measured).
6. **Arm (ii)** restore the pre-contract dump into a fresh DB (`samen_pitr_drill_restore`)
   + `validate` the app suite (measured, restore + validate broken out).
7. `keystore` — point at an EMPTY key dir; restored ciphertext survives but `reveal` denies.

The harness runs in `MIX_ENV=drill` (new `config/drill.exs`) so it uses throwaway DBs and
a plain (non-Sandbox) pool that writes COMMITTED rows a `pg_dump` can see. Nothing touches
`demo_dev`/`demo_test`. The drill drops/creates its DBs and cleans up on success (idempotent
— re-ran green with 0 leftover DBs).

## (c) Key-store exclusion (reuses T1.4's `vault_pitr_test.exs` pattern)

The restore arm proves the load-bearing PII claim: **restore does not resurrect shredded/
absent keys.** Same methodology as `samen_core/test/vault_pitr_test.exs` — the wrapped DEK
lives in an external directory (`Samen.Kms.FileBacked`), never captured by `pg_dump`. In the
`keystore` phase the harness points `SAMEN_KMS_KEY_DIR` at a brand-new EMPTY dir (modeling a
DB-only restore with no key store), confirms the ciphertext row IS present in the restored
DB, then confirms `Vault.reveal` returns `{:error, :unavailable}`. The restore brings back
useless ciphertext; the key is unrecoverable.

## Red path + anti-tautology probe (plan hard-rule 2)

**Red path — post-restore validation fails closed.** `bash pitr-gameday-sim.sh
--probe-corrupt` corrupts the restore target ONCE (`ALTER TABLE cnt_contact DROP COLUMN
cnt_display_name` post-restore) and asserts the app validation harness FAILS. Result: the
`validate` phase exits 1 ("cnt_display_name column MISSING"), the orchestrator confirms the
fail-closed behavior, and prints "RED-PATH PROBE OK". If a corrupted restore ever validated
(fail-open), the script exits non-zero. Confirmed: PROBE OK.

**Anti-tautology probe (scratch copy OUTSIDE `/tmp`, since removed).** Copied the harness to
`.antitaut_scratch/demo` (self-created subdir; `samen_core` symlinked so deps resolve),
sabotaged `DrillValidate.run/3` to always return `0` (fail-open). Ran the `validate` phase
against a DROP-COLUMN-corrupted DB: it returned **exit 0** despite logging "cnt_display_name
column MISSING" — proving the red path's pass/fail is genuinely driven by the schema-reading
validation logic, not a constant. **Reverted** (scratch dir deleted; confirmed 0 `SABOTAGE`
occurrences and the real `if Enum.all?(results, &(&1 == :ok)), do: 0, else: 1` intact). The
validation is load-bearing, not tautological.
