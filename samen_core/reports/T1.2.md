### (b) `Samen.Migration` with `catalog_sync` — Gate-0 fix #4

**File:** `lib/samen/migration.ex`

The `catalog_sync/1,2` macro:
- **Refuses to run under `@disable_ddl_transaction true`** via a runtime guard in `__guard_ddl_transaction__!/1` that reads `caller.__migration__()[:disable_ddl_transaction]`. Raises `RuntimeError` with a clear diagnostic naming both the problem and the fix.
- **Why runtime, not compile-time:** `use Ecto.Migration` injects `@disable_ddl_transaction false` via its own `__using__/1`. The user then overrides with `@disable_ddl_transaction true` AFTER `use Samen.Migration`. Module attribute semantics mean the last write wins — Ecto captures the final value at `@before_compile` time into `__migration__/0`. Reading `Module.get_attribute` at macro expansion time is unreliable because the function body's macros expand before the module is finalized. `__migration__/0` at runtime is the authoritative value (the same one `Ecto.Migrator` uses).
- **Parameterized inserts (spike F4):** Values are developer-controlled compile-time identifiers (module names, attribute names, table names), never user input. SQL values are single-quote-escaped defensively. True `$1`-style parameterized queries are not available in Ecto's `execute/1,2` DDL context.
- Includes `catalog_sync_down/1,2` for explicit `down/0` migrations (non-`change/0` style).

### (c) Codegen helper scoping (spike F2)

`catalog_sync/2` accepts `only: [:attr1, :attr2]` to scope the emitted reversible `execute` statements to exactly the columns this migration added. The `down` step removes only those columns' catalog rows without orphaning the table entry (which other columns may still use). This is the F2 codegen scoping spike recommendation.

### (d) `mix samen.catalog.dump` — deterministic `schema.dict.json`

**File:** `lib/mix/tasks/samen.catalog.dump.ex`

Emits `schema.dict.json` with:
- Top-level key `"tables"` — array of table entries sorted by `table_name` (ascending)
- Each table has `"table_name"`, `"resource"`, and `"fields"` (sorted by `column_name` ascending)
- Fields carry `"column_name"`, `"logical_name"`, and `"type"`
- `build_dict/1` is pure and testable separately from filesystem I/O
- Domains discovered from `Application.get_env(:ash, :domains)` or `--domain` CLI args

### (e) CI linter: `mix samen.verify.column_refs`

**File:** `lib/mix/tasks/samen.verify.column_refs.ex`

Scans `.ex`/`.exs` files for tokens matching `^[a-z]{3}_[a-z][a-z0-9_]*` and fails (exit 1) on any that do not appear in `fld_field`. Features:
- Catalog infrastructure tokens (`tam_`, `fld_`) are never flagged
- `# samen:allow <token>` comment suppresses specific tokens on a line
- `check/2` is separated from `run/1` so tests can call it without triggering `:erlang.halt/1`
- Uses `Samen.Verifier.halt_if_violations/2` (same harness as the spike S0.6)

Also delivered: `lib/samen/verifier.ex` — the verifier harness (ported from s06_verify).

## Honest residues / caveats

1. **The linter is regex-based, not AST-based.** It will flag tokens in comments and multi-line string literals. The `# samen:allow` escape hatch mitigates false positives. An AST-based approach is more precise but out of T1.2 scope (the spec calls for "a mix task failing on any source reference to an unknown `^[a-z]{3}_` storage column").

2. **The linter does NOT catch hallucinated table names** (e.g., `xyz_hallucinated` without a subsequent `_column` segment at the right position). Table-level parity is C1's job (`catalog_parity` verifier, T1.8a).

3. **The dump task requires `--domain` or `:ash, :domains` app config.** In the kernel's test suite these are not configured (the kernel is a library, not an app), so the dump task is tested via `build_dict/1` directly rather than via the mix task's full `run/1`. The mix task wiring is production-correct for host applications.

4. **`catalog_sync` guard is runtime, not compile-time** (see explanation in `Samen.Migration` moduledoc). This is the correct behavior given Ecto's attribute semantics; a compile-time guard would require reading the attribute before `@before_compile` runs, which is unreliable.
