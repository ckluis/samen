## What T3.1 delivers (verified present + correct)

### Scope-packaging decision — ADR-004 (`docs/adr/004-scope-packaging.md`)

Decision: **Option C — library-authored blueprint macro, host-materialized resources.** A scope ships
as a `use Samen.Scopes.<Scope>, otp_app:, repo:, namespace:` macro in `samen_core` that expands into
real `use Samen.Resource` resources **owned by the host** (host otp_app / repo / namespace). This is
the only option that keeps all four host-ownership invariants AND a single canonical definition:
resources land in the HOST's catalog, the host's unchanged verifiers scan them, PII lives in the host's
one Postgres, and a scope upgrade reaches every host by a dep bump + one additive migration. Pure-library
resources (Option A) and copy-generation (Option B) are analysed and rejected with reasons; generation is
kept as the escape hatch for the top rung (`Samen.Context` / a vertical that forks a scope). I reviewed
the ADR against the code — it is accurate: `use Samen.Resource` threads `otp_app`/`domain`/`repo`/`abbrev`,
the abbrev registry records the host module string, migrations ship as a documented `Samen.Migration`
template the host copies (the `mix samen.gen` task is an honestly-flagged follow-up).

### Identity resources (blueprint, `samen_core/lib/samen/scopes/identity/`)

`org · user🔒 · membership · role · api_key · invitation🔒 · audit`, per the vision-doc scope table:

- **Org** — the tenant anchor, org-LESS (nullable `org_id`), no PII, policy `OrgIsSelf` (id == actor.org_id).
- **User🔒** — `full_name` (vault `:pii_name`), `emails` (vault `:pii_email`); composite types, masked by
  default; org-scoped; `reveal_user` action.
- **Membership** — (user, org, role); org-scoped + RBAC-gated writes (admin+ AND no escalation).
- **Role** — Tier-0 config rows (per-org role catalog, bounded enum), admin-gated writes.
- **ApiKey** — two planes (`:tenant`/`:operator`), `token_digest` only (raw key never stored),
  `minter_role` ceiling; org-scoped, admin-gated mint/revoke.
- **Invitation🔒** — `email` (vault `:pii_email`), masked by default; org-scoped; `reveal_invitation`.
- **audit** — rides the existing T2.2 `aud_event` tier via `Samen.Scopes.Identity.Audit` writers
  (token-only rows); **NOT a new table** (ADR-004 §5).

### Canonical policy/pattern library (authored once, inherited by the mount)

- `Samen.Scope` — the `Ash.Scope.ToOpts` actor struct (PII-free `%{id, org_id, role, membership_id}`);
  `new/1` **refuses an org-less scope** (cross-org hazard → fail closed).
- `Samen.Scope.Role` — closed, ranked set (owner>admin>member>viewer); `may_manage?/2` = the
  no-escalation rule; `at_least?/2` = the rank floor.
- `Samen.Scope.ApiKey` — `authorized?/4` = org-match ∧ declared-scope ∧ actor-ceiling; a key can never
  out-reach its minter.
- `Samen.Policy.OrgScope` (FilterCheck — foreign-org rows are *invisible*, not merely forbidden),
  `OrgIsSelf` (anchor), `RoleAtLeast` (SimpleCheck), `ManageRole` (SimpleCheck, no escalation).

## Findings

### Finding 1 (FIXED, was breaking root CI) — DownCheck peeled the wrong migration when a non-expand sits on top of an expand

The prior partial T3.1 session added the Identity mount migration (`20260705130000`) with a version
LATER than the demo's T2.4 expand migration (`20260705120000_expand_add_contact_tier`). The expand-`down/0`
CI check (`Samen.Migration.DownCheck`) exercised each expand with `Ecto.Migrator.run(:down, step: 1)`,
which peels the **newest applied** migration — now the Identity migration, not the expand. Result:
`mix samen.verify.migrations` (demo/ci.sh step 7/9) failed closed with *"stepping down rolled back
[20260705130000] instead of this migration"*, so **root `bash ci.sh` was RED** before I started. This is
exactly the regression the task warns about ("keep the 9-step demo/ci.sh green").

**Fix (`samen_core/lib/samen/migration/down_check.ex`):** exercise each expand with
`Ecto.Migrator.run(:down, to: version - 1)` (roll the stack down THROUGH the expand, running its `down/0`
and any downs above it), assert the expand's version is in the rolled-back set, then `:up, all: true` to
restore. This is robust to any number of non-expand migrations layered on top of an expand and is strictly
more thorough (it also round-trips the layered migrations' downs). Added a regression fixture set
`samen_core/test/fixtures/downcheck_layered/` (base + expand + a non-expand `create_widget2` on top) and a
test `"GREEN: exercises an expand's down/0 with a NON-expand migration layered on top"` that fails under
the old `step: 1` logic and passes under the fix. All 17 `migration_expand_contract_test.exs` tests green;
demo step 7 now passes ("exercised down/0 for 1 expand migration(s)").

### Finding 2 (FIXED) — CRM `Contact.reveal_contact` called a non-existent `Samen.Reveal.granted?/1`

The T1.9 demo CRM's `reveal_contact` action `run/2` called `Samen.Reveal.granted?(ctx)`. `Samen.Reveal`
has **no** `granted?/1` (verified: `function_exported?(Samen.Reveal, :granted?, 1) == false`); the grant
callback lives on the checker *module* (`grant_checker().granted?/1`, the `Samen.Reveal.Grant` behaviour).
CI stayed green only because no test ever invoked that action — invoking it would raise
`UndefinedFunctionError`. The scope-authoring guide §5 and the Identity blueprint already do it correctly
(`Samen.Reveal.grant_checker().granted?(ctx)`). This is the precise "idiom drift" T3.1's guide + Gate 3
exist to kill. **Fix:** aligned `demo/lib/demo/crm.ex` to the guide pattern, with a comment naming the
trap. The new reveal-action test (above) now exercises the Identity reveal path so this class of drift is
caught going forward.

### Finding 3 (honest scope note, NOT a defect) — `ApiKey.authorized?/4` is a decision function, not yet a request-path enforcement

`Samen.Scope.ApiKey.authorized?/4` (the "a key can never out-reach its actor" rule) is a pure function,
exercised only in tests. It is **not** wired into any Ash resource policy or request plug yet — there is
no live path where an api_key authorizes a real request through it. This is correct for T3.1: the
request-path wiring is the external API surface (T3.11) and the operator plane (Phase 4). The ADR (§6.4)
and guide frame it accurately as a use-time decision function; the api_key resource stores the declared
scopes/plane/minter_role for that future wiring. The red path is therefore a **model proof**, not an
end-to-end enforcement proof — stated here so no one over-trusts it before T3.11.
