How "zero hand-edits" is kept true

Four generator probes run in CI on every pull request. The flagship probe generates a fresh app, runs its full gate, seeds it, boots it, HTTP-probes its routes and drives two sabotages against the generated gate. If the substrate drifts from what it generates, this is where it shows. The probes work on a private copy of the abbreviation registry and fail if the committed one changes by a single byte.

Measured honestly. In pawchart, the veterinary vertical, the four scope-mount files total about 188 authored lines. That number is about mounting framework surfaces, not about apps: pawchart as a whole is a hand-built product of about 3,900 lines. Act II · Trust, by construction

Seven features that only work because both planes share one core.

Most products guard customer data in the places someone thought of. Samen moves the decision into the field itself, then builds every feature on top of that one decision.

02The vault

•••• isn't a redaction. It's the value.

Declare pii_attribute :email and the value goes to a per-subject-keyed vault. The row keeps a vt_… token; plaintext is nowhere at rest. Every reader gets %Masked{} back: the UI, the API, the CSV writer, the log line. Forgetting to mask is not a mistake available to you.

1decrypt path in the whole system. One function to gate, one to log, one for a reviewer to read. built
  • Validated, then tokenized: Money, Email, Phone, Address… each type's cast runs before encryption
  • CSV masks by omission: the column isn't in the file, so there's nothing to un-redact
  • A verifier in a separate OS process attests no tier holds plaintext

02The vault
Close ✕

Why exactly one chokepoint

If plaintext can be produced at forty call sites, "no plaintext leaks" is forty separate claims, each decaying as the code grows. Route every read through one function and the claim becomes one question a machine can answer: who called it, under what grant, and was it recorded?

What happens to one PII field

WhereWhat it holds
Domain rowvt_9f2c…, a stable token you can join and group on, which says nothing about the value
VaultAES-256-GCM ciphertext under a per-subject key held in an external KMS
UI · JSON:API · logs · CDC%Masked{}, rendered •••• (four fixed bullets, so the mask doesn't leak the length)
CSV exportNothing: the column isn't emitted

Six idioms, applied to every object

  • Self-qualifying storage: abbrevs projected at compile time into the DB, CDC, logs and catalog
  • A machine catalog written inside the migration transaction; an uncatalogued column doesn't compile
  • The PII vault with one decrypt chokepoint
  • Postgres as the engine: LISTEN/NOTIFY, SKIP LOCKED, Oban in the same transaction
  • A malleability ladder: config rows, validated custom fields, tenant objects, code
  • Two planes, one core: the next three sections

What it costs, on purpose

The guarantee is exactly as strong as key custody. Destroying a subject's key destroys their data everywhere; that's how erasure works. It also means a lost key is an accidental erasure, not a recoverable incident. Samen makes that trade deliberately.

03Reveal

Support can see PII. Only with a second person's yes.

A dispatcher needs the address that bounced. Pretending support never sees data just moves the work into a spreadsheet nobody audits. Samen keeps the exception inside the system and makes it expensive, visible and self-expiring.

2people, always. The requester cannot approve: a database CHECK makes that row impossible, not just a form rule. built
  • Time-boxed: the auto-revoke job commits in the same transaction as the approval
  • Never renewed in place: an extension is a new request and a new approval
  • Tenant-readable: a hash-chained log the operator cannot edit, the tenant can read without asking
The four properties, with teeth →
03Reveal
Close ✕

Four properties, three enforced by the database

A property enforced only in application code holds until the next refactor. Three of these four live where a wrong deploy can't reach them.

PropertyHow it's enforced
Second-partyPolicy check and CHECK (granted_by <> requestor_id). They fail differently and share no failure mode.
Time-boxedEvery grant has expires_at; the revoke job is enqueued in the approval's transaction. If it can't be enqueued, the approval doesn't commit.
Logged, tenant-sideHash-chained, append-only; a trigger refuses UPDATE and DELETE. Each entry carries the hash of the one before.
ScopedThese fields, this subject. Not a role that gets unmasked, not a session that gets elevated.

Why "never renewed in place" matters

A grant with a renew button becomes permanent the first afternoon someone puts it on a schedule. Here every extension is a separate, separately approved entry, so the log shows how many times access was granted, not one row with a date that keeps moving.

The actor that can't be granted anything

Cross-tenant analytics run as a token-blind actor over resources with no pii_* columns at all. The reveal path refuses that actor before any grant lookup, so an actor that can reveal can't run cross-tenant, and one that runs cross-tenant has nothing to reveal.

What we deliberately don't claim. An earlier version of this page said "run support without ever seeing PII." It sounded better and was false by construction, so it was retired. Support can see PII: through a grant a second person approved, that expires on its own, and that the tenant can audit without asking permission.

04Two planes
Close ✕

Why a separate admin app is the leak

The usual shape is an internal console with its own controllers, queries and serializers, written faster and reviewed less than the product. Same database, none of the same discipline.

  • Every query path is a road to plaintext. Masking in the product's render layer simply isn't present in the admin app.
  • Divergence is silent. The product adds a field; the admin app never learns it's sensitive.
  • Audit coverage doesn't transfer. A separate app that reads the row directly produces no audit record, so the tenant can't see it happened.

Building the operator plane from the same resources inverts all three: one decrypt chokepoint means one place to gate, one place to log, one place to review. And impersonation is genuinely useful for support, because the reproduction is real.

The SaaS company is itself a tenant

The operator org mounts the same universal scopes as every customer: its own help desk, its own CRM, platform billing over tenants. The plane boundary is a property of actors, not of codebases.

The cost, named. The operator plane is constrained by what the resource layer exposes. There's no escape hatch to "just run a query," by design, because that escape hatch is the thing being removed.

05Erasure

"Delete my data" is a DELETE. That isn't erasure.

The row goes; the value survives in the audit log, last night's rollup, a queued job's arguments, the CDC stream and the backup. Samen erases by destroying the subject's key: the ciphertext everywhere becomes unreadable at once, including in tiers you forgot you had.

{{SHRED_TIERS}}tiers a separate OS process walks to attest a shredded subject is unrecoverable, including backups, PITR and replay. every CI run
  • A positive over a finite set, not a negative over every copy that might exist
  • The audit chain survives: you can prove a reveal happened, not recover what it showed
  • A new tier that stores plaintext turns CI red instead of slipping past a migration
Why key destruction is checkable →

05Erasure
Close ✕

Why key destruction is checkable and row-scrubbing isn't

Row-scrubbing asks you to prove a negative over an unbounded set: no copy of the value survives in any table, rollup, job, log, replica, backup or downstream consumer, including the ones added last week. There's no finite list, so there's no test. What ships is a migration and a hope.

Key destruction asks you to prove a positive over a finite set: this key material doesn't exist, and every tier that could hold this subject's data holds only ciphertext. Both halves are enumerable, so a verifier can walk them and a sabotage can make the walk fail.

The tiers the oracle walks

{{PII_TIERS}} tier checks in all, {{SHRED_TIERS}} of them run after a shred: database content, the CDC mirror, backups and PITR restores, the KMS attestation, session replay, and the trace-sink ingress. The others cover audit rows and the chain, the catalog, logs and telemetry, Oban jobs, rollups and vault declarations.

Why a separate OS process

An in-process check can be satisfied by the same memory that produced the data: a cached struct, a warm decrypt, a connection still holding a key. A fresh process sees only committed state, so what it attests is what actually persists.

Agent transcripts are inside the envelope

An AI conversation about a subject is subject data. Transcripts live under the subject's key with a 90-day default retention, so a shred takes them too, with no separate cleanup job to remember.

Scope, stated plainly. The full regenerate-and-shred game-day runs end to end in driftwood, the deepest vertical; the verifier itself ships with every generated app. Erasure can't reach a system samen never wrote to: a spreadsheet someone exported, or a downstream consumer that stored its own plaintext.

07Chat
Close ✕

Why one message can render two truths without a second code path

The naive build is two renderers: the tenant view, and an operator view that redacts. The redacting one is newer and less reviewed, and it drifts the first time someone adds a field.

Two mechanisms, both reused

  1. The PubSub envelope carries an id, never a body. Every subscriber re-reads the message through its own scope. A masked session can't receive plaintext by subscribing, because the topic never carried any.
  2. The unfurl resolver composes two kernel gates that didn't change: OrgScope, then PiiResolution. Nothing in chat reads a column directly, unwraps %Masked{} or calls the vault.

A framework capability, not a chat trick

Samen.Web.ObjectRef takes a ref and an actor and returns a card. Chat is its first consumer: a CRM page can unfurl a related object, an audit entry its subject, a notification its target. Declare a new field as PII and it masks in every card on the next render, because the card was never the thing deciding.

Crossing the plane boundary

The thread belongs to the tenant org. Support reaches it through the impersonation grant, so OrgScope is satisfied for both parties with no new policy. An operator session targeting a different org sees the thread as zero rows.

An agent near customer data is a governance problem before it's a feature. So samen's agent loop starts at authority: the agent holds no credential that can write. A write is a proposal parked for a person; on approval it executes under that person's actor, recorded as agent-originated.

Why "runs as the approver" is the whole design

Approval workflows usually get this backwards: the agent asks, a human clicks yes, and the write executes under the agent's identity because that process already holds a connection. That launders the agent's permissions through a click. The human approved one write; the credential that performed it can perform every other write, and the audit trail names a service account.

  • Authority is bound at approval, not before. There's no standing agent credential to escalate, steal or forget to rotate.
  • The blast radius is the approver's own permissions. An agent can't propose its way past what its approver could do by hand.
  • The write is attributable to a person, and ai_agent_write keeps its origin distinguishable from ordinary traffic.

The no-PII-egress chokepoint

Every prompt, tool definition, tool argument and tool result passes one chokepoint before it reaches a provider. No vault-routed value, neither plaintext nor its vt_ token, may cross it. Tool results re-enter the conversation masked. A live reveal grant does not admit plaintext into an agent run: runs persist, and grants never apply to persisted egress.
