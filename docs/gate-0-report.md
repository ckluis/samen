## Per-idiom findings

### S0.2 — Abbrev storage transformer (R2) — **GO, caveat named**

The idiom rides one existing Ash field: `Ash.Resource.Attribute.source`. A compile-time Spark transformer rewrites each attribute's `:source` to `:<abbrev>_<name>`; AshPostgres uses `:source` verbatim as the physical column name, so migrations, SQL, identity indexes, and FK references all speak the prefixed name with **no AshPostgres fork and no custom data layer**. Logical `:name` is untouched; app code/actions/filters/API keep using `:name`. All 11 tests green; `mix ash.codegen --check` exits 0 (idempotent round-trip — no perpetual-diff).

- **Red path fail-closed (independently re-verified):** sabotaging both guard layers fail-open (caller-local `validate_abbrev!` → `:ok`, transformer `fetch_abbrev!` → `"xxx"`) made the abbrev-less/malformed-abbrev resources compile and the red-path tests FAIL. Green acceptance suite also non-vacuous: no-op'ing the transformer failed 6/8 green tests including the emitted-SQL test (`WHERE (c0."name" = $1)`), proving it exercises the runtime query path.
- **Caveat F1 (must-fix in core):** `belongs_to` FK attributes are synthesized by `Ash.Resource.Transformers.BelongsToAttribute`, not written by the user. A naive "run first" transformer silently leaves the FK column unprefixed (`company_id` instead of `com_company_id`). Fix encoded (`after?(BelongsToAttribute) -> true`, `before?(_) -> true`) and independently reproduced: removing the ordering guard flips the FK test to `left: :company_id, right: :com_company_id`. Ordering alone is not enough — a future attribute-adding transformer running after Samen could slip an unprefixed column through, so the C2 `prefixes` verifier is the required backstop.
- **Interface notes carried forward (not correctness bugs):** F2 opt-out convention ("prefix when `source in [nil, name]`, honor otherwise"; explicit `source:` is the legacy escape hatch); F4 stash the abbrev on a first-class DSL section (`samen do abbrev "com" end`) rather than a module attribute, so it is introspectable and survives fragment folding (directly relevant to S0.3); A5 abbrev permanence/collision registry is a core concern, out of spike scope.

### S0.3 — Fragment single-table composition (R3) — **GO**

`Core.Person` is a `Spark.Dsl.Fragment` folded via `use Samen.Resource, base: Core.Person` into two composed resources (Patient `pat`, Staff `stf`). Each composed resource is ONE physical table; the fragment has no table; fragment attributes inherit the composing resource's abbrev; `belongs_to` targets the composed table via a real FK. 15/15 tests green. No-`INHERITS` proven two ways: string scan of every migration + live DB `SELECT count(*) FROM pg_inherits == 0` with both tables `relkind='r'`, `relhassubclass='f'`.

- **Red path fail-closed (independently re-verified) — and this is the load-bearing finding for core:** Spark **silently unions** any fragment's declared extensions into the composing resource (`Spark.Dsl` ~line 332, `Enum.concat(fragment_extensions)`). S0.3 adds an explicit allow-list gate in `Samen.Resource` that refuses a fragment declaring an un-provided Samen extension (`Samen.Audit`). Neutering the gate made the rogue fragment compile and silently pulled `Samen.Audit` into the resource extensions — substantiating the finding. This gate **must carry into `samen_core` (A1)**; it is not optional polish, it is the safety story for fragment composition.
- **Implementation note:** the gate must use `Code.ensure_compiled/1` (not `ensure_loaded?/1`) — the fragment's `extensions/0` is only defined at its `@before_compile`, so `ensure_loaded?/1` races with compile ordering.
- **Scope note (disclosed, not a defect):** the `pii do` section is an S0.3 stub materializing a plain `sensitive?: true` column; the real vault split is S0.5. S0.3's acceptance (fragment PII attrs inherit the composing abbrev) is met.

### S0.4 — Catalog-in-migration-transaction (R4) — **GO, caveat named**

Mechanism decision: a `Samen.Migration` wrapper macro (`use Ecto.Migration` + `catalog_sync/1,2`), **not** a custom Ash codegen extension. Sound and honestly reasoned — the atomicity guarantee comes from Ecto's per-migration DDL transaction, not from codegen; forking `AshPostgres.MigrationGenerator` to interleave data rows is high-surface and would not by itself grant atomicity. Emitting the catalog `INSERT`s from the same `up/0` as the DDL is literally the doc's `BEGIN; ALTER…; INSERT INTO fld_field…; COMMIT`. 6/6 tests green.

- **Red path fail-closed (independently re-verified, and strengthened):** the anti-tautology probe (`@disable_ddl_transaction true`) makes the column survive the crash, flipping the red-path assertion as it must. The auditor added a stronger probe crashing **after** `catalog_sync` wrote the row and confirmed BOTH the column AND the catalog row roll back — so the catalog row is genuinely transactional (the spike's own red path raised before the write, so only the column-rollback half was load-bearing in-suite).
- **Caveat F1 (must-fix in core):** the guarantee rests entirely on the Ecto DDL transaction, which only exists under `@disable_ddl_transaction false` (default). Migrations that legitimately disable it (`CREATE INDEX CONCURRENTLY`, chunked backfills — plan K2 carve-outs) cannot use in-transaction catalog coupling. There is **no guard** in the spike's `catalog_sync` against `@disable_ddl_transaction true` — core must make `catalog_sync` refuse to run in that mode (fail closed) rather than silently write a catalog row outside a transaction.
- **Caveats carried forward:** F2 codegen should always scope the emitted `catalog_sync` call to the columns the migration changed; F3 the C1 `catalog_parity` verifier (S0.6) is the required backstop because the diff is driven by `Ash.Resource.Info` at compile time, not by the DDL text; F4 move to parameterized inserts once `tam_table`/`fld_field` are real Ash resources; F5 catalog tables are plain Ecto tables in the spike to dodge a bootstrap chicken-and-egg.

### S0.5 — Vault + KMS + crypto-shred + `%Masked{}` (R1/R6) — **GO WITH CAVEATS (mandatory fix)**

50 tests green, `--warnings-as-errors` clean. Implements ADR-001's Candidate A with dev stubs (`InMemory` + `FileBacked`) behind the `Samen.Kms` behaviour, proven against a shared conformance suite so the production `AwsKmsDynamo` adapter (T1.4) can be held to the same contract. **The load-bearing PITR claim is proven physically** (real `pg_dump` → shred → `psql` restore into a fresh DB; the restored ciphertext cannot decrypt because the key store was never in the dump; the strongest variant points the key store at an empty dir and confirms deny is driven by key-absence, not merely tombstone presence). Crypto is real AES-256-GCM AEAD. ADR-003 correctly rejects AshCloak (Cloak keys at vault/app-config level, no per-subject destruction lever → fails ADR-001 RQ2).

- **Red paths fail-closed (independently re-verified, non-vacuous):** sabotaging `FileBacked.shred/1` to a no-op made the PITR test catch plaintext leaking back after a real restore; sabotaging the outage guards and the `Masked` `to_string` each flipped their tests to FAIL; a planted second `Crypto.decrypt(` call site was caught by the structural single-chokepoint scanner. RQ5 (pseudonym rides the same DEK; one shred unlinks it) proven.
- **UNMET ACCEPTANCE CLAUSE (why the audit verdict is `partial`, and the mandatory fix):** plan row S0.5 explicitly requires the masked value **"renders `••••` in LiveView render."** `Samen.Masked` implements `String.Chars`, `Inspect`, and `Jason.Encoder` but **not `Phoenix.HTML.Safe`** — verified on disk (`spikes/s05_vault/lib/samen/masked.ex`), and there is no Phoenix/LiveView dependency and no LiveView render test in the spike. `Phoenix.HTML.Safe` has no `Any` fallback and no `String.Chars` delegation, so a HEEx `<%= @person.email %>` on a `%Masked{}` would raise `Protocol.UndefinedError`, **not** render `••••`. This is **fail-safe** (the raise discloses nothing — `%Masked{}` carries only token+label, never plaintext) but the acceptance clause is **untested and would not hold as implemented**. The report silently dropped the LiveView row from its status table rather than flagging it as uncovered. This does not make the audit refuted or the red-path claim false (the crypto/shred/PITR guarantees all hold and were independently verified) — so it is a **GO**, but the LiveView masking gap is a **mandatory in-phase fix** before this idiom is relied on, per the gate rule that a caveat must be named as a fix task.
- **Caveats carried forward:** oracle `:absent == FAIL` for post-shred is T2.9's job, not the adapter's (the adapters report `:absent` vs `:shredded` faithfully); the spike deliberately has NO plaintext-key cache (safer than ADR-001 §6) — if T1.4 adds the short-TTL in-memory unwrapped-DEK cache it must carry its own red path (shred/outage evicts/denies a warm cache); the `Crypto.decrypt(` structural scanner is a literal string match that an aliased module or a direct `:crypto` call could evade — the real AST/dataflow check is the C3 `pii_reads` verifier.

### S0.6 — Verifier harness + `catalog_parity` v0 — **GO**

The mix-task harness pattern is viable: `Samen.Verifier.halt_if_violations/2` calls `:erlang.halt(1)` directly so no cleanup hook can swallow the exit code, and `check/1` is factored out so unit tests can call it without triggering halt. `catalog_parity` checks both directions (physical columns via `information_schema` vs `fld_field` rows) via symmetric difference. 9/9 tests green.

- **Red paths fail-closed (independently re-verified):** neutering `check/1` to always return `[]` failed 7/9 tests including both red paths and both exit-code subprocess tests; disabling `:erlang.halt(1)` (print diagnostics but exit 0) failed exactly the 2 exit-code tests (observed exit 0, expected 1) while output text still printed — proving the exit-code assertion checks real process exit status, not just stdout. Exit-code layer uses `System.cmd/3` child processes, the only way to observe `:erlang.halt/1` codes without killing the test VM.
- **Caveat F1 (carry-forward backstop):** the verifier only checks tables present in `tam_table`; a whole physical table absent from `tam_table` (with an uncatalogued column) passes silently (empirically confirmed: ghost table invisible to both scopes). Core needs a complementary check: every `Ash.Resource.Info` resource appears in `tam_table`. F2 (allow-list for intentional shadow columns), F3 (`--repo` arg / discover from `:ecto_repos`), F4 (name the owning resource module in diagnostics) are lower-priority core polish.

### S0.7 — `pii_reads` AST verifier (R5) — **GO, caveat named**

A syntactic AST match (`Code.string_to_quoted` + `Macro.prewalk`, stdlib only, **zero deps**) over Ash sources is feasible and cheap: 9/9 seeded direct leaks caught (100%), 0 false positives (target `< ~1/50`), 3 laundered leaks documented as **expected misses** (a pure AST match sees an opaque local after a helper hop — laundering is the sink-schema allow-list's job, verifier J2, out of scope). 13/13 tests green. Fail-closed at both ExUnit and shell level (`mix pii_reads.verify corpus/leaks` → exit 1; parse errors also fail closed → never silently skipped).

- **Red paths fail-closed (independently re-verified, non-vacuous):** three mutations in scratch — disabling reveal-scope suppression, disabling field-read taint detection, and forcing the harness exit code to always 0 — each failed both RED PATH tests plus catch-rate/parse-error tests. The RED PATH meta-check proves the exit code is a function of PII presence via a discriminating pii/non-pii pair.
- **Caveat (undisclosed in the spike record; must-fix in C3 productionization):** the `reveal`-scope suppression is a **lexical name-prefix heuristic** — any function whose name **starts with `reveal`** suppresses ALL sinks in its body. `def reveal_report(c), do: Logger.info("ssn=#{c.pii_ssn}")` yields ZERO findings — a real false-negative evasion surface, and suppression propagates through nested closures/defs. This is consistent with a feasibility spike (acceptance is about direct-flow catch rate + declaration-site handling + honest laundered-miss disclosure, all met), but production C3 **must key on real Ash `action :reveal` introspection, not a lexical name prefix**, and should make the reveal boundary a first-class introspectable Ash attribute.
- **Also carried forward:** the registry is stubbed (real impl introspects `Ash.Resource.Info` over `pii do` blocks — walker contract unchanged); aliased sink modules (`alias Logger, as: L`) evade the spike (resolve from module context or rely on J2); the J2 sink schema allow-list is the named laundering backstop and is NOT implemented here. **NOTE:** the spike's `REPORT.md` could not be written (harness blocks subagents from writing report `.md` files); all report content is captured in the S0.9 spike record and the artifacts (walker, tests, corpus, task, `VERSIONS.md`, ci.sh wiring) are on disk and green.

### ADR-001 — Per-subject external-KMS key hierarchy — **SOUND / RATIFIED**

The ADR's contract (`generate_subject_key/unwrap/shred/attest/backups_disabled?/pseudonym` + attestation type) matches the implemented `Samen.Kms` behaviour exactly, and S0.5 proves its semantics physically (see above). The RQ1–RQ5 reasoning holds: RQ1 (key outside the app-Postgres WAL/PITR surface; a restore resurrects ciphertext, never the key) is structurally true because the wrapped DEK was never a Postgres row; RQ3 (O(1) master CMKs, O(subjects) pennies of DynamoDB) is viable at 10⁷; RQ2/RQ4/RQ5 are exercised by the shred/attest/outage/pseudonym red paths. Candidate A (DynamoDB, PITR off) over Candidate B (Vault transit named keys) is soundly argued — B strains RQ1 (Vault DR snapshots are a native practice that would resurrect a deleted key) and RQ3 (10⁷ named keys is outside transit's envelope); B is kept as the recorded fallback. ADR-003 (custom `:crypto` vault over AshCloak) is a correct consequence.

- **Tracked follow-ups (not blockers, already in the plan):** (1) the oracle must treat `attest/1` `:absent` as **FAIL** for post-shred assertions — a positive tombstone is required so a silently-dropped row cannot masquerade as a destroyed key (T2.9). (2) The PITR-off / no-backup invariant on the store is load-bearing and must be CI-asserted (oracle check 2, `DescribeContinuousBackups == DISABLED`) plus IAM deny + org SCP; a misconfiguration silently breaks RQ1 (T1.4/T2.9). Both are in ADR-001 §5–§8 and the plan; no new residue.

## Fallback designs (held in reserve — no idiom triggered a no-go)

All six idioms are GO; the following are the recorded fallbacks to activate **only if** a fix task above proves the mechanism unworkable in core (they are pre-designed so a future regression is not a re-architecture from scratch):

- **If the abbrev transformer's `:source` rewrite (S0.2/R2) ever fights AshPostgres codegen at scale** (e.g. a future AshPostgres release stops reading `attribute.source` verbatim, or an attribute-adding transformer can't be ordered before Samen's): fall back to explicit per-attribute `source:` set by a code generator rather than a runtime transformer (loses the "invisible" ergonomics but keeps prefixed storage), with the C2 `prefixes` verifier as the hard fail-closed gate. Escalation if even that fails: a custom AshPostgres data-layer shim mapping logical→physical names at query build time.
- **If fragment `base:` composition (S0.3/R3) can't safely fold PII/extensions in core:** fall back to explicit resource-level attribute duplication via a `Samen.Resource` macro that copies the shared attribute set into each composed resource at compile time (loses single-source-of-truth for shared shape but keeps single-table, no `INHERITS`), keeping the extension allow-list gate.
- **If catalog-in-migration-tx (S0.4/R4) can't be made fail-closed for the carve-out cases:** fall back to a post-migration `catalog_reconcile` step that runs `catalog_parity` (C1) as a fail-closed gate immediately after `mix ecto.migrate` in CI — trading strict atomicity for detect-and-fail-the-build on drift (the plan's stated R4 fallback: "a `Samen.Migration` wrapper macro that snapshots catalog diffs per migration," here degraded to reconcile-then-verify for `@disable_ddl_transaction true` migrations only).
- **If the per-subject external-KMS store (ADR-001/R1) proves unworkable on the first-choice store:** activate ADR-001's recorded fallback — **HashiCorp Vault transit named keys (Candidate B)** — accepting its RQ1 discipline (Vault snapshots excluded from the erasure-relevant restore surface) and RQ3 operating cost. The `Samen.Kms` behaviour makes this a pure adapter swap.
- **If `%Masked{}`-as-normal-value (S0.5/R6) can't fail closed through every Ash/LiveView/serialization path:** fall back to explicit per-field masked calculations + a default-deny field-selection policy (masking by omission at the query layer rather than at the value type), keeping the single decrypt chokepoint.
- **If the `pii_reads` AST verifier (S0.7/R5) produces a false-positive wall or unacceptable false negatives in core:** fall back harder onto the layered design's J2 backstop — make the **sink schema allow-list** (every span/wide-event field typed as a bounded ID/token/enum/number) the primary build-time gate and downgrade the AST layer to advisory, per the plan's accepted R5 mitigation.
