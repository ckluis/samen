# Theme: delivery-egress — ESP send-path protections, SSRF-proof outbound fetch, webhook delivery hardening, content-sanitization chokepoints

Sections owned: the Keila card in `00-01-executive-summary.txt`; Cluster 2 (SSRF egress) + the Mobilizon sanitize line in `07-08-communication-social-federation.txt`; ONLY Sequin's idempotency-key convention from `05-06-data-realtime-observability.txt`; ONLY Wanderer's webhook-hardening checklist from `08-09-quick-hits.txt`; ONLY Tymeslot's SSRF guard suite + credential re-encryption lines from `06-07-business-collaboration-saas.txt`. The passkeys/step-up cluster is identity-trust's; Sequin's backfill/Broadway/CDC material is ops-data's; billing-side idempotency is billing-metering's.

**Repo ground truth established first — the report's central "samen lacks X" claims for this theme are mostly stale.** Grep-verified against `~/Desktop/projects/samen` (branch `saas-readiness-phase-1`):

- **Suppression + bounce/complaint ingestion is FULLY BUILT** (T28/T30/T114, ADR-038 §4.3/§4.4). The Keila exec-summary card claims "no evidenced rate-limit or suppression-list logic" — half false. `Samen.Delivery.Chokepoint.send/2` (`samen_core/lib/samen/delivery/chokepoint.ex`) is the single send path and consults suppression BEFORE `deliver/2` (step 3 of its documented pipeline); a broken check fails CLOSED, an unwired check degrades honestly open. `Samen.Delivery.SuppressionCheck` backs it with the `dlv_suppression` kernel table (`suppression_check.ex`, `suppression.ex`). The feedback loop exists too: `Samen.Delivery.Deliverability` (`deliverability.ex`) consumes normalized `ProviderEvent`s from ESP webhooks, matches by `provider_message_id -> send receipt -> subscriber ref` (never by email address), records idempotent `dlv_email_event` rows (unique `{provider, provider_event_id}`, `email_event.ex`), and writes `:bounce`/`:complaint` into the SAME suppression store the chokepoint checks — plus DLQ on unmatched events, and consent-gated default-OFF open/click tracking. This is Keila's item 2 already built, with stronger privacy properties than Keila itself (Keila stores plaintext contact emails; samen matches token-blind).
- **Webhook egress hardening is mostly BUILT** (T19 lineage / plan T3.13). Wanderer's checklist (HMAC signing, backoff+jitter, retry caps, payload cap, circuit breaker) audits out at ~4/6 present: `Samen.Webhook.Signer` does HMAC-SHA256 over `timestamp.body` with `Samen-Signature: t=...,v1=...`, constant-time compare, and a stale-timestamp anti-replay verify helper with its own anti-tautology sabotage (`signer.ex`); `Samen.Webhook.DeliveryWorker` has per-event `idempotency_key` UUIDs with Oban `unique` (24h window), capped exponential backoff (`max_attempts: 20`, ~6h) into an operator-visible DLQ (`:discarded`), payload frozen at enqueue through the `show_fields` opt-in allowlist (`payload.ex` — fail-closed empty when no allowlist), and the signing secret vault-routed (`pii_pwh_signing_secret`, primitives blueprint). Missing residue: payload size cap, per-endpoint chronic-failure disable (Oban caps retries per JOB, nothing disables a dead ENDPOINT), endpoint-secret rotation overlap window, and the event id is not in the signed body for receiver-side dedupe (the automation webhook action DOES carry a stable `delivery_id` sha256 in its payload; B9 doesn't).
- **An SSRF guard exists — but only on ONE of the two tenant-URL egress paths, and without the pinned-connect layer.** `Samen.Automation.Actions.Webhook` (`samen_core/lib/samen/automation/actions/webhook.ex`, ADR-039 §5.3) has layers 1–2 of the Baudrate/vutuv three-layer shape: resolve-at-run-time + refuse loopback/RFC1918/link-local/`169.254.x.x`/`0.0.0.0`, https-required outside dev/test, an injectable DNS resolver seam, `:autoredirect` explicitly disabled on its dedicated adapter, and a bounded `ssrf_blocked` outcome enum (sabotage-able). What it lacks is layer 3: it checks the URL then calls `adapter().post(url, ...)` — a second, unpinned DNS lookup inside the HTTP client, the classic rebinding TOCTOU. Worse, `Samen.Webhook.DeliveryWorker` — the durable outbound webhook subsystem posting to org-registered endpoint URLs — has NO SSRF check at all (zero hits in `webhook/delivery_worker.ex`), and its default `Samen.Webhook.HttpAdapter.Httpc` uses `:httpc` defaults, which FOLLOW redirects (the automation action's moduledoc explicitly notes the shared B9 adapter does not set `:autoredirect` and declines to change it). No URL validation at endpoint registration either. Net: a tenant can register `http://10.0.0.1/...` (or a rebinding/redirecting host) as a webhook endpoint and receive server-originated, HMAC-signed POSTs against internal targets. This is the one real security defect this theme found.
- **Send-path throttling is genuinely ABSENT.** `grep -rn -i 'rate_limit|throttle|token_bucket|snooze'` over `samen_core/lib/samen/delivery/`, `scopes/marketing/`, `sequences/`, `notifications/` → zero hits; same for the three ESP adapter packages (`samen_postmark`/`samen_ses`/`samen_resend` — no 429/retry-after/throttle handling). Rate limiting exists ONLY at ingress (T103 auth surfaces; `Samen.Web.RateLimit` Hammer-backed auth+webhook ingress). Nothing governs outbound ESP throughput: a marketing fan-out (`Scopes.Marketing.SendWorker`, queue `:webhooks_out`) will exceed provider caps (SES 14/s-class limits) with no per-provider budget and no Oban-snooze-on-throttle. Keila's item 1 survives intact.
- **No tenant-authored HTML is rendered raw anywhere** — every `Phoenix.HTML.raw/1` in `samen_web` is a static inline SVG glyph (`ui/object.ex:218-245`, `ui/helpers.ex:100-117`); HEEx auto-escapes the rest; T111 shipped email-template escaping; and inbound external text already passes `Samen.Support.Inbound.Sanitize` (T111/T59 lineage, used by `mailbox/sync.ex`). Mobilizon's rich-text sanitize chokepoint has no consumer today.
- **Outbound idempotency keys are substantially present per-path**: webhook egress (UUID key + Oban unique), automation webhook (`delivery_id = sha256(workflow_id:event_id)`, stable across retries, carried in the signed body), deliverability events (unique `{provider, provider_event_id}`), marketing sends (send-row id as the idempotency key), Stripe usage batches (`Idempotency-Key` header + reconciler duplicate gate — per `parse-work/billing-metering.md`). Sequin's "convention" is already samen's practice; only a blanket verifier tier is missing, and its marginal value is low.

## 1. Adopt candidates (ranked)

### 1. SSRF-proof single outbound-egress guard (three-layer, pinned connect) + wiring the unguarded webhook egress
- **SaaS-foundry need**: every generated app inherits two paths that POST to tenant/org-supplied URLs — B9 outbound webhooks and the automation `webhook` action — plus named future consumers (Tymeslot-shaped BYO CalDAV sync, enrichment providers, link unfurls, agent web tools). One of the two live paths has no guard at all and follows redirects; the other has a check-then-connect rebinding window. Samen's own doctrine ("chokepoint-everything", one place to audit, AST-lock verifiers) demands exactly one guard module, not per-subsystem copies.
- **Sources**: vutuv `Vutuv.Ssrf` — `findings/078-vutuv.md` (**MIT** — importable reference, "worth porting close to verbatim"); Baudrate ADR-0007 pinned egress — `findings/062-baudrate.md` (AGPL-3.0, patterns only); Tymeslot SSRF guard suite (dns_resolution/private-IPv6/ip_normaliser/url_validation) — `findings/059-tymeslot.md` (AGPL-3.0, patterns only); Wanderer dispatcher checklist for the hardening riders — `findings/097-wanderer.md` (MIT).
- **License/MIT verdict**: vutuv MIT permits direct study/port with attribution; Baudrate/Tymeslot contribute clean-room ideas only. **Mode: adapt** (first-party module in samen_core; zero new deps — layers use `:inet` + the existing injectable-resolver seam the automation action already proved).
- **What to build**: (a) `Samen.Egress.Guard` in samen_core: layer 1 literal check (loopback/RFC1918/link-local/reserved/`169.254.169.254`/`0.0.0.0`, IPv6 equivalents + ip-normalization per Tymeslot — safe to call in a changeset at endpoint registration); layer 2 resolve-at-fetch (A/AAAA, injectable resolver — lift the automation action's `Resolver` behaviour up); layer 3 pinned connect — the HTTP adapter connects to the vetted IP and sets the Host header itself, no second lookup (TLS/SNI handling is the genuinely tricky part; this is why the item is opus); https-required outside dev/test; no redirect following (a redirect returns the Location for re-validation or refuses). (b) Wire it into `Samen.Webhook.DeliveryWorker`/`HttpAdapter` (today unguarded + redirect-following) and refactor `Automation.Actions.Webhook.ssrf_check/1` to delegate (keeping its `ssrf_blocked` bounded outcome). (c) Layer-1 validation at webhook-endpoint registration in the primitives blueprint (defense in depth; layer 2/3 still run at send time — registration-time-only checks are exactly the rebinding hole). (d) Verifier: extend the existing AST-lock style (`agent_coverage` raw-spawn lock precedent) to refuse direct `:httpc`/`Req` calls outside the named egress adapters. (e) Hardening riders on the same DeliveryWorker touch: payload size cap, per-endpoint chronic-failure disable (N consecutive job exhaustions flips the endpoint row inactive + operator notification — Wanderer's breaker, honest rather than retrying a dead endpoint forever), endpoint-secret rotation with a dual-secret overlap window, and include the `idempotency_key` in the signed body (receiver-side dedupe parity with the automation action's `delivery_id`). (f) Sabotage patches: neuter layer 2 → named rebinding test must fail; remove the endpoint-disable → named breaker test must fail. (g) Record Baudrate's bounded hostile-fetch walk (≤N hops, ≤M hosts, visited-URI cycle guard, target-host-keyed rate limits) as a design note in the guard's moduledoc for the day link-unfurl/agent web fetch lands — one paragraph, no build.
- **Effort**: M. **Maps to**: no G-number — a security defect the scan surfaced; nearest anchors ADR-039 §5.3 (the half-built guard), B9/T19/T3.13 (the unguarded subsystem), INV-4 (guard lands in core, adapters stay dumb), chokepoint doctrine + sabotage discipline.
- **Repo evidence it is missing**: `grep -rn 'ssrf|private_ip|169.254'` hits ONLY `automation/actions/webhook.ex` (+ its outcome enums); `webhook/delivery_worker.ex` and `webhook/http_adapter.ex` have zero URL/IP validation; `HttpAdapter.Httpc` passes no `:autoredirect` option (httpc default: follow); no `payload cap|circuit|breaker|rotate` hits in `samen_core/lib/samen/webhook/*.ex`; primitives blueprint webhook resource shows no URL constraint validation.

### 2. ESP send-path throttling at the Delivery Chokepoint (per-{org, provider} token buckets + Oban snooze)
- **SaaS-foundry need**: the moment any generated app wires a real ESP and a vertical sends at volume (marketing campaigns, sequences, notification digests), nothing prevents blowing provider throughput caps — burned sender reputation, hard 429 loops, and no per-tenant fairness (one org's campaign can starve every other org's transactional sends on the shared `:webhooks_out` queue). The suppression half of Keila's delivery defense is built; this is the missing throughput half, and it belongs at the ONE chokepoint all four send families already route through.
- **Source**: Keila `rate_limiter.ex` — `findings/070-keila.md` item 1. **License: AGPL-3.0 — patterns only, clean-room reimplementation** (consistent with samen's ash_ai/ash_admin posture).
- **Mode: adapt**. What to build: (a) token buckets keyed `{org_id, provider}` at second/minute/hour scales, most-restrictive-wins, limits from per-adapter config (each ESP package documents its provider's defaults; unconfigured = unlimited, honestly logged as such — no fake throttling); (b) consult in `Chokepoint.send/2` between suppression and deliver: on empty bucket return `{:error, {:throttled, retry_after}}` so the calling Oban worker snoozes rather than burning an attempt (Keila's consume-or-snooze, mapped onto samen's existing worker family); (c) persist bucket state across restarts (Keila's `persist/restore` — a small Postgres table, not ETS-only, consistent with samen's Postgres-pure posture); (d) map provider 429/throttle responses from the ESP adapters into the same snooze path (today all three adapters treat 429 as a generic error → retry storm); (e) sabotage patch: remove the bucket consume → named test proving a 100-send burst against a 10/s budget must fail. Per-sender identity granularity (Keila's unit) collapses to per-org in samen's model; a per-host global bucket guards the operator's own ESP account on top.
- **Effort**: M. **Maps to**: ADR-038 §4.3 (provider selection/config — the natural home for limits), the C2/T28 chokepoint contract, WS-C marketing depth. No existing backlog item covers it (T103 is ingress-only; grep of all 169 titles for `rate|throttle` → T103 only).
- **Repo evidence it is missing**: zero throttle/snooze hits across `delivery/`, `scopes/marketing/`, `sequences/`, `notifications/`, and all three ESP adapter packages (greps above); `Samen.Web.RateLimit` self-describes as auth+webhook ingress; the identity blueprint's one throttle reference (`identity/blueprint.ex:1274`) is the login-path Hammer counter.
