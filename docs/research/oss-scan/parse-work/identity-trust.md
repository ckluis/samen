# Theme: identity-trust — ADR-035 identity spine + operator trust plane

Sections owned: `00-01` (Boruta card), `07-08` (Cluster 1 passkeys/step-up only — SSRF cluster ceded to delivery-egress), `03-04` (Codex Pooler + CYFR trust-plane cluster — Neoharness ceded to agent-runtime, metadata-only logging ceded to ai-governance), `08-09` (Semaphore RBAC naming), `06-07` (nyght DB-backed RBAC line + Operately MCP OAuth).

**Headline repo-audit finding (the systematic-understatement error, this theme's instance):** the report's trust-plane cluster tells samen to adopt "HMAC-digest, show-once, non-recoverable token storage." Samen already does this everywhere a bearer secret exists — it is a documented, sabotage-tested invariant, not a gap. Evidence in §4. The genuinely-missing items are three: the OAuth/OIDC **provider** role, passkeys + a generalized post-login step-up gate, and version-pinned-consent/approved-vs-actual reconciliation on E3.

---

## 1. Adopt candidates (ranked)

### 1.1 `samen_oauth` — OAuth2/OIDC provider role as an adapter package (+ MCP OAuth grants as first consumer)
- **Need:** today samen only *consumes* OIDC (`assent`, Google reference IdP). Nothing lets a third party authenticate *against* a samen app: no "Sign in with <product>", no OAuth-scoped API access for tenant integrations (API keys are static bearer keys), no standards-grade grant surface for the MCP server. This is the explicitly deferred "become an OIDC provider" gap the exec summary names as one of four direct gap→project mappings.
- **Source:** Boruta Server (`findings/100-boruta-server.md`) — core `boruta` library: OpenID-Foundation-certified (Basic/Implicit/Hybrid + Config/Dynamic OP), RFC 6749/7662/7009/7636 (PKCE)/7521/7523/9449 (DPoP)/9126 (PAR), plus `wax_` WebAuthn in boruta_identity. Composes with Operately (`findings/058-operately.md`, Apache-2.0): MCP OAuth grants carrying `mcp:read`/`mcp:write` scopes defaulting to read-only, **one-grant-one-tenant binding** (tools structurally cannot take a tenant argument — same shape as samen's org-scoped-actor discipline), Client ID Metadata Documents (no pre-registration), connection dashboard with immediate revocation.
- **License:** Boruta Apache-2.0 → MIT-importable. Operately Apache-2.0 core → clean-room adapt (its ee/ slice untouched).
- **Mode:** **import** (rare) — vendor the core `boruta` library into a new `samen_oauth` package, path-dep on `samen_core`, matching the `samen_stripe`/`samen_anthropic` convention (INV-4: protocol deps stay out of core). Certified PKCE/DPoP/PAR/introspection correctness is exactly the "hard-won complexity" the import bar exists for. NOT the boruta-server umbrella (Phoenix 1.6, Nebulex/Shards/Quantum — see discards).
- **Build:** ADR first (fable): client/scope/consent resources mapped into Ash + vault + OrgScope; token issuance/introspection/revocation endpoints mounted via the two-plane router macros; operator-plane "API clients" surface; then MCP OAuth grants (default-read, single-tenant-bound, revocable) as the first consumer, upgrading the current static per-operator MCP tokens. Feeds G22 packaging.
- **Effort:** L (ADR + phased items per the decompose rule).
- **Maps to:** ADR-035 §A6 (consume-only posture; SAML "documented extension seam only", line 340); ADR-043 §11 MCP token shape; G22.
- **Repo evidence it is missing:** `grep -ri 'authorization_code|pkce|introspection|oauth2' samen_core/lib samen_web/lib` → zero provider-side hits (only verifier-introspection prose). `samen_web/lib/samen/web/auth/oidc_controller.ex` + `oidc.ex` are pure `assent` relying-party code. `spec/full-saas-readiness.md` has zero `oauth provider` mentions — not planned anywhere.

### 1.2 `wax_` passkeys + credential-scoped step-up reauth on the identity spine
- **Need:** ADR-035's auth ladder is password + TOTP + OIDC. No WebAuthn/passkeys; and step-up exists **only as the login-time 2FA interstitial** — no post-login fresh-auth gate on privileged actions.
- **Source:** three-project convergence (`findings/062-baudrate.md` AGPL, `findings/068-kammer.md` AGPL, `findings/078-vutuv.md` MIT) — all on `wax_`. Shared invariant: *passkeys are a faster return login, never a new root of trust* (enrollment behind an already-authenticated settings page; existing password/TOTP flow stays the bootstrap; Baudrate adds role-mandated 2FA for operator-class roles). Kammer details worth keeping: COSE keys stored opaquely, `sign_count` checked for clone detection, usernameless discoverable-credential flow feeding the *existing* login handler. Step-up: Kammer's framing wins over Baudrate's session-timestamp — `stepped_up_at` lives **on the token row** (elevation is a property of the credential that asked; dies with that token; cannot replay onto another device), 10-min window, elevation via passkey re-assertion or single-use email round-trip bound to the target token id.
- **License:** `wax_` library itself is importable (Apache-2.0 — re-verify at adoption); Baudrate/Kammer patterns are AGPL → clean-room only; vutuv is MIT (its `Vutuv.Credentials` wrapper is legitimately readable).
- **Mode:** **import** `wax_` (WebAuthn protocol/CBOR/attestation edge cases = hard-won complexity; lives in samen_web like `assent`/`nimble_totp`, never core) + **adapt** the step-up pattern natively.
- **Build:** (a) passkey enroll/login ceremonies on the spine, credential material through the vault write path like TOTP secrets, auth events into the existing login-family notifications; (b) generalize `Samen.Web.Auth.TotpStepUp` (T100's shared interstitial — the natural extension point, `samen_web/lib/samen/web/auth/totp_step_up.ex`) into a fresh-auth gate accepting TOTP or passkey, recording `stepped_up_at` on the session row; (c) wire trigger surfaces: reveal-grant approval, session revocation, DSAR export, crypto-shred initiation, break-glass open.
- **Effort:** M–L.
- **Maps to:** ADR-035 (spine); ADR-037 line 647 already records "ash_authentication 5.0 final (TOTP/WebAuthn tier)" as a re-evaluation trigger — this closes it first-party instead of waiting.
- **Repo evidence it is missing:** `grep -ril 'webauthn|passkey|wax_|fido'` over the repo → only ADR-037's re-evaluation note + an incidental pawchart test string. `grep -rn 'step_up|stepped_up|sudo' samen_web/lib samen_core/lib` → only the T100 login interstitial (`totp_step_up.ex`, `session_controller.ex:389-391`, `oidc_controller.ex:82-95`). `grep -rni 'reauth|fresh_auth'` on privileged surfaces → nothing; `break_glass` has no fresh-factor check.

### 1.3 Version-pinned consent + approved-vs-actual enforcement reconciliation on E3
- **Need:** E3 approvals approve an action *instance*; nothing records the *definition* that was approved, so "approved v1 of a tool/automation, executed v2" is structurally possible; and the join "this approval covered X; the run touched X and only X" is implicit (RunRecord has bounded outcomes but no reconciliation against the approval's scope).
- **Source:** CYFR (`findings/012-cyfr.md`) — Profiles as immutable consent revisions binding declared needs, grant a component line or pin a version, changed definition ⇒ old grant no longer covers it; Enforcements as per-execution immutable records of approved-vs-actually-executed. Codex Pooler (`findings/011-codex-pooler.md`) corroborates the trust-plane posture.
- **License:** CYFR's relevant subsystem (Sanctum) is FSL-1.1; Codex Pooler is Elastic-2.0 → **patterns only, clean-room**, never code.
- **Mode:** **adapt** — composition of subsystems samen already ships (E3 Gate + requester≠approver DB CHECK, RunRecord, hash-chained audit), not a new subsystem.
- **Build:** (a) hash of the `Samen.Automation.Action` / AI tool definition captured into the approval record at open; Gate fail-closes when the live definition's hash has drifted at execution time; (b) a reconciliation record (or audit event) minted at run finalize pairing approval id + approved definition hash + RunRecord outcome list, with a red-path proving an out-of-scope tool call is refused/flagged; (c) a verifier assertion (extend an existing tier rather than minting a new one) that every approval-gated run carries a reconciliation.
- **Effort:** M.
- **Maps to:** ADR-040 (E3), ADR-047 (RunRecord/agent loop), ADR-002 (audit chain).
- **Repo evidence it is missing:** `grep -rni 'hash|version|definition|pin' samen_core/lib/samen/approvals/` → no definition capture (only authz-scope comments); `run_record.ex` bounded-outcome allowlist (`@allowed_outcome_keys ~w(index kind status error_kind meta duration_ms)`) carries no approval linkage; `grep -rni 'tool_def|definition_hash|def_hash' samen_core/lib/samen/ai/` → only the chokepoint's `safe_tool_def?` static-shape check (egress safety, not consent pinning).

## 3. Explicit discards

- **Keycloak-delegated identity (Semaphore)** — value lives in outsourcing auth; samen's whole thesis is keeping vaulting/masking inside its own chokepoints (ADR-035, ADR-029/031).
- **boruta-server umbrella as a deployed sidecar IdP** — running a second stateful multi-node Elixir cluster (Phoenix 1.6, Nebulex/Shards, Quantum) duplicates capability samen reaches cheaper by importing the core library only.
- **boruta_gateway / microgateway / forward proxy** — perimeter enforcement duplicates samen's in-app chokepoint guarantees at a weaker layer.
- **OpenID4VCI/OpenID4VP/DID/EBSI wallet stack (Boruta)** — eIDAS vertical, no roadmap justification (ADR-032 US-only).
- **LDAP/AD federation (Boruta `:eldap`)** — plausible enterprise on-ramp someday, but no named gap or tenant demand; file with the SAML seam, don't schedule.
- **CYFR MCP stdio→HTTP bridge** — client-side complement; only relevant if samen ever *consumes* external MCP tools. Not on the roadmap.
- **Kammer three-tier config doctrine + first-run wizard; Codex Pooler DB-managed ETS/PubSub instance settings** — samen already has ADR-029 self-serve settings, feature_flags, an onboarding wizard, and env-driven fail-honest config; the residue is a settings-precedence doctrine paragraph, not a build. (Baudrate's setup-key claim gate belongs to the generator/ops theme.)
- **CYFR per-tenant execution concurrency caps** — cheap Oban-partitioning idea, but ADR-047 already has budgets/caps and a breaker; the concurrency-fairness sliver is a one-line note on ai-governance's proposed spend-governance item, not an identity-trust item.
- **Magic-link auth (Kammer), ueberauth (several)** — spine already has stronger equivalents; assent is settled.
- **Metadata-only AI logging (Codex Pooler)** — ai-governance's; their parse confirms it is already built (EG6).
- **SSRF/DNS-rebinding egress cluster (Baudrate/vutuv)** — delivery-egress theme's, not claimed here.

## 4. Annotation recommendations

- **CORRECTION to the assembled report (no backlog item): "adopt HMAC-digest show-once token storage" is ALREADY BUILT.** Every bearer secret in samen is digest-only or KMS-wrapped: emailed tokens (`samen_core/lib/samen/auth/token_mint.ex` — "at rest ONLY the SHA-256 digest", raw returned once); session tokens (`samen_core/lib/samen/auth/session_create.ex:60-74` — digest-only, show-once); tenant/operator API keys (`samen_web/lib/samen/web/settings/api_keys.ex` — "Show-once, digest-only (AC-G18-3, RP-ST-2)"); MCP tokens reuse the host's SHA-256-digest API-token lookup (`samen_web/lib/samen/web/ai/mcp_plug.ex:24-25`, ADR-043 §11 resolved); fleet credentials are KMS-wrapped via a deliberate second AEAD with constant-time compare + unknown-kid dummy-verify (`samen_core/lib/samen/fleet/crypto.ex`, `local_credential.ex`); webhook signing secrets are vault-encrypted and revealed only inside the delivery worker (`samen_core/lib/samen/webhook/delivery_worker.ex:10-11,46`). The `vault:NAME` indirection idea is likewise already samen's shape: secrets live as vault/KMS references resolved at the chokepoint, and automation's bounded 8-kind registry has no arbitrary-HTTP-header step to need it. Residual delta ≈ zero (keyed-HMAC vs plain SHA-256 over 32 random bytes is a non-issue). Recommend the final report flip this cluster from "adopt" to "external validation of an existing invariant."
- **T84b / T155 (cockpit + tenant AI surface):** add the per-key Observatory read-scope (candidate 1.4) as a line item — a key-scoped usage projection over existing wide-event/metrics data; policy-gated read model + LiveView only, no new instrumentation. Source: findings/011-codex-pooler.md (pattern only, Elastic-2.0).
- **G28 gap-register entry (`docs/saas-gap-roadmap.md:82`):** annotate with the settled design references so the eventual build starts warm — Semaphore's org/project role naming + additive-groups tiering (findings/092), nyght's role/permission/resource/role_policy table shape (findings/057, clean-room), Bonfire Boundaries for resolution semantics (other theme). Note T146/T84a already shipped the enforcement spine it plugs into.
- **ADR-037 (line 647 re-evaluation trigger):** if proposed item 5.2 lands, record that the WebAuthn tier arrived first-party via `wax_`, closing the "wait for ash_authentication 5.0" trigger.
- **ai-governance's spend-governance draft item:** one-line addition — per-org agent-run *concurrency* cap (CYFR, findings/012) alongside the cost dimension, expressible with existing Oban queue partitioning.
