# 026 — Symphony (OpenAI)

## What the project is

Symphony is OpenAI's experimental "software factory" orchestrator (Apache-2.0, ~26.8k stars, explicitly "a low-key engineering preview for testing in trusted environments"). It is a long-running service that continuously polls an issue tracker (Linear, GitHub Issues, Jira Cloud, Asana, GitLab), creates an isolated per-issue filesystem workspace, and runs a coding-agent session (Codex in App Server mode in the reference implementation, but the spec is agent-agnostic) inside that workspace until the issue leaves an active state. Agents provide accountability via CI status, PR review feedback, complexity analysis, and walkthrough videos; on acceptance they land the PR. The repo ships two things:

1. **SPEC.md** — a language-agnostic formal spec: normalized `Issue` entity, repository-owned `WORKFLOW.md` (YAML front matter + Markdown prompt template), per-issue workspace with `after_create`/`before_run`/`after_run`/`before_remove` shell hooks, a claim state machine (`Unclaimed → Claimed → Running → RetryQueued → Released`), run-attempt states (`PreparingWorkspace → … → Succeeded | Failed | TimedOut | Stalled | CanceledByReconciliation`), exponential-backoff retries, stall detection (default 5 min), strict prompt rendering (unknown variables/filters MUST fail), single-authority serialization of claims, restart recovery without a database (re-poll tracker + reuse persisted workspaces), and an optional HTTP observability API (`/api/v1/state`, `/api/v1/<issue>`, `/api/v1/refresh`).
2. **`elixir/` reference implementation** — OTP supervisors per agent lifecycle, GenServers for polling/state, Phoenix LiveView dashboard + Bandit, Burrito for self-contained executables, hot code reloading without stopping running subagents, provider-native adapter tools (`linear_graphql`, `github_api`, `jira_rest`, …) executed host-side with tracker tokens stripped from the agent child environment, and live E2E test scenarios per tracker (including Docker-Compose SSH-worker tests).

Trust boundary is intentionally implementation-defined; defaults are fail-closed (`approval_policy` defaults to reject sandbox approvals, rules, and MCP elicitations; blocked runs stay claimed and surface as "blocked" in state/API/dashboard).

## What samen could adopt

- **Tracker-driven orchestrator service for the `_orch/` loop** — What: replace/augment samen's session-driven autonomous loop (backlog.yaml + per-task handoffs run inside Claude Code sessions) with a supervised BEAM service that polls the backlog, claims one item, prepares a workspace, runs the agent, and reconciles on state change — per Symphony's poll/claim/dispatch/reconcile cycle. Why it fits: samen is Elixir-native and its dev loop already IS this shape, just manually cranked; Symphony proves the OTP idioms (one GenServer authority for claims, supervisor-per-run, restart recovery by re-polling source-of-truth + persisted workspaces, no extra DB) that would let the BATON-style burn-downs run unattended between human phase gates. Effort: L (a real service; could start as a thin `mix samen.orch.tick` that implements just poll→claim→dispatch against backlog.yaml — M for that slice).
- **Claim + run-attempt state machines with distinct terminal reasons** — What: adopt the spec's five claim states and the `Succeeded/Failed/TimedOut/Stalled/CanceledByReconciliation` terminal taxonomy for samen's ADR-047 agent-loop runs and ADR-039 automation `RunRecord`. Why: samen already has a bounded-outcome allowlist on RunRecord; Symphony's taxonomy adds two outcomes samen's digest doesn't name — *stalled* (no events within a timeout) and *canceled-by-reconciliation* (source state changed underneath the run) — both directly applicable to durable agent turns and automation runs. Effort: S.
- **Stall detection + continuation retry** — What: terminate silent agent sessions after `stall_timeout_ms`, and after every *normal* worker exit schedule a short continuation retry that re-checks whether the work item is still active. Why: samen's agent loop has budgets/cost caps but the digest shows no liveness watchdog; "agent went quiet" is the classic failure mode of long tool-use loops, and the continuation-retry trick catches "agent exited but the item isn't actually done". Effort: S–M (Oban job + last-event timestamp on the run record).
- **Host-side credential execution / env-stripping for agent children** — What: adapter tools run with configured host-side auth, and declared tracker-token env vars are removed from the agent subprocess environment. Why: this is samen's chokepoint philosophy applied to *process boundaries* — same spirit as the EG2 governed-egress class; worth encoding as a verifier-style rule for any place samen spawns external agent/CLI processes (e.g. gen.agent scaffolds, ops scripts). Effort: S.
- **Repository-owned WORKFLOW.md with strict rendering + hot reload** — What: version-controlled workflow file (YAML config + prompt template) where unknown variables/filters fail rendering, and config edits re-apply at runtime with invalid reloads keeping last-known-good + emitting errors. Why: samen's Prompt resource + runtime catalog grounding pair naturally with "unknown variable MUST fail" (fail-honest for prompts) and last-known-good semantics for automation/agent definitions edited by operators. Effort: S for the strict-rendering rule on samen's prompt templating; M for live reload semantics.
- **Blocked-state surfacing** — What: when a run blocks on approval/elicitation, keep it claimed and expose it as `blocked` in runtime state, JSON API, and dashboard. Why: samen's E3 approvals engine already gates AI side effects; the missing piece Symphony demonstrates is making "waiting on approval" a first-class, operator-visible runtime state (fleet cockpit / operator plane widget). Effort: S–M.
- **Workspace lifecycle hooks with per-hook failure semantics** — What: `after_create` (abort on failure), `before_run` (abort attempt), `after_run`/`before_remove` (log + ignore), all timeboxed; collision-resistant sanitized workspace names (hash suffix, ≥64 bits entropy, must stay inside workspace root). Why: directly reusable for samen's generative CI probes and any future orchestrated runs; the sanitization rule rhymes with samen's abbrev collision discipline. Effort: S.
- **Minimal observability API shape** — What: `GET /api/v1/state` (running sessions, retry queue, token totals, rate limits) + per-item endpoint + `POST refresh`. Why: a clean, tiny contract for exposing agent-loop/automation runtime state on the operator plane and the fleet report wire (token-blind by construction fits samen's aggregate rules). Effort: S.

## What to ignore and why

- **The Codex app-server protocol coupling** — samen's AI plane is provider-behaviour-based with a chokepoint-minted `%MaskedPayload{}`; adopting Codex's session/turn wire protocol buys nothing and violates INV-4's vendor-free-core spirit. The spec itself says to treat the app-server protocol as external documentation, not part of Symphony.
- **Using Symphony as a dependency or running it as-is** — it's a preview "for trusted environments", trust boundary intentionally undefined, no built-in review gate; samen's discipline (285-sabotage harness, adversarial phase gates, human GO/NO-GO) is stricter than anything Symphony provides. Mine the spec, don't mount the service.
- **Tracker adapters (Linear/Jira/Asana/GitLab)** — samen's backlog is file-based (`_orch/backlog.yaml`) by deliberate convention; multi-tracker adapters solve a problem samen doesn't have. If a tracker ever matters, the adapter *boundary* (two required read ops, normalize-or-null best-effort metadata) is the part to copy, not the adapters.
- **Auto-merge of accepted PRs** — contradicts samen's operator-gated BATON/phase-gate process; human adversarial gates are the moat, not overhead to automate away.
- **Burrito self-contained executables / Phoenix dashboard as-is** — samen distributes in-monorepo (ADR-033) and already has a first-party operator plane; no need for a separate dashboard app.
