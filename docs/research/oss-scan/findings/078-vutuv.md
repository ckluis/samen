# What the project is

Vutuv is a self-hostable, federated (ActivityPub) professional/social network — pitched as "the LinkedIn of the Fediverse," an open-source alternative to LinkedIn/Facebook/X. It is a single Elixir/Phoenix 1.8 application (Bandit, LiveView, PostgreSQL via Ecto, Tailwind v4, libvips for images) with a bilingual (German/English) UI, a reference production install at vutuv.de. It is **not** built on Ash — it's straight Ecto/Phoenix with ~90 top-level `lib/vutuv/` context modules. Created 2016, still under active daily development (1,248+ commits on `main`, last push within the day of this scan, 26 open issues, MIT license). Feature surface: member profiles with work/education history, follows/likes/reposts/DMs, verified organization pages (domain-ownership proof), a job board, CV export (PDF/Word/OpenDocument/LaTeX/JSON Resume), passwordless auth (email PIN, passkeys, TOTP), GDPR data export/deletion, a moderation strike ladder, local Ollama-based AI image moderation, webhooks/OAuth for third-party apps, and blue/green zero-downtime deploys onto bare-metal systemd/nginx.

The product domain (consumer social network with federation) has essentially nothing in common with samen (multi-tenant B2B SaaS foundry). The value here is entirely at the subsystem level: several of vutuv's modules are hardened solutions to problems samen's digest lists as open gaps or under-specified areas.

# What samen could adopt

- **DSAR self-serve export pattern (`Vutuv.Export`), for samen's open G19 gap.** Vutuv's `Export.build/1` is a single, owner-only, schema-versioned (`@schema_version 9`, with an inline changelog explaining every version bump) function that walks every per-user subsystem and assembles one JSON-encodable map — comments explicitly tie it to GDPR Art. 20 and require it stay in lockstep with `delete_user/1` ("when a new per-user subsystem lands, add its section here, the same way `delete_user/1` must learn to delete it"). Samen's G19 (DSAR self-serve export + retention admin) is explicitly open/P2. This is a directly transplantable design: a single versioned export-registry module, paired with a test that fails when a new PII-bearing resource is added to the catalog but not to the export. Given samen already has a machine-readable catalog and per-resource `pii_declared` metadata, the catalog could auto-derive most of the export instead of hand-listing associations. Effort: M.
- **WebAuthn/passkey login as a second first factor, filling a real gap in ADR-035's identity spine.** Samen's digest lists TOTP (`nimble_totp`) + OIDC (`assent`) but no passkeys. Vutuv's `Vutuv.Credentials` wraps `wax_` (~> 0.7) cleanly: it builds relying-party config from the endpoint URL (dev signs `localhost`, prod signs the real domain), and — the important discipline — passkey enrolment is explicitly *not* a root of trust: it lives behind an already-authenticated settings page, and the existing PIN/password flow stays the only way to bootstrap an account. That "passkey is always a faster return login, never the account root" rule is exactly the kind of invariant samen's identity spine already applies to TOTP step-up and would slot in the same way. Same `wax_` + `eqrcode` combo (eqrcode already used for TOTP QR) is directly reusable. Effort: M.
- **SSRF hardening for every outbound fetch of a user-supplied URL (`Vutuv.Ssrf`), applicable to samen's webhook/delivery/AI-egress chokepoints.** Three explicit layers, each solving a different threat: (1) `internal_host?/1` — literal-only (no DNS) check safe to run inside a changeset, rejecting localhost/private/link-local ranges and the cloud metadata IP `169.254.169.254`; (2) `resolves_to_internal?/1` — resolves A/AAAA at fetch time to catch DNS rebinding (a public hostname whose record points internal), called out as closing a gap the literal check cannot; (3) `vetted_address/1` — resolves once and pins the fetcher to that exact IP so there's no second lookup for an attacker to poison (used to drive a Chromium screenshot capture through a loopback SOCKS5 proxy that dials only the vetted address, covering redirects and in-page navigation). The resolver is injectable for deterministic tests. Samen's fail-honest adapters and `Samen.Delivery.Chokepoint`/webhook fleet-wire paths take operator- or tenant-supplied URLs (webhook subscriptions, org verification, fleet heartbeat endpoints per ADR-044) but the digest doesn't mention SSRF-class defense; this is a small, self-contained module worth porting close to verbatim. Effort: S–M.
- **Account-activity log as a member-facing companion to the hash-chained audit log.** `Vutuv.AccountEvents` is a different, complementary layer to samen's ADR-002 audit chain: it's explicitly member-facing ("was that me?"), enforces its privacy budget structurally rather than by discipline — `@kinds` is the *whole* vocabulary, each kind declares exactly which `details` keys it may carry, the changeset rejects anything else, and a test fails the build if any declared key name looks like a credential — and makes two deliberate minimalism calls worth stealing as conventions: no IP address stored (device summary + time + confirming factor answers "was that me" without building a movement profile), and emails are stored pre-masked (`an***@example.com`) rather than relying on read-time masking. `record/3` is best-effort (a log write must never break the action it records) and reads come from one shared query builder for both the member's own page and the admin cross-member view — the admin read itself logs an `"activity_log_viewed"` event on the *admin's* account. Samen's audit chain is tenant-readable and hash-chained (append-only, stronger tamper-evidence than vutuv's), but the "declared-vocabulary + build-fails-if-a-key-looks-like-a-secret" test pattern and the masked-at-write convention are cheap, concrete additions on top of what samen already has. Effort: S.
- **Real bilingual i18n + timezone/locale rendering, as a working reference for samen's open G24 gap.** Vutuv ships `gettext`, `ex_cldr`/`ex_cldr_territories` (compile-time territory data, explicitly called out as "no runtime network → intranet-safe"), `ex_phone_number` (E.164 parse/format, locale-aware national rendering), and `tz` for the IANA timezone database compiled into the release (`Vutuv.ViewerClock` renders every timestamp in the viewer's own zone via `DateTime.shift_zone/2`) — with the periodic tzdata updater deliberately *not* supervised, because a tzdata refresh ships with the next vutuv release rather than phoning home at runtime. Samen's G24 is explicitly open (USD+UTC hardcoded, no gettext); vutuv is a working, production-proven reference for exactly this slice (gettext + cldr + tz), including the "no runtime network" constraint samen's air-gapped/intranet-friendly posture would also want. Effort: L (full i18n is a genuine cross-cutting change — likely its own ADR + phased items per samen's decompose-cross-cutting-changes rule).
- **Blue/green zero-downtime deploy script, as a concrete pattern for samen's operator-TODO Fly production deploys.** `scripts/deploy.sh` is a well-commented, ~small bash script: builds a release, runs migrations, boots the idle slot, health-probes it, atomically rewrites the nginx upstream snippet, drains, stops the old slot — with an explicit invariant that migrations must be backward-compatible while the old release still serves against the migrated DB, a `flock`-based single-deploy lock, and careful cleanup-on-abort logic (a killed deploy must not orphan a BEAM node holding a DB pool). Samen's Fly production deploys are listed as human-gated/operator-TODO; this isn't Fly-specific but is a clean worked example of the invariants a generated samen app's real deploy path needs to satisfy (backward-compatible migrations, health-gated cutover, single-flight lock). Effort: S to read as a reference, M if adapted into a `mix samen.gen.app`-emitted deploy script.
- **Deliverability/bounce tracking as a pattern for samen's ESP adapters.** `Vutuv.Deliverability` funnels hard-bounce signals (log watcher + DSN webhook) through one `record_hard_bounce/3`, appends to a bounce ledger, marks the specific address undeliverable, and only freezes the *account* after repeated failures or a grace period — auto-thawing on a successful login PIN. Samen's `samen_postmark`/`samen_ses`/`samen_resend` adapters are listed as fail-honest (return `:not_configured`/`:not_implemented` rather than fake success) but the digest doesn't mention bounce-driven deliverability state; this is a small, well-isolated ledger-plus-reassessment pattern that would fit as an optional `samen_core` capability the ESP adapters feed into. Effort: M.

# What to ignore and why

- **The entire product surface**: profiles, follows/likes/reposts, DMs, job board, CV export, organization pages, posts/feed, mentions — none of it transfers; samen is a B2B multi-tenant SaaS substrate, not a social network.
- **ActivityPub/Fediverse federation** (`Vutuv.Fediverse`, `Vutuv.Mastodon`, `Vutuv.NodeInfo`, Bluesky bridging): solves a problem samen doesn't have (samen tenants are not publishing to a federated social graph).
- **Moderation strike ladder / content freezing / reporter trust scoring**: a UGC-abuse problem specific to open social platforms; samen has no analogous surface today.
- **Not Ash-based at all** — no Ash, Ash.Resource, or Reactor usage anywhere in the dependency list or module inventory; none of vutuv's resource/authorization patterns are directly comparable to samen's Ash-blueprint or policy-SAT architecture, so there's nothing to borrow at that layer (the value is entirely in the standalone-library-wrapper modules listed above, which don't touch Ash either way).
- **Single-node rate limiter (`Vutuv.RateLimiter`, ETS-based)**: explicitly documented by vutuv itself as "not a distributed quota" — strictly weaker than samen's already-adopted `ash_rate_limiter` + Hammer combination (ADR-037), which the digest says is already pinned and narrow. No upgrade here.
- **Ads/job-board/CV-export subsystems, newsletters, Bluesky bridging, cologne-phonetics/soundex name search**: domain-specific consumer-social features with no SaaS-foundry analog.
- **Legal-pages-as-admin-editable-Markdown**: a German-Impressum-law-specific compliance need; samen's compliance posture (`docs/compliance-story.md`) already covers GDPR/SOC2 control posture at a different, more general level.
