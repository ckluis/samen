## What the project is

Wanderer ("#1 EVE Online Mapper") is an actively developed (pushed within the last day, 75 stars, MIT) Elixir/Phoenix/Ash application that lets EVE Online players collaboratively map wormhole space in real time. It ships as a dual-distribution product exactly like the model samen's fleet cockpit envisions: a free, self-hosted "Community Edition" (separate `community-edition` repo with install docs) and a paid, EU-hosted "Wanderer Cloud" SaaS with per-map subscriptions and bot licenses. Backend is standard Phoenix + `ash` 3.9 + `ash_postgres` + `ash_json_api` + `ash_phoenix`; the interactive map canvas is a React SPA talking to the backend over JSON:API and SSE/websockets, with Phoenix LiveView used for surrounding admin/settings surfaces. Deploys to Fly.io (`fly.toml` present), with buildpack and Docker paths too. Real-money subscriptions gate map features (kill tracking bots, SSE/webhook delivery) via an external license-manager microservice.

Category is correctly tagged "Games" and the domain (EVE Online SSO, ESI API integration, wormhole routing, killmail feeds) has zero transferable value to samen's B2B SaaS-foundry mission. What's relevant is purely infrastructural: this is a real, live, revenue-generating Ash/Phoenix app making production decisions samen also has to make (encryption-at-rest, licensing/entitlements, webhook delivery, real-time authz, error tracking, release automation) — a useful "how did another serious Ash shop solve this" cross-check.

## What samen could adopt

1. **Cloak dual-key (primary + fallback) rotation pattern** — `WandererApp.Vault` (`lib/wanderer_app/vault.ex`) configures `Cloak.Vault` with a `default` cipher plus a `fallback` cipher, each keyed from a separate env var (`CLOAK_KEY` / `FALLBACK_CLOAK_KEY`). Decrypt tries the current key, and falls back to the old key on `:error`, letting an operator rotate the encryption key without a synchronous re-encrypt-everything migration. Samen deliberately rejected AshCloak/Cloak for the PII vault itself (ADR-003 — needs per-subject external-KMS keys and crypto-shred, which Cloak's static app-wide key can't give), but samen's own `Samen.Kms` behaviour and file-backed KMS sim don't yet document a *key-rotation-with-fallback-window* story. This pattern is worth porting at the KMS/master-key layer (not the per-subject vault layer). Effort: **S**.

2. **External license/entitlement service pattern** — `WandererApp.License.LicenseManager` + `LicenseManagerClient` (`lib/wanderer_app/license/`): a local DB row (`License` resource: `lm_id`, `license_key`, `is_valid`, `expire_at`) mirrors state from an external microservice that owns subscription truth; validation checks the external service but degrades to the local record's cached validity if that call fails, and license creation is driven off an internal `SubscriptionManager.get_active_map_subscription/1` check. This is a concrete, working answer to exactly the shape of gap samen has flagged as open: G13's `Stripe SyncAdapter.Stub` and the tenant-lifecycle entitlement editor. Worth reading closely when samen wires a real Stripe sync — specifically the local-cache/fail-open-vs-fail-closed split between "can't reach billing" and "billing said no." Effort: **M**.

3. **Webhook dispatcher hardening checklist** — `WandererApp.ExternalEvents.WebhookDispatcher` (GenServer + `Task.Supervisor`) implements: HMAC-SHA256 request signing, exponential backoff with ±25% jitter (base 1s, cap 60s), a hard 3-attempt retry ceiling, a 1MB payload cap, and a consecutive-failure counter (10) that presumably disables a broken subscription rather than retrying forever. Samen's `samen_web` already has a `webhook` surface (per the digest) — this is a good diff-checklist to verify samen's webhook egress has the same hardening (signing, backoff+jitter, payload caps, circuit-breaking on chronically-failing endpoints), which the digest doesn't explicitly claim it has. Effort: **S** (audit + patch gaps, not a rewrite).

4. **Cache-first authz on the real-time hot path** — `WandererApp.ExternalEvents.SseAccessControl.sse_allowed?/1` checks, in order: (a) global config flag (no I/O), (b) per-map cache (no DB), (c) subscription-active cache-or-CE-skip (no DB) — explicitly designed so per-event SSE fan-out never round-trips to Postgres. Samen's chat (cross-plane realtime) and MCP HTTP+SSE server are the analogous hot paths; worth confirming samen's masking/authz chokepoint on those is similarly cache-fronted rather than re-querying org-scope/policy per event at high fan-out. Effort: **S**.

5. **Self-hosted, in-house error tracking (`error_tracker` lib)** instead of a third-party APM/Sentry — a Postgres-backed error store that never leaves the deploy. This fits samen's own INV-4 (vendor-free core) and PII-non-egress ethos better than piping stack traces (which can contain masked tokens or org identifiers) to an external SaaS. Worth evaluating as an optional samen_web observability adapter alongside the existing OpenTelemetry setup (which samen already disables `db_statement` on for the same reason). Effort: **S**.

6. **`git_ops` + `version_tasks` conventional-commit → CHANGELOG/version automation** — Wanderer auto-generates `CHANGELOG.md` and bumps its release version from conventional-commit messages. Samen already tracks ADRs and gate reports by hand; this could reduce the mechanical overhead of keeping a public CHANGELOG in sync with the ~105-task autonomous backlog, especially since samen is now a public repo evaluators read. Effort: **S**.

7. **Nix flake + devcontainer dual onboarding path** — Wanderer ships both `flake.nix`/`default.nix` and a `.devcontainer/` with a `setup.sh` that fetches deps, migrates the DB, seeds reference data, and builds client assets automatically on first container create. Samen documents a pinned Elixir 1.20/OTP 29 toolchain but (per the digest) doesn't mention a one-command reproducible dev environment; either a Nix flake or a devcontainer would lower friction for the "published so the architecture is legible" goal (external readers can `nix develop` or reopen-in-container instead of hand-installing the toolchain). Effort: **S–M**.

## What to ignore and why

- **AshCloak/Cloak itself as a PII mechanism** — Wanderer uses it for simple field-level encryption with a single rotating app key. Samen already evaluated and explicitly rejected this exact library for its PII vault (ADR-003) because it can't do per-subject keys or true crypto-shred erasure; nothing here reopens that decision, only the fallback-key *rotation idea* (item 1 above) is separable and worth taking.
- **The React SPA map-canvas architecture** — bespoke, domain-specific interactive-graph UI (wormhole system nodes/connections) with no transfer value to samen's function-component/LiveView-first UI kit philosophy.
- **EVE SSO / ESI integration** (`esi.ex`, `eve_data_service.ex`, custom `ueberauth/` strategy, `phoenix_gen_socket_client` killmail feed consumer) — entirely EVE-Online-API-specific; samen's identity spine already covers the generic OIDC/TOTP surface these would never generalize to.
- **Bitmask RBAC (`WandererApp.Permissions`)** — a compact, additive bitwise-OR role model (viewer ⊂ member ⊂ manager ⊂ admin) for per-map ACLs. It's simpler than samen's OrgScope + policy SAT-solver approach, but also strictly less rigorous (no fail-closed-on-org-less-actor guarantee, no formal verification story) — adopting it wholesale would be a regression for samen's trust kernel. Only worth a glance if samen ever needs a lightweight *object-level* (not org-level) sharing/ACL primitive on top of the existing policy layer.
- **Game-domain resources** (`map`, `character`, `structures`, `kills`, `route_builder_client`, `changelog`/`blog` content models) — fully domain-specific, no generic scope-blueprint value.
- **`nebulex`/`cachex`/`merkle_map`/`pathex` combo** used for in-memory map-state caching and diffing — tuned for Wanderer's specific real-time graph-sync problem (systems/connections diffing across many concurrent viewers of one map); not a generalizable pattern for samen's Oban/PubSub-based architecture without a matching problem shape.
