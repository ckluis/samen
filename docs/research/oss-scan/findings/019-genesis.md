# 019 — Genesis (EMI-Group)

## What the project is

Genesis ("EvoX Genesis", core app `evo_git`, lineage: EvoGit → Genesis) is an **Elixir ~1.18 / OTP 29 umbrella app** (apps: `evo_git` runtime + `evo_dash` Phoenix dashboard at `localhost:4100`) that runs **long-horizon autonomous software development**: transient LLM agents are spawned in recursive hierarchies (Manager → Executor/Investigator/Architect, observed depth 4–5), each works in an isolated **fresh git worktree**, and only validated results advance the repository's "accepted version" lineage — the git repo is the sole persistent state. Ships as a native desktop app (macOS/Linux/Windows), AGPL-3.0, CLA required, paper at arXiv:2608.10450. Headline demos: a 248,989-line Rust C compiler built from an empty repo in 123.4 h for $44.38 (DeepSeek V4 Flash; 220/220 c-testsuite), and a 139k-line Fortran (MESA) → 90k-line Rust redevelopment with checksum differences ≤ 3.1e-9. Small community footprint (38 stars) but very active (5,314 commits) and the internal `CONTEXT.md` docs reveal unusually mature OTP engineering.

Category fit: it is a **software factory / meta-development tool**, not a SaaS substrate. Zero overlap with samen's actual product surface (no multi-tenancy, no PII governance, no billing/identity/audit). Its relevance is to (a) samen's first-party agent loop (ADR-047) and (b) samen's own autonomous development process (`_orch` loop).

Shared philosophy worth noting: Genesis's core rule — "agent outputs are proposals; only accepted results advance the persistent lineage" — is the same stance as samen's "AI writes do not exist; side effects go through the E3 approvals engine." Independent convergence, which is itself validating.

## What samen could adopt (patterns, not code — AGPL)

1. **Per-model LLM concurrency slot pools with peak-hour scheduling.** Genesis gates every LLM call through a scheduler-owned slot pool: per-model capacity from config profiles, agents block in `:infinity` GenServer calls when saturated, runtime capacity changes merge live holders/waiters without drops, and a `PeakHourEngine` GenServer swaps capacity per IANA-timezone windows (explicit 0 = hard pause, in-flight holders never evicted). *Why it fits:* ADR-047 has budgets/cost caps but (per the digest) no per-model concurrency or time-windowed throttling; this is the natural next layer for fleet-scale agent runs and provider rate-limit hygiene, and it composes with samen's existing chokepoint (gate the slot before minting the MaskedPayload). *Effort: M.*

2. **Graceful cancellation with bounded "grace turns" + auto-commit recovery.** Cancel path: mark `:cancelling`, inject a cancel message into the agent's pending queue, give the agent **3 full LLM+tool turns** to wind down, with `maybe_recovery_auto_commit` saving worktree state first; force-kill is a separate path that persists `:failed` (never `:cancelled`), so terminal statuses stay honest. *Why it fits:* durable multi-step agent runs (ADR-047) need operator-initiated stop that preserves transcript/draft state for the approvals surface; the "graceful = `:cancelled` with result, forced = `:failed` with nil result" distinction matches samen's fail-honest discipline exactly. *Effort: S–M.*

3. **Mid-run message injection into the agent loop.** A scheduler-writable `pending_user_messages` queue drained at the top of each turn and appended as turn-tagged user messages — clean operator steering of a running agent without restart. *Why it fits:* samen's operator plane will want "nudge the running agent" UX; the injection point (after context compression, before the turn) is the right seam and trivially fits samen's loop, with the re-scrub applied at injection since it becomes governed egress (EG2). *Effort: S.*

4. **Monitor-driven workspace reclaim.** `WorktreeManager` GenServer does `Process.monitor(agent_pid)` and on any `:DOWN` idempotently destroys the worktree/branch (rm_rf → prune → delete_branch), with crash-during-setup recovery via `pending_cleanup` and per-agent request serialization; no pool, every run gets a fresh worktree. *Why it fits:* any samen agent tool that materializes scratch state (export staging, generated-app probes, file-quarantine workspaces) should be reclaimed by monitor, not by cron sweep — this is the OTP-native version of samen's lease/cleanup instincts. *Effort: S–M as a pattern applied to samen's own scratch resources.*

5. **Sandbox backend chain for tool execution.** `EvoGit.Sandbox` resolves systemd-run → bwrap → sandbox-exec → passthrough, with a systemd user slice applying CPU/memory/task limits and a process registry that stops orphaned units when the caller dies. Their own docs honestly flag one path that bypasses the sandbox — the kind of self-audit samen's verifiers do mechanically. *Why it fits:* if/when samen's agent loop grows shell-executing or code-executing tools (G22 agent-grounding packaging, generative probes driven by agents), this is the reference Elixir implementation of OS-level confinement; pair it with a `samen.verify.*` tier asserting every exec path routes through the sandbox chokepoint (the verifier is the samen-shaped half Genesis lacks). *Effort: L.*

6. **PubSub delta event contract + node-identity filtering + system sampler.** Typed topic contract (`"tasks"`, `"agents"`, `"scheduler_config"`, `"system"`) carrying delta keyword-lists that strip heavy fields (`:context`), throttled flushes, subscribers ignoring messages where `node != node()`, and a 3s `SystemSampler` broadcasting a fixed 12-key sample into a 60-sample ring buffer. *Why it fits:* samen's fleet cockpit (ADR-044) heartbeat/report wire and any live agent-run observability surface need exactly this discipline — bounded sample schema, deltas not snapshots, and node-identity guards to avoid cross-app state corruption; complements samen's existing wide_event/observability modules. *Effort: S–M.*

7. **Declarative custom-agent registry with a model-selection hook.** User-defined agents in `agents.toml` (prompt, read/read_write type, tool whitelist, subagent allowlist, max_turns, model pin) plus a tiny per-spawn script deciding model routing, with a 4-level dispatch priority and errors that never crash the scheduler. *Why it fits:* samen's `mix samen.gen.agent` generates code; a data-driven registry layered on the catalog would let operators define bounded agents without codegen — but samen would swap the free-form Elixir eval script for a bounded, verifier-checkable declaration (arbitrary eval in an operator file is off-brand for samen). *Effort: M.*

8. **Two small honesty patterns.** (a) Disk-full-safe write boundary: all SQLite writes route through one `execute_write/4` that classifies SQLITE_FULL/IOERR/READONLY, logs, returns `{:error, :disk_full}`, and never crashes the store while reads continue — a good template for samen's backup/archival write paths. (b) `git merge-tree --write-tree` non-mutating merge dry-run (git ≥ 2.38) for conflict prediction with zero repo mutation — useful if samen's operator tooling ever previews generated-app or migration merges. *Effort: S each.*

## What to ignore and why

- **All code, verbatim.** AGPL-3.0 + CLA is incompatible with MIT samen; everything above must be re-derived as patterns (the CONTEXT.md docs describe the designs thoroughly enough that this is practical).
- **ReqLLM dependency and the Jido-adjacent ecosystem.** Genesis funnels all LLM traffic through `ReqLLM.stream_text`; samen already evaluated and rejected the Jido agent stack (`_orch/jido-eval-report.md`) and forbids vendor/HTTP deps in core (INV-4). Samen's chokepoint-minted `%MaskedPayload{}` adapters are strictly stronger — Genesis has **no PII/egress governance at all** (agents ship raw repo content to providers).
- **The core premise (freeform LLM software formation).** Samen's generative proof is deterministic (`mix samen.gen.app` passing a 19-step gate with zero hand-edits); "let agents evolve the repo and keep what passes tests" is a research direction orthogonal to a governed SaaS substrate. Genesis's validation is test-pass acceptance, far weaker than samen's sabotage-verified, AC-mapped gates.
- **Desktop distribution, remote SSH BEAM bootstrap, custom EPMD.** Impressive OTP work (EPMD-less distribution via `:persistent_term` port registry, NixOS patchelf-on-the-fly, per-target tunneled nodes) but solves "run my desktop tool's daemon on a GPU box over SSH" — samen's deploy story is Fly + fleet wire, and multi-node Oban is already proven locally.
- **SQLite store.** Right for a desktop app; samen is Postgres-only by conviction.
- **As a dev-process tool for building samen itself:** not worth adopting — samen's `_orch` loop already has stronger discipline (phase gates run full ci.sh, sabotage harness, verify verdicts), and Genesis's small community (38 stars, 1 fork) means no ecosystem pull.
