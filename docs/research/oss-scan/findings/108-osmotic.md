# 108 — Osmotic

## What the project is

Osmotic is a **self-hosted Elixir/Phoenix AI gateway** that sits between an org and LLM providers (currently Anthropic Messages API and OpenAI Responses API + batches; Google on roadmap, Chat Completions/Embeddings/Realtime/images/audio/fine-tuning explicitly excluded). It "issues API keys to people, teams, and applications, enforces spend and token quotas, scans outbound requests for secrets, and records what every request cost and who it belongs to."

Architecture: four listeners in one release — two loopback data-plane ports (Anthropic :8443, OpenAI :8444) doing raw SSE passthrough, a loopback control-plane admin console (:4000, LiveView), and a loopback-only Prometheus metrics port (:9568). Deploys as systemd + `.deb` packages (Debian/Ubuntu), expects a TLS-terminating reverse proxy in front. Stack: Phoenix 1.8 + LiveView 1.1, Ecto/Postgres, Bandit, Finch (bounded upstream pool), `cloak`/`cloak_ecto` (provider-key encryption at rest), `bcrypt_elixir` (admin console login), Decimal for all money math. Notably **no Ash, no Oban** — plain Phoenix/Ecto with hand-rolled GenServer+ETS hot-path caching instead of a job queue.

Design core: a "thin data plane" that never buffers streaming response bodies (parses usage off the SSE stream as it flies past), native per-provider passthrough with no unified request schema (so provider-specific features like `cache_control` survive untranslated), and an explicit fail-open/fail-closed matrix per control (auth, guardrails, DLP fail closed; rate limiter fails open by design). Usage accounting is an idempotent, exactly-once ledger: telemetry event → ETS buffer with a UUID idempotency key → timer-triggered writer → immutable `usage_records` fact table (unique constraint + `on_conflict: :nothing`) → ETS live tallies rebuilt from source at each billing-period rollover. Pricing is an effective-dated, insert-only rate table (never updated) so historical costs can't be retroactively rewritten. License: BSD-2-Clause. Status: early-stage (created 2026-07-29, 7 commits, 0 stars/forks) but unusually well-documented (ARCHITECTURE.md, SECURITY.md, ROADMAP.md, INSTALL.md, CI gates via credo/dialyxir/sobelow/mix_audit/ex_check) — reads like a single disciplined author's reference implementation rather than a community project.

## What samen could adopt

1. **Idempotent, immutable usage ledger + effective-dated rate card** — telemetry → ETS-buffered writer with UUID idempotency key → insert-only `usage_records` fact table with `on_conflict: :nothing`; live tallies are a *set* rebuild from source at rollover, not an additive counter, so a crash-and-replay can't double-count. Pricing lives in an insert-only, effective-dated table (`effective_from`-ordered lookup), so rate changes never rewrite historical spend. *Why it fits*: this is close to a direct blueprint for samen's open **G13 gap** ("Stripe sync is a stub… usage rating/proration/tax = op-todo") — samen already has the effective-dated-type discipline (ADR-036 rich types) and immutable/hash-chained audit precedent, so extending that same insert-only, idempotency-keyed pattern into a `Samen.Billing.UsageRecord` ledger is architecturally consistent, not a bolt-on. *Effort*: **M** (new Ash resource + writer + reconciliation job; the hard design thinking is already validated by this reference).

2. **GenServer-owned public ETS tables on the hot request path** — a GenServer that only wakes on a timer owns a *public* ETS table; the request path reads/writes the table directly with zero process round-trip (auth-key cache with 5s TTL including negative caching of misses; live quota tallies for O(1) checks; atomic ETS counter for rate limiting). *Why it fits*: samen's chokepoint-everything model (vault decrypt scanner, delivery chokepoint, AI egress chokepoint) does per-request policy/masking work that could benefit from the same "cache owned by a lazy GenServer, read directly from the request process" pattern wherever a chokepoint currently does a DB round-trip per call (e.g. policy/RBAC lookups, feature-flag reads). *Effort*: **S** (isolated, well-scoped pattern; apply to one chokepoint first as a spike).

3. **Explicit fail-open vs. fail-closed control matrix, stated as policy** — Osmotic documents, per control, whether it fails open or closed under scanner/cache/timeout failure (DLP fail-closed with a size-derived timeout on a supervised Task; rate limiter fails open by explicit choice; all other guardrails fail closed) and states the trade-off in prose rather than leaving it implicit in code. *Why it fits*: samen already has the *behavior* (fail-honest adapters, ADR-014/024/026/038) but not, as far as the digest shows, a single documented per-control fail-open/fail-closed table. Writing one — and adding a verifier that asserts each governed chokepoint's documented failure mode matches its actual behavior — closes a legibility gap cheaply. *Effort*: **S** (documentation + one verifier tier).

4. **Boot-time topology safety guards** — the app refuses to start if a data-plane listener is bound to a wildcard address, or if the metrics endpoint is bound anywhere but loopback. Cheap, structural prevention of a whole class of "accidentally public" misconfigurations. *Why it fits*: matches samen's fail-honest posture (missing secret raises and names itself) — the same "boot-time refuse, don't warn" discipline could cover samen's operator-plane and MCP listener bindings (ADR-047's MCP server explicitly runs "no stdio in prod"; a boot guard would make that structural rather than convention). *Effort*: **S**.

5. **Supervised, size-derived-timeout content scanning as a second layer on AI egress** — Osmotic's DLP step runs as a supervised Task with a timeout scaled to body size, fails closed if the pattern cache isn't loaded or the scan times out, and logs only the pattern name + key ID, never matched text. *Why it fits*: samen's AI egress chokepoint already does structural PII masking via `%MaskedPayload{}`, but this is a complementary layer — scanning for *secrets accidentally typed into a prompt* (API keys, tokens) rather than classified PII fields — which the chokepoint wouldn't catch since those values were never vaulted. Worth a scoped ADR: should `Samen.AI` gain a secret-pattern scan alongside its masking pass? *Effort*: **M** (new scan stage + pattern registry + verifier).

## What to ignore and why

- **No unified provider request schema (native per-provider passthrough)** — Osmotic deliberately keeps zero abstraction between provider wire protocols to preserve features like `cache_control`. This is the opposite of samen's `Samen.AI.Provider` behaviour + chokepoint-minted `%MaskedPayload{}` design (ADR-043), which trades some provider-feature fidelity for a single governed egress point. Samen's abstraction is load-bearing for its no-PII-egress guarantee; don't dilute it to match Osmotic's flexibility.
- **Best-effort (non-blocking) audit writes** — Osmotic explicitly lets a failed audit insert *not* fail the underlying mutation, prioritizing availability. Samen's hash-chained audit (ADR-002, DB trigger refuses UPDATE/DELETE) is already a stronger guarantee; adopting Osmotic's softer failure mode would be a regression.
- **`cloak`/`cloak_ecto` for at-rest encryption** — samen already evaluated and rejected Cloak/AshCloak for the PII vault in favor of a custom KMS-backed chokepoint (ADR-003). Introducing Cloak just for provider API-key storage would add a second, inconsistent encryption mechanism alongside the existing vault/KMS story rather than extending it.
- **No MFA on the admin console** — Osmotic's own SECURITY.md flags this as a known limitation ("keep the admin user set small"). Samen already has TOTP 2FA (`nimble_totp`) on its identity spine; nothing to adopt here, samen is already ahead.
- **Treat as a maturity-unverified reference, not a dependency** — 0 stars/forks, 7 commits, three-week-old repo with no visible external adoption. The documentation reads as trustworthy and the patterns are sound in isolation, but nothing here should be pulled in wholesale (even though BSD-2-Clause permits it) without independently verifying the claims against the actual code, since there's no community usage to have shaken out edge cases.
