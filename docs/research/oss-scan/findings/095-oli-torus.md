## What the project is

OLI Torus (Simon-Initiative/oli-torus) is Carnegie Mellon's "Next Generation OLI Authoring and Delivery Platform" — a combined course-authoring + course-delivery LMS with learning analytics, LTI 1.3 integration into external LMSs, and both managed-cloud and self-hosted deployment. MIT-licensed, actively developed (pushed today, 8,600+ commits, 119 stars/41 forks), built on Elixir ~1.19 / Phoenix ~1.8 / LiveView ~1.1 / PostgreSQL. It is a mature, large-scale (20MB+ Elixir source) production app, not a toy or archived repo — so its library and ops choices carry real weight as data points, even though the product domain (course content, activities, LTI, learning analytics) is unrelated to a SaaS foundry.

Architecture: single monorepo integrating authoring (content editing, versioning/publication of course "derivatives") and delivery (student-facing course runtime) with an extensible third-party activity SDK, plus an institution/section multi-tenancy model layered under LTI. Vanilla Ecto/Phoenix — no Ash, no vault-chokepoint or two-plane pattern, no crypto-shred; its trust model is conventional (cloak_ecto field encryption, standard RBAC) rather than samen's governance-by-construction posture. This is the main reason relevance is capped at medium rather than high.

## What samen could adopt

1. **`gettext` + `ex_cldr` (+ `ex_cldr_calendars`/`ex_cldr_dates_times`) for i18n/locale/currency formatting** — Why it fits: samen's own gap register (G24) explicitly flags "USD+UTC hardcoded, no gettext" as an open gap. Torus ships both libraries in a production Phoenix app of comparable scale, proving the combination works at this scale for locale-aware dates/numbers/currency plus translated strings. Effort: **M** (gettext requires marking/extracting all user-facing strings across samen_web; ex_cldr integration for Money/Duration types is more contained since samen already has rich declared types to hook into).

2. **`libcluster` + `libcluster_ec2` for real multi-node BEAM clustering in production** — Why it fits: samen's gap register lists "Oban multi-node in production: proven locally only" as an open item (two-BEAM-node Oban `:peer` proof is a local sim, not a real cloud topology). Torus runs `libcluster_ec2` for EC2-tag-based node auto-discovery in an actual production deployment — a concrete, low-risk pattern for whatever cloud target samen operators pick (even if not EC2, the libcluster strategy-adapter model transfers). Effort: **S** (libcluster is a thin supervisor + strategy config; the harder part — proving Oban jobs behave correctly across real nodes — samen already has test scaffolding for).

3. **`anubis_mcp` — a maintained third-party Elixir MCP server library** — Why it fits: samen hand-built its MCP server (HTTP + SSE in samen_web, per-operator tokens, protocol 2025-03-26) as a first-party chokepoint-integrated component (correctly, since it must enforce masking). Torus's use of `anubis_mcp` for its own "Torus MCP Server" (bearer-token auth, used by Claude Code during dev per their `guides/process/claude-code.md`) is worth a **read-only comparison pass**: confirm samen isn't reinventing wire-protocol plumbing anubis_mcp already solves well, even though samen must keep the masking/chokepoint logic first-party regardless. Effort: **S** (evaluation only, not a swap — likely ends in "confirm current approach, no change," similar to the ash_ai rejection precedent).

4. **Tidewave (dev-only MCP server for live Phoenix app introspection) as an AI-dev-workflow tool** — Why it fits: samen's entire development process is AI-authored-and-gated (Claude, `Co-Authored-By`, adversarial human review). Torus's documented convention of connecting Claude Code to Tidewave (live query/introspect the running dev app), an AppSignal MCP server, and their own Torus MCP server during development (`guides/process/claude-code.md`) is a directly transferable **process** pattern — giving the Claude agent live introspection into a running samen dev instance (routes, ecto queries, process state) rather than only static code + verifier output. Effort: **S** (add tidewave as a `:dev`-only dependency + a documented MCP-connection convention in samen's own process docs; zero production surface, so no chokepoint/PII risk).

5. **`phoenix_live_dashboard` mounted in the operator plane** — Why it fits: samen's operator control-plane already exists as a first-class surface (ADR-009 two-plane mount pattern) and the fleet cockpit (ADR-044) wants ops visibility; Torus mounts `phoenix_live_dashboard` (a standard, well-known Phoenix ops tool for BEAM/process/ecto/telemetry inspection) as a normal LiveView route. This is a cheap, well-trodden addition to samen's operator plane for BEAM-level ops visibility that complements (doesn't replace) samen's own OpenTelemetry/audit stack. Effort: **S**.

## What to ignore and why

- **`cloak_ecto` (field-level encryption library)** — samen's ADR-003 already evaluated and explicitly rejected AshCloak/Cloak in favor of a custom vault chokepoint with per-subject KMS keys and crypto-shred erasure. Torus's use of cloak_ecto is a data point that the library works, but it doesn't offer crypto-shred semantics or a masking-render type, so it changes nothing in samen's decision. No action.
- **LTI 1.3 (`lti_1p3`, `lti_1p3_ecto_provider`), the entire authoring/activity/course-derivative model, and learning analytics dashboards** — domain-specific to LMS/education; samen is a horizontal SaaS foundry with no course/activity/publication concepts. Not transferable.
- **`anthropix` / `openai` (AI provider clients) and `broadway`/`broadway_dashboard` (GenStage ingestion pipeline)** — samen deliberately hand-builds its AI provider adapters (`samen_anthropic`) as thin, chokepoint-only packages that refuse raw strings by construction; a general-purpose AI client library doesn't fit that constraint. Broadway is a data-pipeline tool for high-throughput ingestion Torus needs for content/media processing; samen's CDC/ingestion needs are already served by its own default-deny classifier (ADR-015) and don't need a new pipeline framework.
- **`appsignal_phoenix` (third-party APM/tracing SaaS)** — samen's OpenTelemetry setup deliberately disables `db_statement` so no `pii_` token ever serializes into a span; routing telemetry through a third-party SaaS APM is a net-new PII-egress surface that would need the same chokepoint scrutiny as any vendor adapter, and isn't a clear win over what samen already has.
- **`react_phoenix`/`phoenix_live_react` (React-in-LiveView interop)** — samen's UI kit is a function-component + token-CSS system; introducing a JS framework bridge cuts against that simplicity with no stated need.
