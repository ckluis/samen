## What the project is

Livebook (Dashbit / José Valim's team) is an Apache-2.0 web app for interactive, collaborative Elixir (and via Pythonx, Python) notebooks — `.livemd` Markdown files with evaluated code cells, built on Phoenix + Phoenix LiveView. Notable pieces:

- **Kino**: a library for rendering rich interactive outputs in cells (Vega-Lite charts, tables, maps, forms, kinos for ML/data work).
- **Smart cells**: high-level UI widgets (DB query builder, chart builder, map builder, etc.) that generate real Elixir source code into the cell — editable either as the form or as the underlying code, kept in sync.
- **Runtimes**: notebooks execute in one of three modes — **standalone** (fresh Elixir instance), **attached node** (connect to an already-running Elixir/production node over distributed Erlang), or **embedded** (run inside an existing Elixir project's own VM). Clustering config is via `LIVEBOOK_CLUSTER`/`LIVEBOOK_NODE`/`LIVEBOOK_COOKIE` (standard distributed-Erlang cookie auth, long-name nodes).
- **Security posture**: binds to `127.0.0.1` only by default; production/public deployments require a token or `LIVEBOOK_PASSWORD` (12+ chars) and a `LIVEBOOK_SECRET_KEY_BASE` (64+ chars); pluggable `LIVEBOOK_IDENTITY_PROVIDER` supports Zero Trust header-based auth in front of a reverse proxy (Cloudflare Access, Google IAP, Tailscale) as well as custom providers. The README is explicit that anyone with access to an instance can read any file and run any code on the host — i.e., it deliberately does NOT sandbox code execution; isolation is left to the deployment perimeter.
- **Deployment**: desktop apps (Tauri, macOS/Windows/Linux), Docker, escript/direct Elixir install, Nerves (embedded devices), source/cloud (Fly.io is a platinum sponsor). Apps (deployed notebooks) support password protection.
- **Livebook Teams**: a separate paid hosted product (not in the OSS repo) for team secrets sync and deployment; specifics weren't available from the public marketing/docs pages fetched.
- **MCP**: Livebook core does **not** ship a first-party MCP server — what turns up under "Livebook MCP" is a third-party community CLI (`livebook_tools`) that bridges AI coding agents to a running Livebook session over distributed Erlang. Not an official Dashbit feature.

## What samen could adopt

1. **Header-based Zero-Trust identity provider seam** (what: a pluggable auth adapter that trusts an identity header injected by a reverse proxy — Cloudflare Access, Google IAP, Tailscale — as an alternative to full SAML/OIDC; why it fits samen: ADR-029/031 already frame end-user auth as host-owned/BYO-auth, and SAML is explicitly "documented extension seam, not built" — a header-trust adapter is a much smaller lift than SAML for operators who already sit behind a Zero Trust proxy, and is a natural fit for the **operator plane** specifically, which is lower-user-count and more likely to already be proxied; effort: S).

2. **Generated-code-editable UI pattern ("smart cells")** (what: a UI widget that both renders a form AND emits/accepts the underlying declarative source, kept in two-way sync, so power users can drop into raw editing without losing the form; why it fits samen: `Samen.Automation` already compiles a declarative 8-kind Action registry through `Automation.Compile` → `Reactor.Builder` — an automation-builder UI that shows the generated step graph/config as editable structured data alongside the form would give operators the same "safety of the form, power of raw editing" that makes Smart Cells popular, without changing the compile pipeline; effort: M, UI-layer only).

3. **Explicit default-bind-to-loopback + honest "we do not sandbox" security framing** (what: Livebook's README states plainly that it does not isolate execution — security is the deployment perimeter's job — rather than implying a false guarantee; why it fits samen: this is exactly the "fail-honest" documentation voice samen already practices (ADR-014/024/026 fail-honest adapters, `compliance-story.md`'s "NOT certification" framing) — worth citing as an external precedent for how a respected Elixir project writes its threat-model caveats, not a code change; effort: S, docs-voice reference only).

## What to ignore and why

- **Kino / notebook output widgets** — built for REPL-style notebook cells, not a Phoenix LiveView app's persistent UI; samen already has its own `samen_web/ui` function-component kit for that surface. No direct code reuse path.
- **Attached-node runtime (distributed-Erlang connect-and-run-arbitrary-code)** — this is the one pattern to actively avoid importing: it grants full-VM code execution with no chokepoint, which is the inverse of samen's core invariant (INV-1, "mask-by-default survives everything," enforced via `Samen.Chokepoint`/`Samen.Pii.WriteGuard`). Any "attach a console to a live samen node" tool would bypass the vault, the audit chain, and every verifier in one step — Livebook's own README says as much about itself. If samen ever wants a live-debug console, it needs to be built as a governed, audited, chokepoint-respecting surface (closer to `break_glass`), not modeled on Livebook's runtime.
- **Distributed-Erlang clustering (`LIVEBOOK_CLUSTER`/cookie) for coordination** — samen already solved cross-node coordination for its actual coordination problem (Oban job execution) via **Postgres** (`Oban.Peers.Database`, `FOR UPDATE SKIP LOCKED`), proven in `docs/runbooks/multinode-oban-proof.md` — deliberately choosing Postgres-mediated coordination over raw distributed-Erlang clustering so the same mechanism works locally and in production without cluster/cookie/network topology management. Livebook's clustering solves a different problem (real-time collaborative session state across nodes) that samen doesn't have; adopting distributed-Erlang clustering would be a regression from samen's current Postgres-only coordination posture.
- **Livebook Teams (secrets sync SaaS)** — closed-source hosted product; couldn't verify its actual mechanics from public pages, and it's not something to depend on or port — samen's own KMS/vault chokepoint + `samen.abbrev.reserve`-style host-namespaced registries already cover the adjacent problem (per-subject key material, adapter credentials) more rigorously (crypto-shred, hash-chained audit) than a "sync secrets to a client" model would.
- **Third-party MCP bridge (`livebook_tools`)** — not an official Livebook feature, and samen already has a first-party, chokepoint-respecting MCP server (ADR-043, HTTP+SSE, per-operator tokens, no stdio in prod) that is architecturally more disciplined than a distributed-Erlang-based community bridge.
- **Multi-language (Python via Pythonx)** — no analog need in samen; samen's polyglot surface is vendor adapters (Stripe/Postmark/SES/Resend/Anthropic), not in-process alternate-language execution.
