# What the project is

ServiceRadar (Carver Automation, Apache-2.0) is an open-source, AI-native network management, monitoring, ITOM, and security-analytics platform — not a SaaS-app framework, but a distributed observability/security product for network operators. It is polyglot: a lightweight Go `Agent` runs on monitored hosts (with WASM plugin execution for custom checks), an `Agent-Gateway` is the gRPC ingress point for edge agents and bulk collectors (netflow, logs, SNMP, OpenTelemetry), NATS JetStream is the message backbone, and `Core (core-elx)` — the piece of direct interest — is an **Elixir/Phoenix/Ash control plane** ("orchestration, ERTS, and job scheduling via Oban") handling ingestion, APIs, alerts, and identity reconciliation (referred to in their docs as "DIRE"). The Web UI (`web-ng`) is a Phoenix LiveView dashboard with SRQL (their Rust-based query language) embedded via Rustler/NIF for query execution inside the BEAM. Persistence is a single unified Postgres-family store: CloudNativePG + TimescaleDB (time-series) + PGVector + Apache AGE (graph topology). Auth supports password login, direct SSO (OIDC/SAML), or gateway-proxied JWT, with "instance-scoped roles and permissions" — the docs describe single-instance RBAC, not tenant-isolated multi-org RBAC; there is no evidence of samen-style org-scoping, PII vaulting, or masked/token-blind planes. Deployment is Docker Compose for quickstart and an official Helm chart published as an OCI artifact to a private registry, with mTLS (SPIFFE/SPIRE on Kubernetes) for service identity and Cosign-signed images. Visualization uses a GPU-native topology engine (deck.gl + Apache Arrow zero-copy streaming + a WASM logic layer) rendering large node/edge graphs at 60fps. No LLM/AI-plane integration was found beyond a Rust "Causal Engine" (DeepCausality) for root-cause analysis — this is not an AI-agent product.

# What samen could adopt

- **Rust-NIF-embedded query engine inside Phoenix LiveView (SRQL/Rustler pattern).** ServiceRadar lets its Elixir web layer execute a Rust-implemented query language directly via Rustler/NIF rather than shelling out or running a separate service. Samen's `req`-only-in-adapters / zero-vendor-deps-in-core discipline (INV-4) is a different axis, but if samen ever needs a performance-critical, non-Elixir computation embedded in `samen_web` (e.g., a compiled search/expression evaluator), the NIF pattern — keep it thin, keep the boundary explicit — is a concrete precedent worth studying before reaching for a sidecar service. Effort: M (only relevant if/when such a need arises; not a near-term gap).
- **Structured, per-subsystem instance readiness reporting.** ServiceRadar documents day-1 automated credential/cert provisioning ("Platform TLS and agent enrollment credentials are provisioned for you... does not require hand-built CAs") as an explicit onboarding property. Samen's G11 shipped `/readyz` + metrics-egress/alert runbook but flagged the **public status page as still open**; ServiceRadar's pattern of naming automated-provisioning-as-a-feature is a useful bar for what samen's still-open status page / onboarding story should claim once built. Effort: S (documentation/scope framing, not new code).
- **Polyglot-core-with-thin-Elixir-boundary as a validated real-world shape.** Nothing to copy directly, but ServiceRadar is evidence that a production system can run Ash/Phoenix/Oban as its control-plane "brain" while Go/Rust services own performance-sensitive edges (collectors, query execution, visualization) — reinforcing (not contradicting) samen's own ADR-037 posture of keeping the Elixir core lean and pushing vendor/perf-sensitive code to satellite packages. Effort: N/A (validation, not action).

# What to ignore and why

- **The entire product surface**: network topology visualization, SNMP/NetFlow/BGP collection, CVE/SBOM/vulnerability scanning, Falco/Trivy integration, WASM plugin sandboxing for host checks. None of this overlaps with samen's mission (a SaaS-app foundry for tenant-facing products with PII governance) — it's an infrastructure-observability product, not a substrate for building other SaaS apps.
- **Auth/RBAC model**: instance-scoped roles for a single deployed instance, not samen's tenant-org-scoped, PII-resolution-composed policy model. Samen's two-plane + `OrgScope`/`PiiResolution` composition is already substantially deeper than what's documented here; nothing to backport.
- **No PII vaulting, masking, crypto-shred, or audit-chain equivalent found.** ServiceRadar's security posture (mTLS, RBAC, SSO, signed images) is infra-perimeter security, not samen's data-governance-by-construction model — orthogonal concerns, not a gap samen has.
- **GPU-native deck.gl/Apache Arrow visualization stack**: a specialized large-graph rendering pipeline for network topology; no analog in samen's product surfaces (CRM/support/billing/ops), not worth the dependency weight.
- **Multi-language toolchain (Go + Rust + Elixir + TypeScript/React + WASM)**: samen's single-toolchain (Elixir/OTP), vendor-free-core discipline is a deliberate simplicity choice; ServiceRadar's polyglot sprawl is the kind of complexity samen's ADRs have repeatedly chosen to avoid.
