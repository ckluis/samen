# 021 — Loomkin

## What the project is

Loomkin is an open-source (MIT) **AI agent team orchestration platform in Elixir/Phoenix/LiveView** — a persistent multi-agent development workspace rather than an ephemeral chat. ~179 stars, 28 forks, 800+ commits, ~77K LOC app + ~40K LOC tests (2,700+ tests), actively developed as of the scan. Runs on Elixir 1.20 / OTP 28+, PostgreSQL, Phoenix LiveView (39 components, zero handwritten JS), with Telegram/Discord channel adapters.

Core capabilities:

- **Multi-agent teams under OTP supervision**: DynamicSupervisor + Registry spawns role-typed agents (lead, researcher, coder, reviewer, tester) in <500ms; leads can be restricted to coordination-only tools ("orchestrator mode"). Every agent runs the same ReAct loop (`agent_loop.ex`).
- **Persistent decision graph**: a Postgres-backed DAG of reasoning memory — 7 node types (goal, decision, option, action, outcome, observation, revisit), 7 typed edges (`leads_to/chosen/rejected/requires/blocks/enables/supersedes`), per-node confidence 0–100, session linkage, JSON metadata. Auto-logged on agent lifecycle events; confidence drops cascade `upstream_uncertainty` flags down `requires`/`blocks` edges; "pulse reports" scan for stale/low-confidence regions; context_builder injects active goals + recent decisions into every system prompt under a token budget; interactive SVG DAG in LiveView.
- **Context mesh / Keepers**: instead of summarizing overflow, oversized context chunks are offloaded at full fidelity to `ContextKeeper` processes (ETS/Redis, hash-keyed), discovered cross-agent by walking the decision graph, and re-fetched segment-by-segment. Claims 228K+ effective tokens with zero loss; failure-memory keepers capture lessons from errors.
- **Verification loops + pair mode**: coder proposes via FileEdit, reviewer gets a unified diff component, structured propose/critique/revise/vote debate, low-confidence escalation to costlier models via `model_router.ex`; autonomous write→test→diagnose→fix→re-test cycles with speculative execution and rollback; self-healing teams (error classification, ephemeral fixer agents, per-role healing policies).
- **Permissions/approvals**: tools declare required permissions in their Jido.Action schema; `permissions/manager.ex` gates dispatch; dangerous ops (shell, force-push, delete) raise interactive LiveView approval modals with diffs; approvals are logged into the decision graph as outcome nodes.
- **Stack**: built on **Jido** (agent framework: tools, action composition, signal bus) and **req_llm** (16 providers / 665+ models, streaming, cost accumulation). MCP **server and client** (exposes 28 tools to editors; consumes external MCP servers and registers remote tools locally). Tree-sitter repo intelligence (7 languages, ranked repo map, tiered context packer — Aider-inspired). Per-team budget tracking, token-bucket rate limiting, region-level file locking, skill system with in-app editor + publish/install + `.agents/skills/` auto-load, multi-tenant social layer for sharing personas/skills.

## What samen could adopt

Samen already has a first-party agent loop (ADR-047: durable multi-step tool use, EG2 governed egress, E3 approvals for anything with side effects, budgets, `gen.agent` + `verify.agent_coverage`) and explicitly rejected Jido (`_orch/jido-eval-report.md`) and vendor deps in core (INV-4). So the value is **patterns, not code**:

1. **Persistent decision graph as an Ash resource family** — what: a DAG memory (goal/decision/option/action/outcome/observation/revisit nodes, typed edges incl. `rejected` and `supersedes`, confidence scores) written automatically by the agent loop and injected into prompt assembly. Why it fits: samen's ADR-047 agent loop has transcripts + retention but no *structured, queryable* reasoning memory; a token-only, catalog-described decision graph would ground agents across sessions, feed the operator plane, and stay crypto-shreddable (nodes carry `vt_*` tokens only, erasure-envelope per ADR-046). Loomkin's specific trick worth copying: log approvals as outcome nodes so the approvals engine and the reasoning trace are one queryable structure — samen already has the hash-chained audit for compliance; the graph is the *semantic* layer above it. Effort: **M** (new scope blueprint + agent-loop hook + prompt-assembly injection through the existing masking chokepoint; verifier tier for no-PII-in-graph is cheap given existing `pii_reads` machinery).
2. **Confidence cascade / pulse reports** — what: when an upstream decision's confidence drops, flag downstream `requires`/`blocks` nodes `upstream_uncertainty`; periodic "pulse" scan surfaces stale/low-confidence regions as operator alerts. Why: maps directly onto samen's automation Health/Breaker + notifications; gives the operator cockpit an "agent reasoning health" panel with no new deps. Effort: **S** on top of item 1 (an Oban job + notification events).
3. **Keeper-style context offload (full-fidelity, not summarization)** — what: when the agent-loop context window nears budget, offload coherent chunks to persisted keeper records (hash-keyed) and retrieve segments on demand instead of lossy summarizing. Why: samen's ADR-047 does per-turn history grant re-scrub; a keeper tier would let long-horizon agent runs keep fidelity while every retrieval re-passes the masking chokepoint (the re-scrub point is a natural seam). Effort: **M** (storage is trivial — Ash resource + Oban; the retrieval-relevance heuristic is the real work; skip Loomkin's cheap-LLM semantic search initially).
4. **Cheap-agents + expensive-judge model routing** — what: role/complexity-based model routing with opt-in escalation to costlier models when confidence is low (Loomkin claims ~18x cost savings). Why: samen's AI kernel has budgets/cost caps but a single-model posture per call; a `model_router`-style policy inside `Samen.AI` (still one chokepoint, `samen_anthropic` adapter picks model id) is a pure win for agent-loop economics. Effort: **S**.
5. **Mission-control LiveView surfaces** — what: agent cards + live team activity feed, interactive SVG decision-graph component, per-agent cost dashboard fed by telemetry, diff-review component wired into the approval modal. Why: samen's operator plane already owns approvals (Gate face) and the fleet cockpit; Loomkin proves the exact UI grammar for supervising agents in LiveView with zero JS — the diff-in-approval-modal pattern is the strongest single steal for E3 approvals of AI-drafted changes. Effort: **M** (UI kit work; data already exists in samen's approvals/audit/AI run records).
6. **MCP client (not just server)** — what: Loomkin consumes external MCP servers and registers remote tools locally. Why: samen has an MCP *server* (ADR-043) but no client; a governed MCP client whose tool *results* are treated as EG2 governed ingress (re-scrubbed at the chokepoint) would extend agent capabilities without new vendor deps in core (HTTP lives in an adapter package per INV-4). Effort: **M/L** — do only when a concrete external tool need appears; the trust-boundary work (external tool output → masking chokepoint) is the hard part.
7. **Skill auto-load convention** — what: `.agents/skills/` directory auto-loaded at boot, with an in-app editor. Why: cheap packaging for samen's G22 gap (agent-grounding packaging for builders) — filesystem-convention skills beat a registry for a monorepo foundry. Effort: **S** for load-from-dir; skip the publish/install social layer.

## What to ignore and why

- **Jido and req_llm adoption**: samen already ran a formal Jido eval and rejected it (ADR-037 posture; no chokepoint concept, vendor deps into core). req_llm's 16-provider abstraction is the opposite of samen's design — samen *wants* a single governed provider behaviour accepting only `%MaskedPayload{}`; a universal client would widen the egress surface. Patterns yes, dependencies no.
- **Self-healing / ephemeral fixer agents and speculative execution with rollback**: directly conflicts with samen's "AI writes do not exist" invariant — agents auto-repairing failures without human approval is the exact failure mode E3 approvals were built to prevent. Revisit only as *draft* fix proposals routed through approvals.
- **Multi-tenant social platform / kindred bundles / community snippet marketplace**: Loomkin is community-distribution-oriented; samen is an in-monorepo foundry (ADR-033, no Hex packages). Zero fit.
- **Tree-sitter repo intelligence layer**: valuable for a code-editing agent product, but samen's agents ground on the machine-readable catalog (its own differentiator) rather than AST maps of arbitrary repos; adopting this is scope creep toward "coding agent," not "SaaS foundry."
- **Region-level file locking, Telegram/Discord adapters, LSP client**: dev-tool concerns orthogonal to samen's product plane.
- **Its trust posture generally**: Loomkin has no PII vault, no masking, no token-blind planes, no sabotage-style verification — nothing to learn on the governance axis; the flow of ideas there goes the other direction.
