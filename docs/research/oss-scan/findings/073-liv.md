# 073 — LIV

## What the project is

LIV is a self-hosted personal webmail client written in Elixir/Phoenix LiveView (AGPL-3.0, ~124 stars, ~227 commits, small maintenance-mode project). It is explicitly a one-user-per-instance tool: each user runs their own BEAM instance on its own port behind Nginx and logs in with a single application password. Its design philosophy is "all open source webmail sucks... IMAP sucks" — so instead of IMAP it reads a local Maildir directly and delegates full-text search to the external `mu` indexer (1.6.x). It deliberately has **no database**; config lives in a `~/.config/.../liv.config` file via `self_configer`. Features: mu-powered search, markdown composition with HTML preview, phone-friendly threading, automatic 30-day archive/delete retention, background attachment handling. Sending goes via local SMTP, authenticated SMTP 587, or Sendgrid; retrieval optionally via POP3.

## What samen could adopt

Essentially nothing concrete. Evaluated against samen's mailbox scope, delivery chokepoint, and ESP adapters (`samen_postmark`/`samen_ses`/`samen_resend`):

- **Markdown compose with live HTML preview (idea only).** What: LiveView-side markdown editor with instant preview for outbound mail. Why it fits: samen's mailbox/outreach scopes could use a nicer compose UX than plain text. Effort: S — but this is a generic LiveView pattern, not something LIV's code teaches (and AGPL forbids lifting it); samen would build it independently if ever wanted. Not a real adoption from this repo.
- **Nothing else.** LIV's load-bearing choices — no database, filesystem Maildir as the store, shelling out to the `mu` binary, single-user auth with one shared password, per-user OS-level instances — each directly contradict samen's invariants (Postgres/Ash resources, multi-tenant org scoping, vaulted PII, RBAC identity spine, no external binary dependencies in core).

## What to ignore and why

- **The entire mail-storage architecture** (Maildir + mu): samen is a hosted multi-tenant SaaS substrate; tenant mail lives as Ash resources with PII vaulting, not files on disk. A mu dependency would also violate samen's vendor-free-core rule (INV-4) and its search story (non-PII tsvector, pgvector).
- **Auth model**: one static app password per instance is the opposite of samen's ADR-035 identity spine (orgs, memberships, TOTP, OIDC, sessions).
- **Deployment model**: one BEAM process per human behind Nginx doesn't map to a fleet-of-SaaS-products model.
- **License**: AGPL-3.0 is incompatible with adopting code into MIT-licensed samen; only ideas could travel, and none here are novel.
- **Scale/activity**: hobby-scale personal tool (6 forks, 0 issues) — no ops/deploy or OTP patterns beyond a standard Phoenix release script.
