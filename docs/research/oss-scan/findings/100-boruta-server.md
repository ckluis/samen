# Boruta Server

## What the project is

`boruta-server` is a standalone **Identity and Access Management server** written as an Elixir/Phoenix umbrella app (five sibling apps: `boruta_auth`, `boruta_identity`, `boruta_admin`, `boruta_gateway`, `boruta_web`), Apache-2.0, by malach-it. It is not a demo — it holds **OpenID Foundation certification** (Basic/Implicit/Hybrid OP profiles, and Config/Dynamic OP profiles) and **EBSI certification** for verifiable-credential issuance/verification. Development is very active: daily commits, patch releases roughly every 1-2 days (0.11.0 → 0.11.5 in the week before this scan), 191 stars, 11 forks.

Component breakdown:
- **`boruta_auth`** — wraps the separate `boruta` Hex/git library (the actual OAuth2/OIDC token-issuance engine: RFC 6749 authorization framework, RFC 7662 introspection, RFC 7009 revocation, RFC 7636 PKCE, RFC 7521/7523 JWT client auth, RFC 9449 DPoP, RFC 9126 PAR) plus OIDC core, dynamic client registration, and the newer OpenID4VCI/OpenID4VP decentralized-identity specs (DID resolution/registration via external Universal Resolver/Registrar services, eIDAS 2.0-flavored).
- **`boruta_identity`** — the built-in identity provider: password auth (argon2/bcrypt/pbkdf2 selectable), **WebAuthn** (`wax_` library — passkeys/FIDO2), **LDAP/Active Directory** federation (`:eldap`), email confirmation, consent screens, custom user attributes, and an SMTP delivery path (`gen_smtp`).
- **`boruta_admin`** — the operator UI for managing OAuth clients, scopes, users, and (per recent commits) multi-node cluster status/log aggregation across an Erlang cluster (`libcluster` + Kubernetes/Docker-Compose discovery).
- **`boruta_gateway`** — an experimental reverse-proxy/API gateway applying access rules (auth, rate limiting) to arbitrary upstream traffic, with a "microgateway" sidecar mode, HTTP(S) forward-proxy listeners, and static YAML-driven configuration.
- **`boruta_web`** — the OAuth/OIDC HTTP endpoints proper.

Notable stack choices: Phoenix ~1.6 (dated vs samen's 1.8.9), Nebulex+Shards for distributed/cluster caching, Quantum for cron, `oauth2` client lib, `ex_json_schema` for request validation, a bundled non-production-ready demo wallet for testing the decentralized-identity flows. Ships as Docker images (`malachit/boruta-server` on DockerHub) or a Mix release; supports Kubernetes multi-node clustering out of the box.

## What samen could adopt

- **The `boruta` core OAuth2/OIDC provider library as a reference (and possible future adapter) for samen's own "be an OAuth provider" gap** — samen's ADR-035 identity spine is entirely BYO-auth/consumer-side (`assent` for OIDC login *into* samen); samen has no path today for third-party apps to authenticate *against* samen (e.g., a tenant's own integrations doing "Sign in with samen," or partner apps consuming samen's JSON:API under real OAuth scopes instead of static API tokens). Boruta's core library is the most mature, standards-certified implementation of this in the Elixir ecosystem — worth reading as an architecture reference before hand-rolling, and a real candidate to vendor as a new `samen_oauth` adapter package (path-dep on `samen_core` only, per the existing adapter convention) rather than reinventing PKCE/DPoP/PAR/introspection/revocation correctness from scratch. *Why it fits:* directly fills a documented, explicitly-deferred gap (SAML "documented as extension seam, not built"; no OAuth-provider role at all today) with proven, certified code instead of ad-hoc token issuance. *Effort:* L — real flows (PKCE, DPoP, PAR, introspection) plus mapping client/scope/consent resources into samen's Ash + vault + org-scoping model; only worth doing when a concrete external-integration use case appears.
- **WebAuthn/passkey support via `wax_`** — samen's identity spine today is password + TOTP (`nimble_totp`) only, no passkeys. `wax_` is a small, standalone WebAuthn library (not entangled with the rest of boruta) that could slot into the existing identity spine as a second factor or passwordless option alongside the current TOTP step-up. *Why it fits:* natural extension of ADR-035's auth-event/step-up model; passkeys are increasingly expected for a modern self-serve SaaS onboarding flow. *Effort:* M — one focused library integration plus UI (registration ceremony, credential storage, login ceremony), following the existing chokepoint/vault pattern for credential secrets.
- **LDAP/Active Directory federation pattern (`:eldap`)** — boruta_identity's LDAP adapter is a clean example of federating an external directory into a generator-emitted identity flow without disturbing the core auth pipeline. *Why it fits:* aligns with samen's still-open enterprise-onramp roadmap themes (BYO-auth is host-owned today; LDAP is a plausible next on-ramp for enterprise tenants beyond OIDC). *Effort:* S-M — Erlang's built-in `:eldap` does the protocol work; the integration surface is mostly mapping directory attributes into samen's user/org resources.
- **OAuth client/scope admin UI pattern** — boruta_admin's CRUD screens for OAuth clients and scopes are a reasonable reference for what a samen "API clients" or "integrations" surface would need in the operator plane, if/when the OAuth-provider adapter above is ever built. *Why it fits:* would live naturally in samen's existing operator-plane mount pattern. *Effort:* S once the underlying provider exists — it's UI over already-modeled resources.

## What to ignore and why

- **The gateway/microgateway/forward-proxy components**: samen's chokepoint architecture already enforces masking/policy at the application layer (single decrypt scanner, single send/upload/AI-egress paths); a separate reverse-proxy tier for access rules would duplicate that guarantee at a weaker layer and add an unwanted network hop. Not aligned with samen's "governance by construction in the app, not the perimeter" posture.
- **Decentralized identity / OpenID4VCI / OpenID4VP / DID resolution / EBSI / the demo wallet**: eIDAS 2.0 / EU digital-identity-wallet compliance is a deep, narrow vertical with no connection to samen's current SaaS-foundry scope (US-only data residency per ADR-032); adopting it would be pure surface area with no roadmap justification.
- **The umbrella app as a whole / boruta_web / boruta_gateway deployment topology**: different Phoenix version (1.6 vs samen's 1.8.9), different persistence/caching stack (Nebulex+Shards, Quantum) that overlaps rather than composes with samen's existing Oban/ash_rate_limiter choices; running boruta-server *alongside* samen (rather than lifting the core library) would mean operating and securing a second stateful multi-node Elixir cluster for no capability samen doesn't already have a cheaper path to.
- **Nebulex+Shards distributed cache pattern**: samen's caching/rate-limiting needs are already served by Hammer + ash_rate_limiter (pinned 1.0.0, ADR-037); no evidence of a gap this would fill.
- **`oauth2` Elixir client library dependency**: samen already consumes OIDC via `assent`, which is the more actively-recommended library for that role in the current Elixir ecosystem; no reason to add a second OAuth client lib.
