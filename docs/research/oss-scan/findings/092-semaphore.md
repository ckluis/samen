## What the project is

Semaphore is an open-source, self-hostable CI/CD platform ("all-in-one delivery platform for AI-driven development") with a dual-license structure: Community Edition (Apache-2.0, everything outside `ee/`) and Enterprise Edition (commercial license, code in `ee/`) plus a hosted Semaphore Cloud offering. It's actively maintained (~1.6k stars, 738 commits on main, active Discord/RFC/SIG process).

Architecturally it is the opposite of samen's monolith-with-mountable-planes design: **30+ independently deployed microservices** (`projecthub`, `public-api`/`public-api-gateway`, `loghub2`, `secrethub`, `notifications`, `hooks_receiver`/`hooks_processor`, `repository_hub`, `mcp_server`, `keycloak`, plumber/zebra job-orchestration services, etc.), written in a mix of Elixir/Phoenix (core concurrency-heavy services), Go (performance-critical paths, including the MCP server), and legacy Ruby being phased out. Services talk over gRPC/protobuf internally, RabbitMQ for async/background work, HTTP for external API/UI. Data layer is PostgreSQL + Redis. Identity/auth is delegated to Keycloak rather than homegrown. Deploys target Kubernetes (Helm charts present per-service, e.g. `secrethub/helm/`), with a stated 10-30 minute self-host setup across Ubuntu/Kubernetes/Minikube.

Multi-tenancy is org-based: Organizations contain Projects; RBAC has three organization roles (Member/Admin/Owner, additive permissions) and three project roles (Reader/Contributor/Admin), plus Groups that hold one role and propagate it to members, plus Custom Roles gated to paid tiers. Audit logs are provided per-org, exportable to CSV and streamable daily to an S3-compatible bucket — this is an Enterprise-tier feature alongside SAML/SCIM.

## What samen could adopt

1. **MCP-server-as-audited-gateway pattern.** Semaphore's `mcp_server` (Go, `mark3labs/mcp-go`, Streamable HTTP on a dedicated port, bearer-token auth, `/healthz`/`/readyz` probes, 18 read-oriented tools, dials internal gRPC services for data, publishes audit events to AMQP when enabled) is a clean reference for "MCP as a narrow, audited, read-mostly query surface fronting the real system," conceptually validating samen's own choice (ADR-043/047: HTTP+SSE MCP server, per-operator tokens, audited). **Why it fits:** samen already has an MCP server; this is a second real-world implementation to diff against for tool-surface shape (their split of workflow/job/artifact/scheduled-task tools) and for the healthz/readyz probe convention samen's fleet cockpit could reuse. **Effort: S** (docs/pattern comparison, maybe adds 2-3 tool ideas, no new deps).

2. **Audit log CSV export + daily S3-compatible streaming.** Samen's hash-chained audit is currently tenant-readable in-app and periodically WORM-anchored, but the digest doesn't mention a self-serve CSV export or continuous off-platform streaming path for compliance/SIEM ingestion. Semaphore ships this as a named, gated (Enterprise) feature. **Why it fits:** directly extends samen's existing audit_chain/anchor subsystem toward a concrete, demoable compliance surface (helps G19/DSAR-adjacent gaps and the compliance-story.md posture) without touching the vault/chokepoint invariants. **Effort: M** (export job + S3 adapter, reuses existing WORM-anchor plumbing).

3. **RBAC role-naming and tiering UX (Member/Admin/Owner org roles; Reader/Contributor/Admin project roles; additive Groups; Custom Roles as a paid-tier lever).** Samen's OrgScope/policy system is more structurally rigorous (fail-closed, org-scoped, SAT-solver-backed), but Semaphore's role vocabulary and "additive, never-reduces" permission model is a well-user-tested naming/UX convention for the operator-facing role editor that samen's G28 (operator RBAC granularity, P3) gap could crib from. **Why it fits:** addresses an explicitly open gap (G28) with a proven, documented UX rather than inventing role names from scratch. **Effort: S** (naming/UX only — no architecture change; samen's policy engine underneath is already stronger).

4. **Dual-license `ee/` folder convention as a future productization lever.** If samen ever needs to separate a commercial/hosted layer from the Apache-core substrate (currently ADR-033 keeps everything in-monorepo, no Hex packages), Semaphore's pattern — Apache-2.0 everywhere except a clearly separated `ee/` directory under a commercial license, same repo — is a low-friction template that doesn't require a packaging/distribution rewrite. **Why it fits:** compatible with samen's "distribution stays in-monorepo" invariant while opening a licensing lever later. **Effort: S** (a licensing/business decision, not a build item — flag for the operator, not autonomous work).

## What to ignore and why

- **The 30+-service gRPC/protobuf microservices topology and RabbitMQ.** Samen's INV-4/substrate-first invariant deliberately keeps the core web-dependency-free and avoids splitting into independently-deployed services; adopting Semaphore's topology would be a direct regression against samen's own architectural bet (single-gate generative CI, one deploy unit per generated app). Not a fit at any effort level.
- **Keycloak-delegated identity/auth.** Samen explicitly built and hand-verified its own identity spine (ADR-035, ADR-029/031 BYO-auth, rejecting `ash_authentication` rewrites) specifically to keep PII-vaulting and masking guarantees inside its own chokepoints. Delegating to Keycloak would reintroduce an external system samen's masking/vault model doesn't control — contradicts the whole thesis of the repo. The one transferable idea (SAML/SCIM as a documented extension seam) samen already has noted as a deliberate future seam, not a gap to close via Keycloak.
- **secrethub's actual encryption implementation** — could not be confirmed from public docs/directory listing (only module names, no visible encryption/KMS code in what's browsable without cloning). Given samen's own vault chokepoint (per-subject KMS keys, crypto-shred, AES-256-GCM via OTP `:crypto`, ADR-001/003 already rejected AshCloak/Cloak after evaluation) is already more rigorously specified and proof-gated than anything confirmable here, this is not worth further digging — low expected payoff for the fetch cost.
- **CI/CD job-orchestration domain itself** (plumber/zebra pipeline execution, agent fleet, YAML pipeline config) — off-domain relative to samen's SaaS-foundry/PII-vaulting focus; nothing here maps to samen's product surface.
