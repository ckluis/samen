# What the project is

Azimutt is a database schema exploration, documentation, and analysis tool ("full-stack database tool" for ERD visualization, search, querying, notes/tags, and consistency analysis across Postgres/MySQL/MongoDB/Snowflake/BigQuery/etc.), MIT-licensed, actively maintained (2,167 stars, 140 forks, pushed June 2026, not archived).

Stack: plain **Elixir/Phoenix 1.6 + Ecto/Postgres** backend (`backend/`, `mix.exs` — no Ash anywhere), an **Elm + elm-spa** frontend editor (`frontend/`), a small **Node/TypeScript gateway** (`gateway/`) that proxies live database connections so the browser app can query customer databases without the main backend touching credentials, a TypeScript **CLI**, and a desktop **Electron/Tauri-style extension** that keeps DB access fully local as the credential-free alternative to the gateway. Deployment is self-host via Docker/Helm, or Heroku/Clever Cloud one-click listings; billing is live Stripe (webhooks handled, subscriptions real, not a stub). Backend Ecto contexts are conventional: `Accounts` (user/token/profile), `Organizations` (org/member/invitation/plan), `Projects` (project/project_file/project_token — schema docs stored as versioned blobs with `storage_kind: :local | :remote` and Waffle/S3-backed file storage), `Admin`, `Blog`, `Gallery`, `Tracking` (PostHog analytics), plus Heroku/CleverCloud marketplace integration modules.

# What samen could adopt

- **A real, working Stripe subscription lifecycle as a concrete reference implementation.** `Azimutt.StripeHandler` (`@behaviour Stripe.WebhookHandler`) handles `customer.subscription.created/updated/deleted`, resolves the org by Stripe customer id, revalidates the org's plan on every event, and threads trial/cancel/renew/quantity-change transitions into analytics — using the plain `stripity_stripe` Hex package rather than Ash. Samen's `SyncAdapter.Stub` (G13) is the biggest labeled operator-TODO in the digest; Azimutt's webhook handler is a small, legible pattern for what "org plan revalidated on every Stripe event" looks like end-to-end once live keys land. Effort: M (samen still needs to keep its fail-honest-adapter and audit-chain discipline around the same webhook shape).
- **`OrganizationPlan` as a typed, versioned feature-entitlement struct.** A `TypedStruct` with one boolean/integer field per gated feature (`ai`, `schema_export`, `project_share`, `projects` limit, etc.), built once from a `plans()`/`features()` config map, `@derive Jason.Encoder`'d so the same shape ships to the Elm frontend — with an explicit code comment that the struct must stay in sync across three language boundaries (Elixir/TS/Elm). Samen's plan/entitlement editor already shipped (G13 note); this is a smaller, concrete pattern for keeping a single entitlement source-of-truth serializable straight into the AI/catalog layer and any future non-Elixir surface, worth comparing against samen's current representation. Effort: S.
- **Gateway-proxy vs. local-desktop split for touching customer infrastructure without persisting credentials.** Azimutt's `gateway/` is explicitly documented as a stateless proxy so the browser can query a customer's live DB "without keeping everything local"; the alternative path is a desktop app that never sends credentials over the network at all. This is a different mechanism from samen's vault-and-mask model (avoid touching the secret at all vs. vault-and-govern it) but is a relevant pattern for any future samen adapter that needs to reach a tenant-owned resource (e.g., a customer's own Stripe/db/API key) — proxy-without-persist is cheaper than a full vault classification for secrets that are never samen's own PII. Worth a one-paragraph ADR note if such an adapter is ever proposed. Effort: S (research/ADR note only).
- **`project_token.ex` as a scoped-sharing-link pattern.** Projects support shareable read/write visibility tokens independent of org membership. Samen's DSAR/self-serve export gap (G19, P2) and any future "share a masked view externally" surface could reuse the shape of a narrowly-scoped, revocable token tied to one resource rather than a session/actor. Effort: S.

# What to ignore and why

- **The entire domain and product surface** (ERD visualization, AML markup language, schema import/diagramming, Elm frontend): unrelated to samen's SaaS-foundry purpose; nothing here is a SaaS-infrastructure pattern, it's the product itself.
- **Plain Ecto/Phoenix architecture with no policy/authz layer visible in the modules inspected**: no `Ash.Policy`-equivalent, no per-field masking, no reveal-grant model, no hash-chained audit, no crypto-shred, no token-blind aggregate plane, no vault chokepoint. Azimutt stores project/schema data and account PII (email, GitHub OAuth via `ueberauth`) with ordinary Ecto changesets and no vaulting; adopting its data-handling model would be a straight regression from samen's INV-1 (mask-by-default) and the whole trust-kernel story. This is the single biggest gap versus samen and the reason relevance is capped at medium, not high.
- **`hackney`/`httpoison` (two overlapping unmaintained-trending HTTP clients), `extwitter`, `posthog`, `waffle`/`waffle_ecto`**: legacy/vendor-specific dependency choices from a 2021-era Phoenix app; samen's `req`-only-in-adapter-packages discipline (INV-4, zero vendor deps in core) is already stricter and shouldn't regress toward this dependency shape.
- **elm-spa frontend and the Node gateway/CLI/extensions monorepo layout**: samen_web is LiveView-first by design (ADR-009 two-plane mountable pattern); Azimutt's split-language, split-repo-workspace frontend is a different bet driven by its own product (a heavy client-side diagramming canvas) that samen has no analog need for.
