## What the project is

AetherS3 (MIT, Elixir `~> 1.20` / OTP 29, umbrella app) is a self-hostable, distributed, S3-compatible object store that runs on the BEAM — nodes discover each other (libcluster), replicate object blobs, and self-heal without an external coordinator. Actively developed (pushed 2026-08-16, 53 stars, not archived), with a real CI pipeline, Docker/Burrito release packaging, and unusually thorough documentation (`docs/architecture.md`, `security.md`, `clustering.md`, `configuration.md`, `observability.md`, `transforms.md`, `console.md`, `development.md`).

Two-plane architecture:
- **Data plane (AP)**: object blobs + metadata, placed via rendezvous (HRW) hashing (no placement registry), configurable write quorum, cross-node proxied reads with range support, read-repair, and anti-entropy that both migrates and sheds on topology change. Metadata in embedded CubDB; blobs on local disk; conflict resolution via version vectors with deterministic last-writer-wins tiebreak.
- **Control plane (CP)**: bucket ownership/ACLs/identities/groups, backed by **Khepri** (a Raft/`ra` tree store) with libcluster auto-discovery and Raft auto-join; dead-member eviction + boot-time self-heal (wipes only the stale Raft log, blobs untouched).

Security: SigV4 request signing, config-seeded root identities + dynamic access keys (secrets AES-256-GCM-encrypted at rest under a master key), grant-based per-bucket/object/prefix authorization (owner + grants + groups, `:list`/`:get`/`:write`/`:full`), a token-gated admin API, bounded-staleness auth/ACL caching (explicitly documented tradeoff), and optional in-app TLS.

Observability: split `/health` (liveness), `/ready` (data-plane), `/ready/cp` (control-plane, leader-routed Khepri probe — catches phantom-leader/lost-quorum), `/metrics` (Prometheus), `/cluster` (fanned-out JSON topology snapshot), `/whoami`. OpenTelemetry tracing (off by default, zero-cost until an OTLP endpoint is set) propagates trace context across the replication RPC hop so one PUT is a single cross-node trace. A companion `aether_console` app (separate Phoenix LiveView release, HTTP-only client of the admin port, never joins the BEAM cluster) gives a live cluster/replica-flow view and identity/bucket management.

Deps of note: `bandit`, `plug`, `cubdb`, `saxy` (XML), `khepri`, `libcluster`, `toml`, `telemetry_metrics_prometheus_core`, `opentelemetry_*` (samen_core namespace); console: `phoenix`/`phoenix_live_view`/`req`, no Ecto (stateless HTTP client of the cluster).

Test posture: unit tests plus a real e2e suite driving actual `aws-cli` against live clusters — `same_host.sh`, `docker_cluster.sh`, `split_brain.sh` (iptables-partitioned, proves CP keeps quorum + AP converges on heal), `rebalance.sh` (3→5 nodes, proves migrate+shed), `reap.sh` (orphaned multipart cleanup), `converge.sh`, `warp.sh` (load), all run in CI.

The README's "Status and limitations" section is unusually candid: it lists exactly what's simulated/incomplete (formation-window write loss, single-value conflict resolution, best-effort conditional writes, orphan cleanup gaps, no policy engine, no encryption at rest, no `ListMultipartUploads`/versioning/lifecycle) rather than glossing over them.

## What samen could adopt

1. **A real target for `Samen.Files.Storage.S3`** — samen's own skeleton (verified: `samen_core/lib/samen/files/storage/s3.ex` is an explicit operator-TODO, no `ex_aws`/`req` wired) currently has no runnable S3 backend to test against locally. AetherS3 speaks enough of the S3 HTTP API (bucket/object ops, range reads, multipart, SigV4) to self-host as a dev/CI target instead of mocking S3 or requiring live AWS credentials. Why it fits: directly closes the WS-E "real Storage.S3 impl" gap's *test fixture* problem without needing cloud credentials. Effort: **S** (docker-compose up + point the S3 adapter's endpoint at it; the adapter implementation itself is still samen's own work).

2. **Dual readiness-endpoint pattern (`/ready` vs `/ready/cp`)** — separating "can I serve traffic" from "is the control plane/consensus layer actually healthy" (with the CP check being a leader-routed probe that actually commits, not a cached lookup) is a sharper version of samen's existing `/readyz` (G11, shipped). Why it fits: samen already has fail-honest adapter philosophy (never fake success); this is the same idea applied to health checks — avoids a phantom-leader or lost-quorum state reading as "healthy." Effort: **S** (if samen ever runs a consensus/coordination layer — e.g. multi-node Oban, which is currently only proven locally) — otherwise low priority since samen has no Raft-like component today.

3. **Honest-gaps README section as a pattern, not the code** — AetherS3's "Status and limitations" bullet list (what's real, what's a documented tradeoff, what's simply not built) is close in spirit to samen's `docs/claim-evidence.md`/`claim-sweep.md` and the "fail-honest adapters" invariant. Why it fits: reinforces samen's own INV-6 (docs/claims sync) discipline; nothing to port, just a legibility bar worth holding samen's own README to. Effort: **S** (process, not code).

4. **Trace-context propagation across `:erpc` hops (`AetherS3.Tracing.rpc/4`)** — a small, concrete pattern for injecting a W3C trace-context carrier before an `:erpc` call and re-attaching it on the far side so a single logical operation (their PUT; samen's cross-node Oban/agent-loop work) shows as one trace instead of orphaned spans per node. Why it fits: samen already uses OpenTelemetry (with `db_statement` disabled to keep PII tokens out of spans) but the digest doesn't mention explicit cross-process trace propagation; this becomes relevant once/if samen's automation engine or multi-node Oban work spans processes. Effort: **M** (needs a concrete multi-node code path in samen to attach to; speculative until then).

5. **Burrito single-binary release packaging** — wrapping an OTP release into one self-contained executable per OS/arch (`BURRITO_BUILD=1 mix rel`, needs zig) is an alternative distribution story to samen's existing Docker/Fly deploy path. Why it fits: could simplify demo/eval distribution of `mix samen.gen.app`-generated apps for prospective external builders (G22 agent-grounding-for-builders gap) without requiring Docker. Effort: **M** (new toolchain dependency; evaluate only if external-builder packaging becomes a priority).

6. **Per-node metrics + PromQL cluster aggregation instead of a central metrics DB** — AetherS3 deliberately keeps metrics per-node and pushes cluster-wide views into PromQL (`sum(...)`, `max-min` for partition detection) rather than building a custom aggregation service; `GET /cluster` gives a no-Prometheus-needed JSON fallback. Why it fits: cheap pattern to note for samen's fleet cockpit (ADR-044) if/when it needs cross-instance aggregate health beyond the current token-blind report wire — though fleet cockpit already solves a related but distinct problem (tenant-identity-aware rollups, not infra metrics). Effort: **S** (documentation-level pattern, not a dependency).

## What to ignore and why

- **Khepri/Raft and libcluster themselves as new samen dependencies** — samen_core is explicitly vendor/HTTP-and-clustering-free by design (INV-4, "Zero vendor/HTTP deps in core"), and samen's persistence model is Postgres + Oban, not a Raft-backed tree store. Pulling in Khepri would contradict samen's own ADR-037 adopt/reject discipline (which already rejected several packages for violating chokepoint/core-purity invariants) — there is no analogous "needs its own consensus layer" problem in samen today.
- **The object-store domain logic wholesale (HRW placement, version-vector conflict resolution, anti-entropy/rebalancing, bitrot scrub)** — this solves distributed *blob* storage across untrusted/independent nodes, a different problem from samen's PII-vaulting-over-Postgres model. Not reusable as code; useful only as background reading if samen ever needs its own multi-node data-plane story (not indicated by the roadmap).
- **SigV4 auth/authorization implementation** — samen already has its own identity spine (ADR-035, OIDC via `assent`, TOTP, session management) and grant/policy model (OrgScope, RBAC, approvals engine with DB-CHECK enforcement) that is more sophisticated than AetherS3's flat grant model (which itself documents "not a full policy engine" as a known gap). No reason to borrow the weaker model.
- **`aether_console`'s architecture as a template** — it's a clean "separate release, stateless HTTP client of an admin API" pattern, but samen's operator plane is already a first-party mounted module inside the same app (ADR-009 two-plane + three-identity model), which is a deliberately different (and for samen's purposes, more integrated) choice; adopting a fully separate console app would cut against samen's mount-leverage thesis (pawchart's ~188 lines of scope mounts).
- **Object transforms (`?transform=`, Lambda-style read-side gzip)** — a storage-layer feature with no counterpart need in samen; samen's files subsystem is about chokepointed upload/quarantine, not on-the-fly object transformation.
