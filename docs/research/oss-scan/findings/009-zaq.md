# 009 — ZAQ (collaborative agent operating system)

Evaluated 2026-08-18 via repo README, `docs/architecture.md`, `docs/services/agent.md`, `docs/guides/workflows-guide.md`, and `mix.exs`. Active project: ~1,383 commits, 66 stars, v0.16.0, release-please + ghcr images, AGPL-3.0 with commercial dual-license.

## What the project is

ZAQ is a sovereign, self-hosted "company brain": an Elixir/Phoenix/LiveView agentic OS that connects org knowledge (RAG over pgvector) to configured AI agents with a deterministic permission system ("AI can only see what the asking user can see"), multi-channel delivery (Mattermost live; Slack/Teams/Telegram/Discord planned; native IMAP/SMTP email), MCP tool connections, a JSONB-DAG workflow engine, and a LiveView Back Office admin panel.

Architecture: a single OTP app with five role-gated supervision trees (`engine`, `agent`, `ingestion`, `channels`, `bo`) selected by a `ROLES` env var; multi-node via Erlang distribution + EPMD auto peer discovery; all cross-service calls go through a hand-rolled `Zaq.NodeRouter` dispatching a `%Zaq.Event{}` envelope with hop-driven sync/async/multi-hop semantics. It is built almost entirely on the Jido ecosystem: `jido` 2.3, `jido_ai`, `jido_action`, `jido_chat` (+ Mattermost/Telegram/Discord adapters), `jido_mcp`, `jido_studio`, `jido_runic`, `jido_connect`, `req_llm`, `llm_db`, `zoi` schemas — many pinned to GitHub branches/forks. Ingestion uses an OTP-supervised Python sidecar (PDF/DOCX/XLSX/image → markdown) feeding an Elixir chunk/embed pipeline (Oban, pgvector). Layered domain architecture (`Types → Config → Repo → Service → Runtime → UI`) with forward-only dependencies enforced by custom linters and structural tests — kindred spirit to samen's verifier discipline.

## What samen could adopt

1. **Progressive-disclosure agent skills (Open Agent Skills pattern).**
   - *What:* Skills are DB records (name, description, markdown body, provided tool keys). The system prompt carries only an index of name+description (O(skill count) tokens); a `load_skill` tool pulls the full body on demand as a tool result — stateless, transcript-is-the-record, idempotent, self-healing on restart. `load_skill` is scoped to the invoking agent's own enabled skills and its not-found payload never enumerates the catalog (an explicit info-leak fix over upstream). Write-time byte/token caps protect the context window; a truncation guard rejects silently-shortened records.
   - *Why it fits samen:* Directly serves ADR-047's agent loop and G22 (agent-grounding packaging). Samen already grounds agents in the catalog; a skills index + on-demand body loader is the same "catalog as data" move applied to operator-authored agent instructions, and the scoping/no-catalog-leak rule matches samen's fail-closed posture. Zero new deps — it's a schema, a tool, and prompt assembly through the existing masked chokepoint.
   - *Effort:* M.

2. **Trusted-execution-context identity rule for person-scoped tools — as a verifier.**
   - *What:* ZAQ's hard rule: identity for permission-scoped tools comes from `ctx[:actor]`, never from LLM-supplied parameters; an LLM-facing `person_id` param is honored only under an explicit `skip_permissions: true` admin opt-in; `nil` actor is never an implicit grant; blank IDs never resolve.
   - *Why it fits samen:* Samen's EG2 governs tool args/results as egress, but the inverse direction — LLM-supplied args must never select the acting identity or widen scope — is a distinct invariant worth locking. It is exactly the kind of AST/structural check samen already ships (`samen.verify.agent_coverage` style): flag any agent tool whose action actor derives from tool params rather than the loop's actor.
   - *Effort:* S.

3. **Persist-before-deliver auditability ordering.**
   - *What:* ZAQ mandates channel delivery only after transcript persistence succeeds; persistence failure aborts delivery with an explicit error, never a delivered-but-unrecorded message.
   - *Why it fits samen:* Samen's delivery chokepoint + ADR-046 transcript retention almost certainly do this, but ZAQ states it as a named, testable rule. Cheap to encode as a red-path test on the agent loop and delivery chokepoint (sabotage-able: swap the order, a named test must fail).
   - *Effort:* S.

4. **Two-tier runtime reconciliation for configured agents (hot patch vs stop-and-lazily-recreate).**
   - *What:* Per-field change classification: tool/MCP/skill toggles hot-patch a running agent runtime; structural fields (model, credential, strategy, memory size) stop the server and recreate lazily on next message; `active=false` drains. Mutation fanout re-syncs every runtime referencing the changed record; sync responses report `stopped_server_ids` so the UI can surface operational impact.
   - *Why it fits samen:* Today samen's agent loop is per-run, so this is forward-looking — but if ADR-047 ever grows long-lived agent servers or streaming (currently deferred), this field-tier taxonomy is the cleanest reconciliation design seen in the scan. Worth a paragraph in the ADR-047 follow-on notes now, implementation later.
   - *Effort:* M (deferred).

5. **Workflow-engine ergonomics: map/fan-out nodes, embedded sub-workflows, edge conditions+mappings, build-time contract refusal.**
   - *What:* Workflows are JSONB `{nodes, edges}` DAGs; node types include `map` (run a body per collection item) and `workflow` (inline composition); edges carry a condition and a data mapping; the DAG build refuses any node whose module lacks the declared input/output schemas (`{:error, {:contract_violation, module, missing}}`).
   - *Why it fits samen:* Samen's automation engine (ADR-039, Reactor + 8-kind action registry + bounded outcomes) is stronger on compensation and governance but lacks fan-out and composition as first-class node kinds. The build-time contract refusal mirrors samen's fail-fast taste and would slot into `Automation.Compile`. Adopt the *features* (map node, sub-workflow embed, per-edge mapping), not the JSONB representation.
   - *Effort:* M–L (automation v2 candidates, per-feature).

6. **Answer-quality telemetry: no-answer counting + knowledge-gap detection + data-quality dashboard.**
   - *What:* The pipeline emits `qa.no_answer.count`, tracks confidence scores per answer, and surfaces a BO dashboard tying data quality to AI performance; "knowledge gaps" are first-class (questions the KB couldn't answer).
   - *Why it fits samen:* Samen has an AI eval harness and red-team tier but no production-side "the assistant couldn't help" signal feeding the operator plane. A no-answer/low-confidence wide-event + operator-cockpit tile is a small, high-leverage addition to samen's support/CRM AI surfaces and would feed G21 (support-desk depth).
   - *Effort:* S–M.

7. **Atom-safety guard for runtime-minted atoms.**
   - *What:* MCP endpoint runtime IDs are atoms minted from DB ids; ZAQ centralizes creation behind guards — block new atoms at ≥85% atom-table usage and hard-cap endpoint count (2000) — in one module.
   - *Why it fits samen:* Samen mints per-host/per-abbrev names and may mint per-agent process names under ADR-047. If any samen path converts unbounded DB-derived values to atoms, this guard (plus a verifier that greps for `String.to_atom` outside the guard module) is the fail-closed version.
   - *Effort:* S.

8. **Ops pattern: role-gated supervision trees via env var.**
   - *What:* One release binary; `ROLES=engine|agent|ingestion|channels|bo|all` decides which supervisors start; peers self-discover.
   - *Why it fits samen:* Samen just proved multi-node Oban (L4). A `SAMEN_ROLES`-style startup gate (web vs jobs vs AI workers) is a near-free deployment-topology option for Fly-era scaling, consistent with samen's single-artifact posture.
   - *Effort:* S.

## What to ignore and why

- **The Jido ecosystem itself.** Samen already evaluated and rejected Jido (`_orch/jido-eval-report.md`; ADR-037 posture), and ZAQ's dep list is a cautionary exhibit: nine-plus Jido packages, several pinned to `main` branches or private forks, with commented-out local `path:` deps left in `mix.exs`. That is precisely the vendor-dep fragility INV-4 exists to prevent. ZAQ validates that Jido *can* carry a real product, but changes nothing about samen's decision.
- **Code reuse of any kind.** AGPL-3.0 (with CLA + commercial dual-license) is incompatible with copying into MIT-licensed samen. Patterns and test ideas only.
- **NodeRouter / hand-rolled event-envelope RPC.** Samen's cross-boundary work rides Oban and OTP; a bespoke hop-driven RPC layer with role→supervisor lookup is complexity samen does not need and would blur samen's chokepoint story.
- **The RAG company-brain product shape.** ZAQ is a destination app (ingest docs, answer questions); samen is a substrate. Samen's KB/embedding needs are already served by pgvector + catalog grounding; adopting ZAQ's ingestion-centric worldview would be scope drift.
- **Python sidecar document conversion.** Useful trick (OTP-supervised external pipeline), but it drags a Python runtime into the trust boundary of PII-bearing documents. If samen ever needs PDF→text, it belongs in a fail-honest adapter package (INV-4), not core — and that's a future G21/G22 decision, not now.
- **ZAQ's "deterministic permissions" as a model to import.** Its permission system is person-scoped retrieval filtering — necessary for RAG, but strictly weaker than samen's vault/masking/token-blind construction. Nothing to learn there that samen doesn't already do more rigorously; only the tool-identity rule (adopt #2) transfers.
