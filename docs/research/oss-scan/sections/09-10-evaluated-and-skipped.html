Evaluated & Skipped

The remaining 67 repositories — 65 low and 2 none — were read in full and evaluated against the same rubric as everything above, and none of them cleared the bar. They cluster into five recognizable shapes, and within each shape the reasoning repeats almost verbatim from project to project, so it is stated once per cluster here rather than 67 times. Two structural facts cut across all of them. First, license risk is the norm, not the exception: AGPL-3.0 accounts for roughly a third of this list (Akkoma, Kazarma, Inkwell, linkhut, LIV, Philomena, Pleroma, Comcent CE, Loopyard, Maestro, Codebattle, Cannery, Mydia, Pinchflat, Revix, TeslaMate, Mindwendel, Claper), several more carry non-OSI source-available or no-license terms that block code reuse outright (Buster Claw's PolyForm-Shield, JidoBuilder's PolyForm-Noncommercial, Frontman's AGPL-plus-AI-supplementary-terms, and the unlicensed Agent Harness/Conductor/Codrift/jido-conductor), and even the MIT/Apache-2.0 majority rarely offers code worth vendoring — only patterns. Second, domain mismatch dominates: the great majority of this list is single-tenant, single-operator, or single-community software (personal media servers, federated social nodes, homelab utilities, dev-tooling daemons) with no Ash, no org/tenant model, and no PII-governance concept at all — the exact shape samen's kernel exists to generalize away from. Where a project nonetheless earns a genuinely worthwhile line — a library, a CI check, a naming convention — it is called out in the table; everything else is domain-correctly out of scope.

Rejected agent frameworks and the Jido lineage (18)

This is the largest single cluster, and it resolves the same way every time. Samen ran a formal evaluation of the Jido agent framework on 2026-08-13 (_orch/jido-eval-report.md) and rejected it — jido_ai hard-depends on req_llm, putting vendor/HTTP deps in the execution path (the identical INV-4 failure that got ash_ai rejected in ADR-037), and neither Jido nor any competing framework below has a masking-chokepoint concept: every one of them moves raw prompt strings, which samen's %MaskedPayload{}-only providers refuse by construction. ADR-047 then shipped a first-party, zero-new-dependency agent loop that closed the one gap the Jido eval found (durable multi-step tool use), so the rejection now generalizes cleanly to every entrant in this space: JidoBuilder, jido-conductor, Jido Studio, and Synapse are UIs or orchestrators built directly on Jido and inherit its rejection; Agens, AgentForge, Avalon, LLMAgent, and LegionWeb are independent competing frameworks that fail the identical chokepoint test; Fermix, Buster Claw, Frontman, Loopyard, Maestro, Agent Harness, Codrift, and Conductor are dev-process / coding-agent-harness products (a different layer — orchestrating coding agents against repos, not product-embedded agents over tenant data) that samen's own _orch/ loop already covers with different, deliberate conventions. Nothing here is adoptable as a dependency or as code; the worthwhile items below are all small, independently-reimplementable ideas, most of which ADR-047 already covers in a stronger form.
