Quick Hits (Medium Relevance, Miscellaneous)

Six projects that share no category, no architecture, and mostly no Ash: a self-hosted CMS, a database-schema tool, a Git forge, a CI/CD platform, a university LMS, and an EVE Online mapping SaaS. None clears the bar for its own deep-dive section — each is a single-repo data point, not a cluster of independent confirmations — but read together they land on two genuinely useful things a scattered-category catch-all rarely produces: two live, working reference implementations for samen's single biggest labeled operator-TODO (the Stripe/billing sync stub, G13), and two external, independently-arrived-at validations of architecture bets samen has already made (the approval-gated AI write and the audited MCP gateway). The rest is a grab-bag of cheap, concrete library and hygiene picks against open gaps (G24 i18n, G28 RBAC naming, the multi-node Oban proof, webhook egress hardening). Licensing is mixed and matters here: Nivose and GitBlixt are AGPL-3.0 (patterns only, never code), Semaphore splits Apache-2.0 core from a commercial ee/ slice, and Azimutt / OLI Torus / Wanderer are MIT-compatible outright.

Two concrete answers to samen's biggest labeled gap (G13)

The digest flags SyncAdapter.Stub — samen's stand-in for real Stripe billing sync and plan/entitlement truth — as the largest named operator-TODO. This batch delivers two independent, live-production answers to the same problem, arrived at differently. Azimutt runs real Stripe keys: Azimutt.StripeHandler (a Stripe.WebhookHandler behaviour using the plain stripity_stripe Hex package) resolves the org by Stripe customer id and revalidates the org's plan on every customer.subscription.* event, threading trial/cancel/renew/quantity-change transitions into analytics — a legible reference for what "org plan revalidated on every webhook" looks like end to end, alongside a companion pattern worth copying regardless of billing provider: OrganizationPlan, a typed, versioned entitlement struct built once from a plans()/features() config map and Jason.Encoder'd so the identical shape ships to non-Elixir surfaces (Azimutt's Elm frontend; samen's analog would be the AI/catalog layer). Wanderer answers the same problem from the opposite direction — no Stripe, an external license-manager microservice instead: WandererApp.License.LicenseManager mirrors subscription truth into a local DB row (lm_id, license_key, is_valid, expire_at), and validation checks the external service but degrades to the cached local record if that call fails — a documented fail-open-vs-fail-closed split for "can't reach billing" versus "billing said no" that samen's stub doesn't currently specify. Neither is Ash and neither should be vendored wholesale, but together they de-risk the two hardest design questions in G13: what the webhook handler's revalidation loop looks like end to end, and how the cache should degrade when the billing service itself is unreachable.

External validation for two of samen's own bets

Two projects in this batch independently arrived at architecture decisions samen already made, without any awareness of samen's ADRs — useful precisely because the validation is unprompted. GitBlixt ships a named, marketable "Scheduled Agents" feature: recurring AI tasks run on a cron schedule, but every output lands as a merge request for human review, with auto-merge explicitly excluded from the feature. That is samen's own ADR-047 stance — "AI writes do not exist; anything with side effects goes through the E3 approvals engine" — reinvented from scratch by a different team as a first-class UX affordance rather than an invisible policy, which is the actionable idea: package the approval gate as something the product foregrounds, not just enforces. Semaphore and OLI Torus do the same for ADR-043's MCP server. Semaphore's mcp_server (Go, Streamable HTTP, bearer-token auth, 18 read-oriented tools dialing internal services, audit events published to AMQP, /healthz//readyz probes) is a second real "MCP as a narrow, audited, read-mostly gateway fronting the real system" implementation to diff samen's tool-surface shape against. OLI Torus adds two smaller, cheaper data points on the same theme: anubis_mcp, a maintained third-party Elixir MCP server library, worth a read-only pass to confirm samen isn't reinventing wire-protocol plumbing it already solves (expected outcome: "confirm current approach, no change," same shape as the earlier ash_ai rejection) — and Tidewave, a dev-only MCP server for live Phoenix introspection that Torus's own team wires into Claude Code during development. That second one is a process win, not a product one: since samen's entire build process is AI-authored and gated, giving the coding agent live query access to a running dev instance (routes, Ecto queries, process state) rather than only static code and verifier output is a small, zero-production-surface change worth adding to samen's own process docs.

Grab-bag: cheap library and hygiene picks against open gaps

The remaining items are single-line, single-effort picks, several reinforcing gaps already covered at higher-relevance elsewhere in this report. On i18n (G24): Nivose and OLI Torus both run production Phoenix apps on the same ex_cldr + gettext combination the Business & Collaboration cluster already converged on four separate times — no new information, but two more confirmations that the library choice is settled, and Nivose additionally proves flop/flop_phoenix is worth a read-only sanity-check against samen's bespoke keyset-pagination contract (not a replacement — samen's is purpose-built for masked/token-blind reads). On the open "Oban multi-node in production: proven locally only" gap, OLI Torus runs libcluster + libcluster_ec2 for real EC2-tag-based node auto-discovery in production — a thin supervisor-plus-strategy-config pattern that transfers to whatever cloud target samen operators pick, even off EC2, leaving only the harder work (proving Oban jobs behave correctly across real nodes) that samen already has test scaffolding for. On G28 (operator RBAC granularity), Semaphore's Member/Admin/Owner org roles plus Reader/Contributor/Admin project roles, additive Groups, and paid-tier Custom Roles is a well-user-tested role-naming and tiering convention samen's policy engine — already more rigorous, fail-closed and SAT-solver-backed underneath — can borrow the vocabulary from rather than inventing names from scratch. On crypto-ops UX, two complementary pieces: GitBlixt's encrypted-backup envelope shows the private key exactly once at enable-time with an explicit off-server warning and documents that the secrets key must carry over on restore — a concrete runbook shape for samen's own backup-verification proof (WS-L/L6, currently local-sim) when it moves to real infrastructure; Wanderer's WandererApp.Vault configures a primary-plus-fallback Cloak cipher pair, decrypting against the current key and falling back to the old one on error, which is a rotation-with-fallback-window pattern worth porting at the KMS master-key layer specifically (not the per-subject vault layer — ADR-003 already rejected Cloak there for lacking per-subject keys and crypto-shred). Wanderer's webhook dispatcher is also a ready-made audit checklist for samen's existing webhook egress surface, which the digest doesn't explicitly confirm has equivalent hardening.

Three items round out the batch as smaller, take-it-or-leave-it notes. Nivose's vix (libvips NIF) image-optimization pipeline and sitemapper/atomex feed generators are proven, self-contained libraries to slot behind samen's existing upload chokepoint and cms scope blueprint, respectively, if a CMS-flavored vertical is ever built — plus sobelow as a cheap addition to ci.sh's static-analysis chain, catching Phoenix-specific web hygiene (XSS/CSRF/config footguns) that samen's PII-focused verifiers don't target. GitBlixt's Docker Swarm + Caddy admin-API self-host PaaS, with dynamically registered routes and per-merge-request preview environments, is a legitimate lower-cost alternative to samen's Fly-centric deploy story — real architecture work (a new Samen.Deploy.Swarm-style adapter), but the per-PR ephemeral tenant instance idea is a concrete feature samen's fleet cockpit could offer builders directly. And Wanderer's self-hosted, Postgres-backed error_tracker (versus piping stack traces to a third-party APM) fits samen's INV-4 vendor-free-core posture better than any SaaS alternative, worth evaluating as an optional observability adapter alongside the OTel setup that already disables db_statement for the same PII-non-egress reason; its git_ops conventional-commit changelog automation and dual Nix-flake/devcontainer onboarding path are small quality-of-life picks now that samen is a public repo external evaluators clone and read.

Nivose medium

What it is: a self-hostable "Small Web" CMS (Phoenix 1.8 + LiveView, plain Ecto, no Ash) — WYSIWYG page builder, media manager, blog/RSS, multi-account dashboard.

Adopt: the ex_cldr+gettext i18n stack as a proven G24 reference (M); the vix/adept_svg/file_info/xxh3 image-optimization pipeline behind samen's upload chokepoint if a CMS vertical materializes (S–M, native libvips dependency — a posture change worth flagging); sitemapper+atomex for sitemap/feed generation on the cms scope (S); sobelow added to ci.sh's static-analysis chain for Phoenix-specific web hygiene (S); flop/flop_phoenix as a read-only cross-check on samen's pagination contract (S, review only); remote_ip for correct client-IP resolution behind Fly's proxy layer, feeding rate limiting and any future analytics surface (S).

Why it fits / caveat: AGPL-3.0 — every item above is "reimplement via Hex," never "copy the source." Skip the WYSIWYG builder and the analytics module outright: neither maps to an open samen gap, and Nivose's analytics is single-tenant with no cross-tenant token-blind aggregation to learn from.

Azimutt medium

What it is: a database schema exploration/documentation/ERD tool, plain Phoenix/Ecto (no Ash) with an Elm frontend, live Stripe billing, 2.1k stars, actively maintained.

Adopt: Azimutt.StripeHandler's live webhook lifecycle (org resolved by Stripe customer id, plan revalidated on every subscription event) as the concrete reference for samen's stubbed G13 sync adapter (M, keep samen's fail-honest-adapter and audit-chain discipline around the same shape); the OrganizationPlan typed, versioned, Jason.Encoder'd entitlement struct pattern for a single serializable source of truth across language boundaries (S); the gateway-proxy-without-persisting-credentials pattern (a stateless Node proxy versus a credential-free desktop alternative) as a one-paragraph ADR note for any future adapter touching a tenant-owned secret that isn't samen's own PII (S, research only); project_token.ex's narrowly-scoped, revocable, resource-tied sharing-link shape for the DSAR/self-serve export gap (G19) (S).

Why it fits / caveat: MIT, so code-level reuse is legally clean, but architecturally shallow versus samen — no Ash-policy-equivalent, no masking, no vault, ordinary Ecto changesets over PII. Treat as a billing/entitlement reference, not a data-handling one; adopting its data model wholesale would regress INV-1.

GitBlixt medium

What it is: an actively developed, self-hosted, GitLab-v4-API-compatible Git forge (Phoenix 1.8 + Bandit + LiveView, plain Ecto, no Ash) with a built-in Docker Swarm PaaS and Claude Code-powered AI agents.

Adopt: the "Scheduled Agents" UX — recurring AI tasks that always land as a merge request, never auto-merged — as a packaging idea for surfacing ADR-047's approval gate as a marketable, first-class capability rather than an invisible policy (M, governance substrate already exists — mostly an Oban-cron scheduling primitive plus UI affordance); the encrypted-backup envelope UX (show-once private key, explicit off-server warning, documented secret-carryover requirement on restore) as a runbook reference for samen's backup module and WS-L/L6 proof once it moves from local-sim to real infrastructure (S–M); the Swarm+Caddy self-host PaaS with dynamic route registration and per-merge-request preview environments as a lower-cost alternative deploy target to samen's Fly-centric story, including the ephemeral per-PR tenant-instance idea for the fleet cockpit (L — a genuinely new adapter, not a bolt-on).

Why it fits / caveat: AGPL-3.0 — patterns to reimplement, not code to copy. Skip the entire git-hosting/forge domain (repos, MRs, issues, CI runners, GitLab-parity tracker) as off-mission, and treat the "hot code upgrades" marketing claim as a cautionary example: the actual mechanism is a Swarm start-first rolling restart, not a BEAM hot-upgrade — don't oversell infra mechanics the same way.

Semaphore medium

What it is: a self-hostable CI/CD platform, dual-licensed (Apache-2.0 core / commercial ee/), architected as 30+ gRPC microservices across Elixir, Go, and legacy Ruby, with Keycloak-delegated identity — deliberately the opposite of samen's monolith-with-planes design.

Adopt: the mcp_server pattern (Streamable HTTP, bearer-token auth, 18 read-oriented tools, audit events on AMQP, /healthz//readyz probes) as a second real "MCP as narrow, audited, read-mostly gateway" implementation to diff samen's ADR-043 tool-surface shape against, including the healthz/readyz probe convention for the fleet cockpit (S, docs comparison, no new deps); audit-log CSV export plus daily S3-compatible streaming as a concrete extension of samen's existing hash-chained audit_chain/anchor subsystem toward a demoable compliance surface for G19/DSAR-adjacent needs (M, reuses existing WORM-anchor plumbing); the Member/Admin/Owner org-role and Reader/Contributor/Admin project-role naming, with additive Groups and paid-tier Custom Roles, as proven UX vocabulary for the open G28 operator-RBAC-granularity gap (S, naming/UX only — samen's policy engine underneath stays stronger); the Apache-core-plus-commercial-ee/-folder convention as a low-friction template if samen ever wants a licensing lever without a packaging/distribution rewrite (S, a business decision to flag for the operator, not build).

Why it fits / caveat: skip the 30+-service gRPC/RabbitMQ topology outright — adopting it would directly regress samen's INV-4 single-gate, one-deploy-unit bet — and skip Keycloak-delegated auth entirely, since samen's hand-verified identity spine exists specifically to keep vaulting and masking inside its own chokepoints (ADR-035, ADR-029/031).

OLI Torus medium

What it is: Carnegie Mellon's course authoring-and-delivery LMS — a large (8,600+ commits), actively developed, real-production Elixir ~1.19/Phoenix ~1.8/LiveView monorepo with no Ash and conventional (cloak_ecto) field encryption.

Adopt: gettext+ex_cldr (+ calendars/dates-times) as a second production-scale confirmation of the G24 library stack (M); libcluster+libcluster_ec2 for real multi-node BEAM clustering, a concrete answer to the open "Oban multi-node: proven locally only" gap, transferable to whatever cloud target samen operators pick even off EC2 (S); anubis_mcp, a maintained third-party Elixir MCP server library, as a read-only comparison pass against samen's hand-built MCP server to confirm it isn't reinventing solved wire-protocol plumbing (S, evaluation only — expected outcome is "no change," same shape as the earlier ash_ai rejection); Tidewave, a dev-only MCP server for live Phoenix introspection wired into Claude Code during Torus's own development, as a process pattern for samen's AI-authored build loop (S, :dev-only dependency, zero production surface); phoenix_live_dashboard mounted in the operator plane as a cheap, well-trodden BEAM-ops-visibility addition alongside samen's existing OTel/audit stack (S).

Why it fits / caveat: MIT, and its scale (20MB+ source) makes its library choices carry real weight — but the domain (course content, LTI, learning analytics) is fully off-mission, and cloak_ecto itself is already-rejected territory (ADR-003): it works, but offers no crypto-shred or per-subject keys, so it changes nothing.

Wanderer medium

What it is: a production, revenue-generating Ash/Phoenix SaaS (EVE Online wormhole mapping) shipped as free self-hosted Community Edition plus paid hosted Cloud — the same dual-distribution model samen's fleet cockpit envisions, with zero domain overlap otherwise.

Adopt: the WandererApp.Vault primary-plus-fallback Cloak cipher pattern (decrypt against the current key, fall back to the old one on error) as a key-rotation-with-fallback-window story worth porting at samen's KMS master-key layer specifically, not the per-subject vault layer (S); the external license-manager pattern — a local cached row mirroring an external subscription-truth service, with an explicit fail-open-vs-fail-closed split on "can't reach billing" versus "billing said no" — as a second concrete reference for G13 (M); the webhook-dispatcher hardening checklist (HMAC-SHA256 signing, backoff with jitter, 1MB payload cap, 10-failure circuit breaker) as a direct audit list against samen's existing webhook surface (S, audit-and-patch, not a rewrite); cache-first authz on the SSE hot path (config flag → per-map cache → subscription cache, no per-event DB round-trip) as a pattern to confirm on samen's chat and MCP SSE hot paths (S); the self-hosted, Postgres-backed error_tracker as an INV-4-aligned alternative to third-party APM (S); git_ops conventional-commit changelog automation and the Nix-flake/devcontainer dual onboarding path as small public-repo quality-of-life picks (S each).

Why it fits / caveat: MIT, and a real Ash shop's production decisions carry weight — but its own PII mechanism (Cloak, single rotating app key) is exactly what ADR-003 already rejected for the vault proper, and its bitmask per-map RBAC is simpler but strictly less rigorous than samen's OrgScope+policy-SAT model; neither reopens a settled decision.

Net read for a product leader skimming only this section: nothing here is vendorable at the code level — two of six are AGPL (patterns only), one splits Apache/commercial — but the section earns its keep on two fronts. First, G13 stops being an open design question: Azimutt's live webhook-revalidation loop and Wanderer's fail-open/fail-closed license-cache split are two independent, production-proven answers to the two hardest parts of "wire up real billing sync," leaving mostly integration work once Stripe keys land. Second, three unprompted external confirmations of samen's own architecture — GitBlixt's approval-gated scheduled agent (ADR-047), and Semaphore's plus OLI Torus's audited MCP gateways (ADR-043) — are worth more as validation than as new design input, since samen already built the stricter version of each. Everything else is S-effort grab-bag: two more i18n confirmations (G24, already settled by the Business & Collaboration cluster), a concrete multi-node clustering answer (the open Oban gap), a role-naming convention (G28), a webhook-hardening audit checklist, and a KMS key-rotation pattern — cheap enough to pick up opportunistically rather than schedule.
