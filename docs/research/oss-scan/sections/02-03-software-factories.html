Deep Dive: Software Factories & Multi-Agent Dev Platforms

Eight self-hosted Elixir projects here are a different species from the agent-framework libraries in the previous section: none of them are runtime dependencies a product embeds. They are development-process tools — control planes that sit outside the product, delegating coding tasks to Claude Code, Codex, or similar CLI agents against a real repo, gating the result behind CI and a human merge. That makes them irrelevant to samen's product kernel (no PII vaulting, no multi-tenancy, no billing surface among any of them) but directly on-topic for two things samen already owns and is actively hardening: its own _orch/ autonomous burn-down loop, and the in-product durable agent loop (ADR-047, BUILT, accepted 2026-08-17). All eight land the same verdict as the agent-framework set — pattern quarry, not dependency — for an added reason beyond the masking-chokepoint test: five of the eight ship under licenses samen's MIT posture can't vendor from at all (GPL-2.0, AGPL-3.0, MPL-2.0, FSL-1.1-MIT), so even the three that are MIT (Pixir, Shep) are being read here for design, not code.

Cluster 1 — the tracker-driven orchestrator shape, for samen's own _orch/ loop

Four of the eight independently converge on the identical service shape: a supervised process polls a source of truth (a tracker, a backlog file), claims exactly one item under a single-authority lock, prepares an isolated workspace, runs the coding agent inside it, verifies the result, and reconciles on restart by re-deriving state from the source rather than trusting in-memory history. Symphony's SPEC.md formalizes this most completely (claim state machine Unclaimed → Claimed → Running → RetryQueued → Released, restart recovery with no database — re-poll the tracker, reuse persisted workspaces); Shep implements a scrappier version of the same idea with GitHub labels literally as the state machine ("tracker-as-database": restart and re-learn the world from label positions, no Postgres/Redis/state file); Svärm wraps it in a GenServer poll over pluggable Tracker/Runner/Provider behaviours; ControlKeel runs a lighter-weight variant purely for verification (mine failures → draft eval candidates → human-gate promotion → auto-archive on results). This is the single most load-bearing finding in the section, because it maps onto a named samen pain point almost exactly: the _orch/ loop today is session-driven and manually cranked (backlog.yaml + per-task handoffs run inside a human-launched Claude Code session), with documented failure modes — session-limit hits stranding an agent mid-task, serialized fan-outs, phase-gate tasks deadlocking when backgrounded instead of run foreground. All four projects prove the OTP idioms that would let BATON-style burn-downs run unattended between human phase gates: one GenServer authority owns claims (no two processes can double-claim an item), a supervisor tree owns each run's lifecycle, and restart recovery costs nothing extra because the backlog file — already samen's source of truth — is re-read, not reconstructed from process memory. The honest scoping: building the full service is L; a thin mix samen.orch.tick implementing just poll→claim→dispatch against the existing backlog.yaml is M and captures most of the value.

Cluster 2 — durable run-lifecycle taxonomy, for ADR-047's in-product agent loop

A second cluster targets not samen's own dev process but the agent loop it ships inside products. ADR-047 already has budgets, cost caps, and transcript retention, but per the digest it has no liveness watchdog and no vocabulary richer than pass/fail for a run that stops partway. Four projects supply exactly that missing vocabulary, and they agree closely enough to read as one design: Symphony's run-attempt states (Succeeded | Failed | TimedOut | Stalled | CanceledByReconciliation) name two outcomes samen's RunRecord allowlist doesn't — stalled (no events within a timeout) and canceled-by-reconciliation (the underlying work item changed state out from under the run); Genesis's cancellation path distinguishes graceful (mark :cancelling, give the agent three full turns to wind down, auto-commit recovered state, terminal status :cancelled with a result) from forced (immediate kill, terminal status :failed with a nil result) — never letting a forced kill masquerade as a clean stop; Camelot's session-adoption reconciler solves the orthogonal problem of a run that finished correctly but the supervising process didn't survive to record it (tee output to a durable file, write an exit-code marker only after the tee completes, and on boot a pure recovery_action/4 decides adopt-vs-fail per orphaned session, re-attaching without re-running); Pixir's checkpoint_status vocabulary (checkpoint_ready | partial | failed | held | needs_orchestrator) adds the "partial-but-usable vs partial-but-blocking" distinction that samen's Automation engine's bounded-outcome RunRecord lacks today, with a dependent_safe flag gating whether downstream steps may consume a partial result. Read together, these close the exact gap the "resume re-runs only the stragglers" fan-out memory names: a durable-marker-plus-reconciler discipline lets a resumed session adopt completed-but-unharvested work rather than re-executing it.

Cluster 3 — cost governance and operator visibility

A third theme, less architecturally novel but directly fundable, is turning ADR-047's existing budgets/cost caps from a blunt cutoff into a governed, visible economic layer. Svärm's hard-vs-hold budget modes are the sharpest single idea: instead of a silent refusal when a cap is hit, hold parks the run and routes it through the same E3 approvals engine samen already has (requester ≠ approver, enforced in policy and DB-CHECK) — composing two existing subsystems instead of building a third. ControlKeel adds the layer above cutoffs: rolling 24-hour budget windows (not just per-run totals), preflight estimate-and-block, circuit breakers on burn rate and consecutive-failure rate (not just absolute spend), cached-token accounting, and allowlisted capture of provider rate-limit headers (anthropic-ratelimit-*, retry-after) — all describable, honestly, as "records telemetry, does not pretend to throttle," the same fail-honest framing samen already applies to its adapters. Genesis's per-model concurrency slot pools (capacity from config profiles, agents block on saturation, a PeakHourEngine that swaps capacity by IANA-timezone window) is the fleet-scale sibling of the same governance problem. On the visibility side, Svärm posts append-only cost receipts to each run (tokens, model, estimated USD, explicitly labeled "estimated") and a merge-rate/$-per-outcome ROI dashboard; Hive's Inference gateway meters billable usage per model binding at its relay chokepoint; both are read-model work over data samen's chokepoint already has — they feed the roadmap's open usage-rating gap with real numbers rather than requiring a new instrumentation point. Hive's "Flights" — durable, inspectable, resumable agent executions launched from a domain object, listed and filtered per-user — is the cleanest reference for the operator-plane surface all of this cost and state data should render into: a fleet-cockpit view of agent runs, not a raw log tail.

The eight, in detail

Camelot medium

GPL-2.0, ~10★/247 commits, actively developed. A Kanban control plane for Claude Code/Codex agents built on exactly samen's stack — Phoenix 1.8, Ash 3.0 + AshPostgres + ash_oban, Oban, LiveView 1.1. Tasks move through a 6-stage state machine with human-approved plans and a pluggable runner backend (LocalPort/Docker Engine/Docker Swarm).

Adopt: the headless-Claude-Code planning output contract — a schema-validated StructuredOutput tool with a 7-level fallback parser, guaranteeing a question always persists a message and a plan is never scraped from the last transcript turn — hardens any future _orch/ planning step against exactly the class of bug it documents (ExitPlanMode not registering in headless mode). Session adoption after restart (see Cluster 2) is the other headline item. M

Why it fits: same-stack idioms transplant almost verbatim as design, and it is direct prior art for reattaching to completed-but-unharvested work instead of re-running stranded agents — a named samen pain point.

ControlKeel medium

Apache-2.0, ~11★/1,283 commits, single author, actively developed with CI/release automation. A governance control plane between agent hosts (Claude, Codex, Copilot, OpenCode) and production: deterministic pre-mutation scanning (median 52ms), decision lineage, precedent retrieval, cost governance. Plain Ecto on embedded SQLite, not Ash.

Adopt: the findings→eval-candidate→benchmark promotion loop (Cluster 1) mined from real agent-loop transcripts, human-gated into samen's existing red-team eval tier (≥90% bar, ADR-043); policy-version stamping on approval/reveal audit rows so historical decisions replay against the ruleset in force at the time; the budget circuit breakers from Cluster 3. M

Why it fits: grows samen's eval corpus from production behavior rather than hand-authored candidates, and the decision-lineage idea makes compliance answers mechanical rather than reconstructed.

Genesis medium

AGPL-3.0 + CLA, Elixir ~1.18/OTP 29 umbrella, 38★ but 5,314 commits — unusually mature OTP engineering for its size. Spawns transient LLM agents in recursive hierarchies, each in a fresh git worktree; only validated results advance the repo's "accepted version" lineage. Headline demo: a 248,989-line Rust C compiler built from empty in 123.4h for $44.38.

Adopt: per-model concurrency slot pools with peak-hour scheduling and graceful-vs-forced cancellation semantics (Clusters 2–3), plus monitor-driven workspace reclaim (Process.monitor(agent_pid), idempotent cleanup on :DOWN) as the OTP-native pattern for any samen scratch resource — export staging, generated-app probes — that should be reclaimed by monitor rather than cron sweep. M

Why it fits: independently converges on samen's own "AI outputs are proposals; only accepted results advance the persistent lineage" stance, and the cancellation/reclaim mechanics are directly portable OTP idioms, not domain-specific code.

Hive medium

MPL-2.0, ~7★/300 commits, early-stage but built by Tuist, a credible Elixir team. A "product-development system" — Forage (inbound signals), Specs, Domains, Drops (releases), and Flights (durable agent executions), all Phoenix 1.8/LiveView 1.1/Postgres/Oban, delegating agent runtime to Condukt.

Adopt: "Flights" as the operator-plane surface pattern for agent runs (Cluster 3) — typed objective/outcome vocabulary, list/filter/inspect UI, launchable from a domain object; the Slack-message/alert → structured item → agent-run pipeline is a concrete design for the open product-feedback-to-roadmap gap. M

Why it fits: it is the one project in this set that ships the missing UI layer, not just the missing mechanism — read models over agent-loop records samen's kernel already persists, no new kernel work required.

Pixir medium

MIT, developer preview — 21★/~24 commits, explicitly unstable as a library API, but backed by 39 unusually thorough ADRs. An OTP-supervised runtime for coding agents (Claude Code presenters, Zed ACP clients) whose philosophy — "summaries are not evidence; local logs and artifacts are" — reads as unusually samen-shaped.

Adopt: the five-state checkpoint-status vocabulary (Cluster 2) and the canonical-vs-ephemeral event-log split — streaming deltas broadcast for UI but never persisted, only canonical events get monotonic seq and fold into history, failures are dedicated turn_failed events, salvaged partial text is explicitly flagged. Both are near-zero-cost design inputs to ADR-047's deferred streaming work. M

Why it fits: pre-solves the dedup/replay trap for AI streaming while keeping transcripts append-only and crypto-shreddable — exactly the shape samen's own transcript retention (ADR-046) needs.

Shep medium

MIT, ~3,000 LOC, single maintainer, 0★ but 71 commits and 166 no-mock integration tests. Turns GitHub issues labeled shep into CI-verified PRs: a single-GenServer error kernel, Port-per-agent under a Task.Supervisor, tracker-as-database (no Postgres/Redis/state file at all).

Adopt: "green means a check reported" — require a named CI check to have actually reported, treat no-report-within-grace as failure, poll mergeability and treat un-mergeable PRs as red (GitHub builds no check suite for those). Also the two-phase verify-then-PR loop with capped fix turns, feeding failure logs back into the same agent session before any PR exists. S

Why it fits: closes a real false-green hole in exactly the fail-honest style samen already verifies mechanically elsewhere — cheap to encode as a rule in _orch/ prompts plus a small gh-based check script alongside verify.sh.

Symphony medium

Apache-2.0, OpenAI, ~26.8k★ — "a low-key engineering preview for testing in trusted environments," not a finished product. Ships a language-agnostic formal spec (SPEC.md) plus an OTP reference implementation: Phoenix LiveView dashboard, Burrito executables, hot code reloading without stopping running subagents.

Adopt: the full poll→claim→dispatch→reconcile orchestrator spec (Cluster 1, the section's headline finding) and its claim/run-attempt terminal-state taxonomy (Cluster 2); also worth lifting as small standalone rules: strict prompt-template rendering (unknown variables/filters MUST fail — samen's Prompt resource wants this today), and blocked-state surfacing (a run waiting on approval stays claimed and visible in state/API/dashboard, rather than disappearing into a queue). L

Why it fits: samen's dev loop already is this shape, just manually cranked — Symphony proves the exact OTP idioms (one GenServer claim authority, supervisor-per-run, restart recovery from source-of-truth with no extra DB) that would let BATON-style burn-downs run unattended between human phase gates. Full service is L; a thin poll→claim→dispatch slice against backlog.yaml is M.

Svärm medium

FSL-1.1-MIT (converts to MIT after two years, not OSI-approved today), v0.1.5, 1★/132 commits — an early solo project on exactly samen's stack (Elixir 1.20+/OTP 29, Phoenix LiveView). A gatekeeper for external coding agents: preflight checks, per-ticket isolated workspaces, humans keep the merge button.

Adopt: budget hold mode routed through E3 approvals instead of a silent refusal (Cluster 3, the section's sharpest single idea — composes two subsystems samen already has); per-run cost receipts as first-class, honestly-labeled ledger entries; a bounded mid-run pause-for-human-Q&A step kind (ask, wait ≤N minutes, fail honest to {:error, :no_human_response} on timeout) that extends "AI writes do not exist" to ambiguity mid-run instead of forcing abort-or-guess. S

Why it fits: same-stack idioms transplant directly, and every item above is a composition of subsystems samen already ships (budgets, E3 approvals, hash-chained audit) rather than new infrastructure — the cheapest cluster in this section to actually build.

Net read for a product leader skimming only this section: none of the eight are dependency candidates — five carry licenses (GPL-2.0, AGPL-3.0, MPL-2.0, FSL-1.1-MIT) that forbid vendoring outright, and even the two MIT entrants (Pixir, Shep) are pre-1.0/single-maintainer projects better read as design documents than supply chain. The value clusters into three funded-looking work items: (1) a supervised, tracker-driven orchestrator service for samen's own _orch/ loop — independently proven by four projects, and the direct fix for stranded-agent and serialized-fan-out pain that's already on record; (2) an honest terminal-state taxonomy (stalled, adopted-on-restart, partial-but-usable) for ADR-047's in-product agent loop, assembled from four projects that converge tightly enough to read as one design; (3) budget hold-mode-via-approvals plus cost receipts, the single cheapest win in the section since it composes subsystems samen already ships. Effort clusters at S–M, with one L (Symphony's full orchestrator service, though a thin M-sized slice captures most of the value).
